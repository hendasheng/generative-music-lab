## 0.1 · 基础实现

直接打开 [0.1/index.html](0.1/index.html)，无需构建或联网。内置本地合成的八秒谐波素材，也可导入浏览器支持的音频文件（最大 40 MB，使用前 30 秒、最多双声道）。文件只在本地解码，不上传。

播放后拖动波形选择取样中心。可调整位置、粒子长度 15–1000ms、密度 2–60 颗/秒、音高 ±24 半音、位置散布、立体声散布和倒放概率。绿粒子正放，橙粒子倒放；横条是该粒子读取的源音频区间，亮点按实际播放速率移动，上下位置表示左右声像，亮度按 Hann 包络变化。提前调度的粒子到发声时间才显示。

种子控制位置、声像与倒放抽样。停止后重播重置随机流；相同音源、参数及种子可复现随机序列。实时操作的结果还取决于操作时间。「换一版」只换随机序列，不改参数和音源。切到后台自动停止。

### 实现约定

- `engine.js`：纯粒子计划、独立种子随机流、原生 Web Audio 与生命周期。每 25ms 预排未来 120ms；遇到主线程长暂停，跳过过期时刻，不补发积压粒子。
- 每颗粒子：BufferSource → Hann 包络 → StereoPanner → 总线。时长以输出秒数计，源读取长度乘播放速率，取样区间限制在音源边界内；倒放使用反向副本。
- 预计重叠量 `density × duration` 控制粒子增益，最多 192 个待播放/活动粒子；onended 清节点。母带 +6dB，35–40ms 淡出入，末级压缩器用于缓和峰值，不是严格限幅器。
- 声音/画面共享音频时钟；视觉不消耗音乐随机数。改变参数只影响之后计划的粒子，最多约 120ms 调度延迟。
- 停止取消调度、淡出后清所有节点并关闭上下文。异步启动和导入分别带代次取消检查。`window.exercise.activate()` 返回 `{schedule, end, deactivate}`；schedule 重复调用幂等，end 后重播需重新 activate。
- `app.js`：音源管理、参数与 Canvas 显示；播放与种子沿用公共组件。

0.1 保留基础颗粒声音，不加入混响、XY 宏、麦克风录音或导出。后续版本可逐项扩展。

## 0.2 · XY 音色联动

入口：[0.2/index.html](0.2/index.html)。保留 0.1 独立文件。波形和音源导入继续保留，增加 XY 操作面板；拖动松手锁定，方向键微调，Shift 加大步长，Home 或「回到中央」复位。旋钮始终表示基础值；中央与 0.1 的粒子随机序列一致，宏调制使用另一条种子随机流。

四角强度由双线性角权重减去中心基准后归一化得到，因此中央全部为零，相邻区域可混合。

| 角落 | 最强时的映射（相对基础值） |
| --- | --- |
| Reverse | 剩余正放概率中 85% 转倒放；长度 ×0.55；45% 概率升八度 |
| Chorus | 长度 ×2.5；密度 ×0.75；逐粒子 ±30 cents 失谐；中心以 14 秒周期漂移 ±12% 音源长度 |
| Gater | 密度 ×1.8；固定 120 BPM 十六分音符音量门，50% 开门占比，最大衰减 95%，5ms 边沿平滑 |
| Scatter | 位置散布增加 ±25% 音源长度（上限 ±50%）；密度 ×1.5；从 0/0/+7/-7/+12/-12 半音抽样 |

没有混响。音量门作用于粒子总线，粒子可视亮度乘同一音频时间上的门控增益。倒放、长度与位置继续从实际已排程事件读取；波形上的竖线及散布带显示当前宏调制中心/范围。UI 操作对未来约 120ms 已排程事件无追溯作用。

验证：`node tools/check.cjs 0.2`，包含中央恒等、100 组 XY/时间组合、四角映射、短素材边界、节奏门相位以及原有调度/清理测试。声音审美与最终听感仍需实际试听。

浏览器验收：0.2 页面加载、XY 方向键更新、中央复位、播放/停止状态切换通过，检查时没有控制台警告或错误；未进行实际听感评估。

0.2 参数联动显示：参数主数值实时显示 XY 调制后的结果，受调制时高亮；小字显示基础值，滑杆继续编辑基础值，回到中央恢复。音高为逐粒子随机，因此显示可能范围，包含 Reverse 的八度、Scatter 的音程和 Chorus 的微量失谐，不以假平均值冒充实际音高。显示不消耗音乐随机流。

0.2 UI：采用暖灰机身、石墨色波形屏、紧凑编号参数分区及少量橙色操作强调；取消绿色发光。宽屏波形与 XY 并排，窄屏上下排列；浅灰粒子正放、橙色倒放。仅改视觉，音频规则不变。

0.2 滑块拖动修正：此前滑轨仅 3px 高，落点偏到邻近可选中文字（标签、数值、编号）上再拖动会触发浏览器原生文本拖拽，光标变为禁用符且拖拽期间滑块失灵、状态可能卡住。现整个演奏面（乐器区、页脚、注释）禁用文本选择并拦截页面原生拖拽（本页无放置目标，导入仍走点击）；滑轨命中区加高到 22px、视觉仍为居中 3px 线；窗口失焦或切后台时清除滑块编辑状态，避免丢失的 pointerup 冻结某格显示。头部种子输入不受影响，仍可正常选取文字。

## 0.3 · 位置 × 质感（基地）

入口：[0.3/index.html](0.3/index.html)。直接打开即可，无需构建或联网。0.1 基础版和 0.2 四角效果宏完整保留作为对照。

### XY 与手动控制

左右寻找片段，上下改变播放质感。横轴选择 0–100% 的取样中心；纵轴从上到下将位置散布从 0 增加到 ±50%，并逐渐提高倒放概率。

倒放映射为 `(2 × spray)^2.5`：顶端正放，中点约 18% 倒放，底端纯倒放。上半区以正放为主，下半区反向质感明显增强。Reverse 滑块可独立覆盖当前概率，不改变 XY 点；纯横向移动保留覆盖，下次纵向变化重新接管。

XY、滑块、波形和音频引擎使用同一组实际参数，数值与滑块同步更新。波形拖动仅改变取样位置；位置和散布滑块同步 XY 点，散布滑块单独操作时保留当前倒放概率。方向键微调 XY，Shift 加大步长；XY 获得焦点时空格切换自由流动。

本版不使用 0.2 的四角效果宏、随机音程、自动失谐及节奏门。粒子按实际音频时钟显示：浅灰正放、橙色倒放，阴影表示起点散布范围，读取区间仍受素材边界与音高/时长约束。轨迹录制不在本版范围内。

### 自由流动

从开启瞬间的当前值开始，位置、散布、长度、密度和立体声散布分别使用独立种子随机流，以不同幅度和周期生成目标，通过五次平滑曲线连接。音高始终不变。

| 参数 | 每段目标的游走时间 |
| --- | --- |
| 取样位置 | 6–13 秒 |
| 位置散布 | 9–18 秒 |
| 粒子长度 | 7–15 秒 |
| 密度 | 5–11 秒 |
| 立体声散布 | 11–21 秒 |

倒放跟随纵轴的散布曲线，不单独随机游走。如果开启前手动设置了倒放，用 4 秒平滑过渡到映射曲线，避免突然跳变。`flow.js` 的随机流独立于粒子抽样；相同起点、种子与操作时序可以复现。

25ms 控制定时器独立于画面刷新推进；卡顿时限制单次推进量，不追赶长时间积压。关闭后保留当前值。手动操作 XY、波形取样位置或任意参数滑块（包括音高）立即关闭整个自由流动，按钮同步关闭，松手不会自动恢复；键盘调整同样关闭。停止播放、导入素材和切到后台会关闭流动并清理定时器。未播放时也能开启观察参数变化。

### 界面布局

延续暖灰、石墨色与少量橙色强调的硬件风格。01 SOURCE 与 02 SAMPLE FIELD 是平级两栏，各自包含标题、操作面和读数。两栏共享 100px 标题行、300px 操作面及 48px 读数行，波形与 Pad 顶部和底部对齐。窄屏上下排列，操作面统一 235px。

参数区独立位于两栏下方，DOM 顺序与键盘焦点顺序一致：

- 第一排三等分：取样位置、位置散布、倒放概率，对应 XY 控制。
- 第二排四等分：粒子长度、密度、立体声散布、音高。
- 窄屏前三项各占一行，其余按两列排列，保持控制分组边界。

沿用加大的滑块命中区、指针捕获失败兜底、失焦释放和禁止原生文本拖拽处理。

### 0.3 麦克风采样

音源区新增「录制采样 · 30s」。点击后停止合成器与自由流动，再请求麦克风；按钮显示录制秒数，可随时提前停止。30 秒自动结束，随后本地解码并载入波形，点击播放使用新采样。最大载入长度仍严格裁为 30 秒；浏览器定时器暂停可能使实际采集超过该时间，因此不是硬实时设备限时。录音小于 0.25 秒或失败时保留旧素材。

等待权限可点击取消；录制中禁用播放和其他音源入口，切后台/离开页面取消录音并释放所有麦克风轨道。取消后的迟到授权也会立即释放轨道。没有实时麦克风监听，不自动播放录好的素材。录音只在本地内存中，未添加下载或持久保存。

使用浏览器 MediaRecorder 支持的格式（优先 Opus WebM/Ogg，再 MP4，否则默认格式），请求关闭降噪、自动增益和回声消除，以保留采样质感。权限与设备失败显示具体提示；若本地文件方式不可用，通过 localhost 或 HTTPS 打开并允许麦克风。API 依据：[getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)、[MediaRecorder.stop](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/stop)。

`node tools/record-check.cjs` 离线验证手动停止、30 秒定时结束、等待权限取消、拒绝权限、录音取消、过短拒绝及轨道/计时器释放。引擎原回归也通过；未进行真实麦克风录制、浏览器编解码兼容性及录音听感验收。

录制时波形屏显示橙色实时麦克风波形（REC / LIVE INPUT），由 AnalyserNode 读取 2048 点时域数据，沿用现有画面刷新循环；不是整段录音的累计波形。停止并解码成功后切换为完整采样波形；取消/失败恢复旧波形。分析节点不连接扬声器，结束后断开节点并关闭专属分析 AudioContext。离线桩增加波形读取和分析上下文清理检查；真实设备显示尚需浏览器验证。

### 0.3 听感调整：采样补偿、空间与输出

对照 [Granula 源码](https://github.com/serezhaOk/Granula/blob/db1191e8ad404d81fc20e9a69d5e7a822413198f/index.html) 后独立实现以下调整，未复制其源码或音频素材。参考提交 `db1191e8ad404d81fc20e9a69d5e7a822413198f`；仓库公开源码不代表开源许可。

- 轻采样在音频总线补偿，源 buffer 不变：统计全部声道 RMS 和峰值，目标 RMS 0.16，峰值预算 0.85，最多放大 4 倍（约 +12dB）；RMS 低于 0.001 不放大，已经响的素材不衰减。补偿使用整段素材统计，不会把局部静音自动拉满，也不保证不同素材听感等响。
- 新增独立「03 / SPACE & OUTPUT」区：混响 0–100%，默认 30%；输出 −24 至 +6dB，默认 0dB（相对既有 +6dB 母带）。两者不受 XY 或自由流动驱动，手动操作仍关闭流动。
- 自行生成 4.5 秒双声道衰减噪声脉冲，前后平滑、低通平滑噪声；并行混响发送最大 0.8，干声保持，不是等功率干湿交叉淡化。无高八度层、不改变音高。停止时总干湿一起淡出清理，不保留后台尾音。
- 默认散布改为约 ±250ms：初始八秒素材 spray=0.03125；每次成功加载音源按时长重设 spray（最大 0.5），同步 XY。Reverse 保留当前值，下一次纵向手势重新接管。纵轴最大范围仍是 ±50% 素材长度。
- 发声间隔增加 ±10% 随机变化，使用独立 `seed + ':timing'` 流；粒子位置/倒放随机流不受其消耗影响。密度仍为平均速率的目标。

母带 +6dB、Hann 窗和按重叠数量的增益补偿保留。新信号链：粒子 → bus → 采样补偿 → 干声 / 卷积混响并行 → master 淡入淡出 → 输出旋钮 → compressor → destination。压缩器仍非严格限幅器。

离线检查新增静音不提升、增益上限、瞬态峰值预算、源数据不变、默认散布时长一致、调度扰动边界、脉冲有限值及所有新节点释放；录音回归通过。尚未进行本轮真实浏览器音频渲染与试听；默认混响和输出为首轮调音值，可按用户试听继续调整。

### 0.3 内置素材去噪与高八度空间层

移除内置 demo 中主动添加的 0.015 幅度白噪声，保留谐波与包络；混响返回加入 4.5kHz、Q=0.707 低通，减轻高频噪声感。用户导入/录音的原始素材不做去噪。卷积脉冲中的衰减噪声作为滤波响应保留，不是独立持续发声的噪声源。

在混响大于 0 时，每颗主粒子以 45% 概率附加 +12 半音粒子，独立 shimmer 随机流，峰值为主粒子 40%、目标长度 1.25 倍（受素材边界限制），继承倒放方向和声像。附加粒子仅送混响，并使用相同采样音量补偿；混响为 0 时不生成，湿声归零后不可听。主音高参数保持不变；因此先前「无高八度层」的说明由本节取代。粒子显示读取该声部事件，包含实际 rate/length，湿声尾音本身不逐粒子显示。所有声部共用 192 上限，停止清理新增节点。

离线检查覆盖八度倍率、短素材/末端边界、调度与新增节点清理；尚未进行此次调音的实际试听。

### 0.3 原音与八度的音乐层次

主粒子有 15% 概率直接升高八度，峰值乘 0.8，原音仍占 85%；独立 `:harmony` 随机流，不改变 pitch 滑块。湿声高八度依旧从原始粒子事件派生，不从已升八度的主声部再升，避免意外 +24 半音。混响为 0 时仍可听到少量干声八度。没有加入四度、五度或低八度。干声八度事件有 octave=12 标记，视觉按真实 rate 移动。

自由流动的密度目标改为：开启时密度 × (开启时长度 / 当前长度目标)^0.45 × 0.8–1.2 随机系数，并钳制到 2–60；独立时间曲线平滑接近，因此长粒子倾向更疏、短粒子倾向更密，并非逐帧强制反比。起点保留当前值，手动操作仍关闭流动。离线边界/清理、十分钟流动模拟通过，尚未实际试听本轮改动。

用户已对本轮八度与长度/密度配合的听感给出正向确认；代理验证仍限于离线检查，不将用户反馈表述为代理侧测量。

### 0.3 混响清晰度与八度高频处理

### iOS：音频会被系统压低（录制后尤其明显）

**真机上「声音特别小、尤其录制」的主因不在增益，而在 iOS 音频会话类别。** 参考实现的 `engine.js` 第 24–30 行已经写明并处理了，本版原先没有搬过来：

- 默认（`auto`）会话有两个坑：输出跟着**静音开关**走；而且**采集麦克风期间系统会把整个页面的输出压低**（[WebKit #236219](https://bugs.webkit.org/show_bug.cgi?id=236219)：非 MediaStreamTrack 音频在录音时被衰减）。
- 更关键的是**离开麦克风后不切回**，iOS 会把之后的播放一直留在被压低的那一档。所以表现为「录完之后一直很小」。

处理方式（照搬参考，`engine.js` 的 `setAudioSession` + `app.js` 四处接线）：

```js
function setAudioSession(type) {
  try { if (navigator.audioSession) navigator.audioSession.type = type; } catch (_) {}
}
```

| 时机 | 会话类型 |
| --- | --- |
| `play()` | `liveSource \|\| livePending` 时 `play-and-record`，否则 `playback` |
| 录音 `onState` | `recording` / `requesting`（或实时输入开着）时 `play-and-record`，其余 `playback` |
| 打开实时输入 | `play-and-record` |
| `stop()` | `playback` |

★ `play()` 里**不能硬写** `playback`：实时输入开着时 `play()` 也会被调用，会把刚声明的 `play-and-record` 顶掉，采集期又回到被压低的那一档。判据必须是「当前是否在用麦克风」。

`navigator.audioSession` 是很新的 API（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession/type)，标注 limited availability），所以全部走特性检测 `?.()`——不支持时静默跳过，不影响旧 Safari。`tools/live-check.mjs` 装一个可写探针记录取值序列，断言**必须出现 `play-and-record`，且结束时回到 `playback`**。

#### 另一处未搬的 iOS 差异（待定）

参考实现整页**共用一个 AudioContext**，并在**首次用户手势的同一个调用栈**里同步 `prime()` 建好并 `resume()`（`engine.js` 第 15–23 行），理由是「每次 `play()` 新建 context 在 iOS 上会一律停在 suspended、完全没声音」；它对 `resume()` 还有 400ms 超时兜底，因为 iOS 缺手势时该 promise **永不 settle**。本版仍是**每次 `play()` 新建 context**（`deactivate()` 时 `close()`）。这是比会话类别更大的架构差异，**本次没有改**：它需要把上下文抬到共享层并改 `deactivate` 的所有权语义，风险与改动面都大，且要真机才能确认收益。若 iOS 上出现「第一次播放没声音、要再点一次」，多半就是这一条。（★ 2026-09-28 真机验收未出现该症状。）

### 0.3.1 输出音量：默认调大一档

起因是「声音特别小，录制和播放都小」。查参考实现（`moonlight_grains_0.4.1`）后确认：**两边的增益链代码完全相同**（`inputGain` 目标 RMS 0.16/峰值 0.85 上限、`peak = .38/√(density×length)`、master 启播淡入 +6dB、`output = 10^(volume/20)`、compressor −6dB/12:1），参考的 AnalyserNode 只是电平表、直通不改声音。差别只在两个默认值：

| | reverb | volume | 干声实测 |
| --- | --- | --- | --- |
| 改前 | .3 | **0** | 峰值 −7.5 / RMS **−15.5 dBFS** |
| 0.4.1 参考 | .65 | **6** | 峰值 −2.5 / RMS **−10.2 dBFS** |

6 dB ≈ 2 倍幅度。本版默认改为与参考一致（`reverb .65` / `volume 6`），改后真实引擎读数 **峰值 −3.4 / RMS −7.9 dBFS**（3 秒稳定段）。仍在压缩器 −6dB 阈值之上工作，峰值低于满刻度，未见削顶。

- 接线与生命周期都变了：引擎在 compressor 与 `destination` 之间加了 `AnalyserNode`，并导出 `levels()`（与参考同名，返回线性 `{peak, rms}`）。它**直通不改声音**，用途是测量与将来的电平显示。`deactivate()` 会 `disconnect()` 它。
- ★ **采样窗要够长**：启播头 1.2 秒还在淡入与起播阶段，实测 RMS −14.7 dBFS，3 秒才到 −7.9。用短窗量电平会把正常音量误判成偏小——我第一版断言就是这么误报的。
- 回归入口：`tools/live-check.mjs` 会读真实引擎的 `levels()`，断言 RMS 落在 **−12…−4 dBFS** 且峰值 **≤ −0.5 dBFS**（太小＝听不见，太大＝削顶）。改动默认增益后跑它。
- 离线桩 `tools/check.cjs` 也补了 `createAnalyser()`——桩要随被测代码一起改，否则 `levels()` 一读就崩。
- 若在 iOS 上仍明显偏小，先排除设备侧：媒体音量、以及 iOS 的**静音拨片**（Web Audio 通常不受它影响，但如果音频会话类别被降级就会受影响）。

### 0.3.1 录制波形：必须与 pad 的「起点 / 终点」同轴

用户反馈「波形和 XY pad 的起点 / 终点对不上」。根因是**两条轴语义不同**：

- pad 的横轴 `position` 是**采样位置 0–100%**（波形上的竖线、`起点/终点` 都指它）。
- 而录制中的波形原先画的是 analyser 的**43ms 时域滚动窗口**——那是**时间轴**，与位置无关。所以播放头永远对不上波形内容。

**做法：录制波形与采样波形同构**——按位置分 1000 列、随录制从左向右累积（列 = 位置）。实现放在采集侧（`recorder.js`），因为那本来就是滚动窗口的职责：

- `recorder.columns()` 返回 `{mins, maxs, have}`：每次刷新把 analyser 的当前时域块按 `floor(已录毫秒 / 25ms)` 累进对应列，一个像素列一个 25ms 桶（与解码后 `analyse()` 的 1000 列同构，所以录制中与载入后的波形看起来是连续的）。
- `have[i]=0` 的列**不画**：未录到的部分留白，波形随录制向右生长，而不是先铺满再显示成平线。
- app.js 的绘制改成按列 `fillRect`，播放头与采样波形用同一句 `params.position*w`——同一个位置量映射到同一处像素。

实时输入模式（LIVE）则用 `liveSource.peaks()`（8 秒环形窗概貌），与 pad 切到「较早 / 刚刚」的语义一致。

★ 调试这条时的两个测量坑：
1. Chrome 假麦克风默认**静音**，平线分不清「画错」还是「没输入」。要用 `--use-file-for-fake-audio-capture=<wav>%noloop` 喂已知波形（如连续 440Hz）才能验证。
2. `getImageData` 读的是**设备像素**，不受 canvas transform 影响；而绘制用的是 CSS 宽度。用「最右有笔画像素」比宽度会得出错误结论（取样区域有限时早期/后期同时被截断），**要用「有笔画列数」度量墨水量**。

回归：`tools/live-check.mjs` 的「录制波形与 pad 同轴」——断言 1.2s 与 2.7s 的有笔画列数显著增加，且早期只占左侧一小段。

### 0.3.1 录完自动播放

录制结束 → 解码载入 → **自动起播**（`onResult` 里 `load(...).then(()=>play())`）。顺序有讲究：`load()` 内部会先 `stop()`，所以必须等它 resolve 后再 `play()`，否则两者会互相抢。`play()` 的守卫（`loading` / `recordPreparing` / `recorder.active`）在 load 完成后都已复位，实测可起播。回归在 `tools/live-check.mjs` 的「录完自动播放」。

### 实时输入的响度：输入层缺口与 A/B 诊断

排查 iOS「输出偏小」时按「先定位、再补偿」的顺序做，逐条结论：

| 检查项 | 结论 |
| --- | --- |
| `getUserMedia` 关掉三项语音处理 | ✅ 本来就是（`live.js`、`recorder.js` 都显式 `echoCancellation/noiseSuppression/autoGainControl: false`） |
| Granular 后有 makeup gain | ✅ `output` 就是，公式 `10^(volume/20)`，默认 +6 dB、上限 +6 dB；实时输入与素材路径共用同一公式，A/B 才可比 |
| Gain 后有压缩/限幅 | ✅ `compressor`（−6 dB / 12:1 / knee 3 / 3 ms / 150 ms）在 output 之后、destination 之前 |
| 点击后 `resume()` | ✅ `engine.js`、`live.js`、`recorder.js` 三处都在用户手势路径上 |
| 麦克风前后输出变化 | ✅ 已用 `setAudioSession` 处理（play-and-record ⇄ playback） |
| **实时输入的输入补偿** | ❌ **原来是写死 `input.gain = 1`，等于不补偿**——素材路径有 `inputGain`（最多 4 倍），实时路径没有 |

最后一条是「麦克风输入层」的实打实缺口：iOS 采集到的麦克风电平常远低于桌面，而实时路径不做任何抬升。已改为**按环形缓冲的当前电平反复标定**，与素材路径共用同一个目标（RMS .16 / 峰值 .85 / 最多 4 倍，即最多 +12 dB），每 250 ms 重估一次、只在变化超过 5% 时改（避免把增益本身变成调制噪声）。离线断言：安静麦克风（峰值 0.02）被抬到 4 倍上限。

#### A/B 诊断入口（`window.__iosAB`，0.3.1 保留）

真机 iOS 上用它区分「麦克风输入层」与「Granular DSP 层」：

```js
await __iosAB.start()    // A：麦克风 → 直通 destination（★ 戴耳机，否则啸叫）
__iosAB.read()           // { path:'raw', gainDb, peakDb, rmsDb }
await __iosAB.engine()   // B：内建素材 → 引擎
__iosAB.read()           // { path:'engine', gainDb, peakDb, rmsDb }
__iosAB.gain(-6)         // 两条路径同时改增益，量「还差多少 dB」
await __iosAB.stop()
```

两条路径经过**同一个 output 增益公式**，音量设成相同值再比，差异就只来自 DSP。

★ **本机（Chrome 无头 + 假麦克风）量不到 A 的真实数值**：实测假麦克风峰值为 `0.0000`，两条约束都一样，所以 A 路径恒读 −99 dB。这不是接线问题。A 的数值必须在 iOS 真机上读，别拿无头结果当依据。

#### ★ 未解决：iOS 上 LIVE 的响度仍然偏小（2026-09-26）

**现状：问题没有解决。** 桌面正常，iOS Safari 上 LIVE（实时麦克风 → 引擎）输出仍明显偏小。已做的改动都没能消除它，用户实测反馈依然偏小。

已排除的（有据可查，不要再重复排查）：

| 已排除 | 依据 |
| --- | --- |
| 采集约束被语音处理干扰 | `echoCancellation/noiseSuppression/autoGainControl` 两项都已显式 `false` |
| 采集后未切回会话类别 | `setAudioSession` 已在 `play/录音/实时输入/stop` 四处接线，探针实测序列 `playback → play-and-record → playback` |
| 输出链路缺增益或限幅 | `output`（+6 dB）+ `compressor`（−6 dB / 12:1）位置正确 |
| 实时路径完全没有输入补偿 | 已改为按环形缓冲电平标定（最多 ×4 = +12 dB），离线断言通过 |
| 单纯是设备音量 | 用户已确认不是系统音量问题 |

**卡在哪**：需要真机上的 A/B 数值才能判断量级——是「麦克风采集本身就只有那么小」（那要抬输入补偿上限或换采集参数），还是「DSP 之后才变小」（那要查混响/压缩/八度层）。本机测不了（假麦克风无信号）。

**下一步（按顺序）**：

1. 在 iOS Safari 上跑 `window.__iosAB`，把 **A（`raw`）与 B（`engine`）两次 `read()` 的 `rmsDb`/`peakDb`** 记下来。
2. 按差值分诊：
   - A 与 B 接近且都偏小 → 问题在**采集层**（考虑抬 `inputGain` 上限、或改 `channelCount` / 采样率约束）；当前上限是 **4×（+12 dB）**，`gainForLevel()` 一行可调。
   - A 明显大于 B → 问题在 **DSP 层**，查实时输入路径上多出来的环节（shimmer 八度、混响干湿）。
   - 两者都远低于桌面上同素材的 B → **采集层绝对电平**问题（设备/浏览器差异）。
3. 只有拿到数值才决定补偿量；**不要先凭猜提高所有平台的增益**（会破坏已经正常的桌面端）。

★ 排查时留意：A 路径是「麦克风 → destination」直通，**必须戴耳机**，否则扬声器串回麦克风会啸叫。

### iOS 全屏适配：画布色必须与 theme-color 一致

Safari 的顶部 / 底部工具栏区域显示 **`theme-color`**，而页面画布的底色由 **`html` 的 `background`** 决定（`html` 有背景、`body` 无背景时，前者会被提升为整个视口的画布背景）。两者不一致时，收放工具栏就露出一深一浅两块，看起来像「背景没填满」。

本版原先正是这种情况：`html` = `#bfc0b8`（更深的暖灰外框），`main` 与 `theme-color` = `#deded5`。现统一为 **`#deded5`**（`html` / `body` / `main` / `theme-color` 四处同色）。

对照清单（`tools/layout-check.mjs` 逐条断言）：

| 要求 | 做法 |
| --- | --- |
| `viewport-fit=cover` | `<meta name="viewport" content="width=device-width,initial-scale=1,viewport-fit=cover">` |
| 全屏容器优先 `100dvh` | `body` 与 `main` 都是 `min-height:100dvh`（不是 `100vh`） |
| html / body / 主容器背景一致 | 四处（含 `theme-color`）同为 `#deded5`，断言按 RGB 数值比较（避免 `#deded5` 与 `rgb(222,222,213)` 的字符串误报） |
| `theme-color` 与页面背景一致 | `#deded5` |
| safe-area 不给 body 留白 | `body` 无 padding；`env(safe-area-inset-*)` 只加在 `main` 的 padding 上，背景仍铺满整屏 |

★ 副作用（有意）：`main` 有 `max-width:980px`，宽屏上两侧原本是与画布同色的外框；现在外框与内容同色，等于把那圈深色边框去掉了。这正是「背景铺满、不出现额外色块」的要求，且只在宽屏可见。

★ 探针比较颜色时要先归一：CSS 写 `#deded5`，`getComputedStyle` 返回 `rgb(222, 222, 213)`，直接比字符串会误报不一致（踩过一次）。

### 开启摄像头不得改变布局

`<video>` 有固有宽高比（1280×720）。只要它参与网格轨道计算，**一开启摄像头布局就跳**：空 video 高 0，有流之后按比例把相机窗顶高、把 XY pad 挤小、整页开始滚动。实测（竖屏 390×610）：相机窗 168.5 → 206.8px、pad 171.5 → 155px、文档高 610 → 632。

修法两条，缺一不可：

- `.camera-window video` 用 `position:absolute; inset:0` 填充，比例不再参与轨道计算（保留 `object-fit:cover`，画面仍按比例裁切、不拉伸）。
- `.camera-window` 保留 `min-height:var(--min-camera)`，且 `--min-camera` 不能取太小。它是竖屏 `1fr` 轨道的下限：给得低就先压取景窗——实测 48px 时相机窗只剩 116.5px、pad 却占 223.5px，比例失衡；扫过 48/90/120/150/180/220 后取 **150px**（390×610 下相机窗 167.5 / pad 172.5，390×780 下 252.5 / 257.5），再往上到 180px pad 就触底、文档开始变高。

回归入口 `node exercises/06-granular/tools/camera-layout-check.mjs`：用画布流替换 `getUserMedia`（走真实的 `video.srcObject` + `play()` 路径），在竖屏 610 / 780 与横屏 330 三个视口比对开启前后的相机窗、波形条、XY 窗、pad、旋钮行与文档高，**任何一项变化即失败**；同时断言**波形浮层仍在摄像头窗内、高度 ≤80px、底边贴合窗口底边**。改布局或动摄像头相关 CSS 后跑它。

★ 那条浮层断言是补漏来的：早先改 HTML 时误删了 `.sample-strip` 包装层，canvas 裸露在 `section` 里，`width/height:100%` 失去参照后按固有尺寸铺开、几乎盖住整个摄像头画面；当时探针里已经有「浮层高度 / 底边差」两个字段，但**没有断言**，`null` 也没报错，所以这个 bug 一路漏到了真机。教训：探针里量到的量要么断言，要么删掉，别留着好看的字段。

### 纵向布局修正：手机浏览器可视高度不是屏幕高度

0.3.1 是**网页**，跑在手机浏览器里，而浏览器自己的地址栏 / 工具栏会吃掉一截可视高度；`window.innerHeight` 往往只有设备屏幕高度的 70%–90%，横屏地址栏展开时甚至只剩 250–330px。此前的纵向布局用「屏幕高度」的思路写死了行高，真机上把 XY pad 压成了横向一条：

- 根因：`main` 同时设了 `height:100dvh` 与 `min-height:620px`（横屏 390px），且行高写死（`64px … 100px 32px`）。可视高度低于该下限时页面被钉住，顶部/旋钮/页脚这几行不会缩，被挤到 0 的正是那个 `1fr` 行 → `xy-group` 变矮 → XY pad 变矮，而且**没有下限**。
- 实测（改前）：竖屏可视高 610px 时 pad 只剩 **114px**、高 704px 时 **156px**；横屏虽然靠 `min-height:390px` 把 pad 稳在 180px，代价是整个下层（旋钮与页脚）被推到屏幕外，要滚 140px 才看得见。

改为「按可视高度自适应 + 该滚就滚」：

- `main` 去掉 `height:100dvh` 与像素级 `min-height`，改为 `min-height:100dvh` + `grid-template-rows:auto minmax(0,1fr)`；`body` 同样 `min-height:100dvh`。可视高度不够时页面变高并滚动，而不是把内容压扁。
- `--min-pad` 给 XY 窗一个真下限（竖屏 185px、横屏 112px，边框盒实测得 pad 净高 **155px / 84px**），`--min-knobs` 保住四旋钮行。
- `--min-camera` 也是**承重**的，不要删：相机窗没有下限时，`<video>` 会用固有宽高比把整页顶高（实测文档高 610 → 696，反而多出滚动）。这些 `min-height` 的原因都写在 `style.css` 注释里。

改后实测（Chrome CDP 按被浏览器吃掉后的高度逐个视口量）：

| 场景（可视高） | pad 高 | 文档高 / 是否滚动 |
| --- | --- | --- |
| 竖屏 844（桌面参考） | 302 | 844 / 否 |
| 竖屏 704（屏 844，栏吃 140） | 232 | 704 / 否 |
| 竖屏 610（屏 800，栏吃 190） | 186 | 610 / 否 |
| 竖屏 580（刚好到下限） | 170 | 580 / 否 |
| 竖屏 520（栏 + 键盘将出） | 155 | 549 / 是 |
| 横屏 330（屏 390） | 136 | 330 / 否 |
| 横屏 250（极端） | 94 | 288 / 是 |

即：**pad 全程 ≥ 94px，最短边不会再被压成一条**；只有可视高度低于约 580px（竖屏）或 250px（横屏）时才出现滚动，滚多少取决于缺多少。

#### 精简到「只留内容」

界面只保留四块内容：摄像头 / 波形 / XY pad / 参数（含四个旋钮）。据此删掉/收紧的东西：

- **底部状态行删掉**：`footer` 改为 `sr-only`，`#status` 与 `#recordTime` 仍留在 DOM 里（app.js 持续写入：启动失败原因、录音秒数等），对屏幕阅读器可见，但不再占版面。因此 `main` 只剩 `auto minmax(0,1fr)` 两行。
- **两个窗口标题删掉**：`01 / CAMERA` 与 `02 / POSITION × TEXTURE` 及配套 CSS 一并移除（无可操作内容，纯装饰）；顶栏品牌字也删掉。
- **波形条整条让给摄像头**：原来 `.sample-strip` 是 `.camera-group` 的第二行（46px），占掉的正是摄像头的高度。现改为**浮在摄像头窗口底部的浮层**（`.sample-strip` 绝对定位 `bottom:0`、`height:var(--wave-h)` 默认 56px、`z-index:2`），`.camera-group` 只剩一行，摄像头窗从 180 → **261px**（竖屏 610 下）。
- **波形只留粒子**：画布背景色连同 8 条网格竖线一起删掉，只画采样粒子、播放中的粒子与取样位置竖线；`#duration` 读数加重了 `text-shadow` 以便压在画面上仍可读。竖直位置由画布自身高度决定（`h/2 ± h*0.42`），不再依赖原来那套写死的 `22px` 内缩。摄像头状态文字上移到 `bottom:calc(var(--wave-h) + 12px)`，不再与波形重叠。取样位置拖拽仍可用（`#positionSurface` 叠在浮层上、`pointer-events:auto`）。
- **粒子读数要细**：粒子条原作者是 **2px**、端点圆 **r=3**，手机上会糊成一片。现改为**条 1px、端点 r=2**（`fillRect(a, y-.5, len, 1)` / `arc(x, y, 2, …)`）。粒子一多就不要再加粗，否则又会糊。
- **波形按峰值归一化**（参考实现的 `WAVE_AUTO_GAIN`）：麦克风原始电平常只有 ±0.2~0.4，按 ±1 直画又小又平，小声时几乎看不见波动。两处都归一化了：**录音实时波形**（`recorder.waveform()`，变响快/变轻慢的不对称平滑：400ms / 1600ms）与**采样波形**（`peaks`，按整段的峰值一次性算）。`WAVE_FLOOR = .02`、`DRAW_MAX_SCALE = 32` 是「最多放大多少倍」的两个闸门：
  - 素材峰值 ≥ 0.031（约 −30 dBFS）→ 一律放大到铺满；
  - 0.02…0.031 → 按 `1/peak` 放大（上限 ×50）；
  - 低于 0.02 → 停在 ×50，避免把底噪放大成满屏（−30 dBFS 以下本来就当噪声处理）。
  实测（56px 浮层）：峰值 0.01 → 7.5px，0.02 → 15px，0.05 → 23.5px，0.4 → 23.5px。
  ★ 显示增益**只影响画面，不改音频**；`DRAW_MAX_SCALE` 一开始设成 8 是被 `WAVE_FLOOR:0.12` 挡住的（`1/0.12 = 8.33`），真正的闸门是 floor 而不是 cap——调这两个值时先看 `1/floor`。
  `tools/live-check.mjs` 分两档断言：峰值 ≥0.02 的柱子必须 ≥12px（看得清），峰值 0.01 的必须在 4…30px（可见但不糊满）。
- **XY pad 与参数区之间不要分隔线**：`#coreParameters` 去掉了 `border-top`。`tools/live-check.mjs` 断言它 `border-top-width` 为 0。
- **XY pad 下方的读数行删掉**：`#xyDescription`（「位置 35% · 散布 ±3% · 倒放 0%」）从 DOM 移除，`xy-window` 不再需要两行网格（`.xy-pad` 改为 `height:100%` 填满）。同一行文字仍写进 `pad` 的 `aria-label`，读屏仍有反馈。这 28px 直接归 pad：竖屏 700 下 pad 230.5 → **258.5px**。
- **坐标文字收紧并回中**：四个 `.axis-label` 的盒子原来是 12px 字 + 3px 上下 padding = 18px，现改为 `line-height:1` + `1px 4px`，盒子正好等于文字高；`起点 / 终点` 原来只有 `top:50%` 没有回中，盒子中心比 pad 中线低 9px（半个盒高），补 `translateY(-50%)` 后与 `padCenterY` 完全相等。上下两个离边从 27 / 18px 收到 10 / 6px。
- **旋钮去掉外圈**：原来的外圈来自 `box-shadow:inset 0 0 0 5px` 加 7px 内缩的深色圆盘，视觉上就是一圈多余的环。现改为单层空心圆（1px 描边）加橙色指针，直径 52 → 46px，指针与圆等径只做旋转。
- **旋钮区收紧**：`--min-knobs` 100 → 84px（横屏 88 → 72px），内边距 8 → 6px，标签与读数统一 9px。命中区改用 `inset:0;margin:auto` 与旋钮同心，不再手算 `left` 偏移。

省下的高度自动流向摄像头与 XY pad（两者都是 `1fr`）。竖屏 610 下：pad 172 → **186px**，相机窗 167 → **180.5px**；竖屏 780 下分别为 270.5 / 265.5px。

不要退回「写死行高 + 像素级 min-height」的写法。改布局后跑 `layout-check.mjs`：它会断言所有视口的 pad ≥ 80px，并在 390×610 下实测 XY pad 拖动与旋钮拖动是否仍然响应（尺寸好看但拖不动不算通过）。

### 0.3.1 验证（当时范围）

## 0.3.2 · 精简顶栏

基于 0.3.1，**声音与参数一律未改**，只动顶栏：去掉实时输入（不加载 `live.js` / `live-worklet.js`，无 LIVE 按钮与 `window.__iosAB` 诊断）、菜单按钮在移动端隐藏（菜单内的功能一项没删，桌面仍可用），顶栏改为**自由流动最左、录制中间、播放最右**。

### 去掉实时输入的理由（不是版式取舍）

**产品理由：它在 iOS 上目前处理不好。** 只把版式说成「精简顶栏」会让人以为这是纯视觉取舍，进而在别处又把它加回来——所以依据一并记在这里：

| 依据 | 出处 |
| --- | --- |
| iOS Safari 上实时麦克风 → 引擎的输出**明显偏小，问题未解决** | 本文「★ 未解决：iOS 上 LIVE 的响度仍然偏小」一节（2026-09-26） |
| 已知的 iOS 会话坑：默认 `auto` 下输出跟静音开关走；**采集麦克风期间系统会把整个页面输出压低**；离开麦克风不切回 `playback` 就会一直留在被压低的那一档 | [WebKit #236219](https://bugs.webkit.org/show_bug.cgi?id=236219)；`engine.js` 的 `setAudioSession` 注释 |
| 唯一的分诊入口 `window.__iosAB` 需要**真机数值**才能继续；本机（Chrome 无头）量不到——假麦克风峰值为 0.0000 | 本文「A/B 诊断入口」 |
| 已排除的原因（采集约束 / 会话类别 / 输出链路增益 / 实时路径无补偿 / 设备音量）逐条有据，**不要重复排查，也不要凭猜提增益** | 本文「已排除的」表 |

取舍：与其在一个**在主力平台上只有一半能用**的功能上继续加控件，不如把它整体退出这一版，留在 0.3.1 里继续排查。桌面端实时输入本身是正常的（引擎与实时路径**与 0.3.1 逐字节相同**），所以这不是引擎缺陷，是平台适配没做完。

★ **用户已在桌面与 iOS 真机上验收 0.3.2：没问题（2026-09-28）。** 这条反过来证明了上述取舍是对的——去掉实时输入、保留录制链路之后，主力平台上是可用的；也就是说「iOS 上不好」的**范围仅限实时麦克风 → 引擎那条路**，录制采样、摄像头、录完自动播放都不受影响。**不要**把「iOS 有问题」当成整个 0.3.2 的结论，也不要把这条历史问题当作删除录制或再砍功能的理由。

由此推出两条边界，改动时别越界：

- **「录制采样」必须保留。** 两者都要麦克风，但录制走 `MediaRecorder` + 解码，不依赖 AudioWorklet 实时取窗这条链路；它也是目前唯一能在手机上换音源的手段。录音期的 `setAudioSession('play-and-record')` 一并保留——**这条与实时输入无关**，是 iOS「录完之后声音一直很小」的必需修复，且现在已有真机验收背书。
- **实时输入不是死了，是搬去 0.3.1 了。** 要接回来，先解决本文「未解决」一节（拿到真机 A/B 数值再决定补偿），并**从 0.3.1 搬**它已经调过的实时补偿与 `columns()`，不要在 0.3.2 里另写一套。★ 搬之前先想清楚代价：0.3.2 现在是**两个平台都验收过的版本**，把一条只有桌面正常的链路加回来，等于把一个已验收版本重新变成「一半可用」——没有真机 A/B 数值之前不要动。

## 内置音源库与随机音源按钮（2026-09-28）

用户要求：「0.3.2 顶部左侧，自由流动右边增加新 icon，随机的 icon，点击切换几种内置音源」。

**做法**：音源库放在**引擎**里（`demo(ctx, index = 0)` + `demoNames`），不是放在 app.js。理由是 `demo()` 本来就是引擎自带的素材生成器，三份引擎的这段代码逐字节相同，换素材不该各版本各写一套。UI 只有 0.3.2 有，0.3 / 0.3.1 仍只调用 `demo(ctx)`（= 0 号），行为不变。

| 号 | 名字 | 时长 | 做法 | 峰值 | RMS |
| --- | --- | --- | --- | --- | --- |
| 0 | 谐波片段 | 8.0s | 首版那段，**循环体一个字没动** | 0.390 | 0.158 |
| 1 | 钟形泛音 | 6.0s | 非谐分音 1 / 2.76 / 5.4 / 8.93 × 指数衰减，四次敲击 | 0.402 | 0.085 |
| 2 | 拨弦余韵 | 6.0s | Karplus-Strong 延迟线，五音依次拨响 | 0.352 | 0.038 |
| 3 | 人声共振 | 8.0s | 脉冲列过三个共振峰，颤音 + 逐句换音高 | 0.332 | 0.053 |

第一版还有第 2 号「**噪声气流**」（白噪过一阶低通、截止缓慢开合）。用户听完要求删掉：**白噪底在颗粒化之后只剩「嘶声」**，既没有音高结构、也没有另外三段的层次，留着只会稀释「换一段素材」的意义。删掉后就是上表这 4 段，索引重排为 0–3（拨弦 3→2、人声 4→3，`demoSeconds` 与注释同步改；它们的噪声种子随之从 `demo-3` 变 `demo-2`，素材内容有细微不同，但没有对外承诺过稳定性）。

**几个定下来的行为**（用户没指定，按最不意外的选，都写在 README 里）：

- **随机不立即重复**：`while (next === sourceIndex)` 保证连点两次不会听到同一段。
- **点了就出声**（用户要求「点击自由流动 / 随机，都自动播放」）：随机键在 `load()` 完成后统一 `play()`（不再区分「本来在响」）；自由流动在 `toggleFlow()` 的**开启**一侧 `void play()`——放在这里而不是按钮的 `click` 里，因为 pad 的空格键也走 `toggleFlow`，两个入口必须一致。**关掉流动不停声**（只是停止参数游走）。`play()` 自带 `engine / starting / loading / recorder.active` 守卫，连点不会叠引擎；随机键另外判 `!loading`：这次载入若已被下一次点击顶掉，就不抢着起播，交给新的那次。
- **录完/导入不影响「上一段是第几号」**：`sourceIndex` 只在载入内置音源时更新，所以录一段麦克风采样之后再点随机，仍然从内置库里挑。
- **屏幕上不加文字**：用户要求界面只留摄像头 / 波形 / pad / 参数，采样名只更新菜单里的 `#sampleName` 与按钮的 `aria-label`（「随机内置音源（当前：…）」）。
- **XY 下轴标签「散开 / 纯倒放」→「散开 / 倒放」**（用户要求）：去掉「纯」。映射本身没变（底端仍是纯倒放，`reverse = (2 × spray)^2.5`），只是标签不再用一个容易读成「另一种模式」的字。0.3.1 与 0.3 的标签没动。
- **十字线收到文字之间**（用户要求「xypad 线也不要超过文字」）：横竖两条线原来 `width/height:100%`，铺满整个 pad，两端从「起点 / 终点 / 聚焦·正放 / 散开·倒放」的外侧戳出去（标签有不透明底色，所以线是被遮住的，但**两端仍露在文字外面**）。改成用内缩变量：`.xy-pad{--cross-x:38px;--cross-y-top:24px;--cross-y-bottom:20px}`，横线 `left/right` 用它、竖线 `top/bottom` 用它。

数值不是猜的，是按标签实测盒子 + 2px 间隙算出来的（390×844、dpr 3 实测）：

| 量 | 实测 | 内缩取值 |
| --- | --- | --- |
| 起点 / 终点 | 宽 28px、距左右边各 8px | 左右各 **38px** |
| 上标签「聚焦 / 正放」 | 底边距 pad 顶 22px | 上 **24px** |
| 下标签「散开 / 倒放」 | 顶边距 pad 底 18px | 下 **20px** |

★ **改标签文字、字号或 `top/bottom` 偏移都要重新量**（临时量测脚本会直接打印需要的内缩值）。`layout-check.mjs` 现在把这条钉住了（`padCross`）：四个间隙必须 ≥0 且线长 >0，13 个视口实测全部 2px 间隙、最短的竖线出现在「极短横屏 极端」= 66px。

### 双击旋钮回默认值 + 去掉双击的灰方块（同日）

用户要求「四个参数旋钮，像 maxmsp、ableton live 那种，双击恢复默认值；现在双击会闪一下灰色的方块，要去掉这个」。

**灰方块是谁**：旋钮上盖着一个 52×52 的隐形 `<input type=range>`（`opacity:0`，拖拽与键盘都靠它），双击命中的就是它；iOS 会给被点到的元素盖一层 **tap highlight**，尺寸正好是那个 52×52 的方块。文字选中高亮可以排除 —— `#coreParameters` 在 `.performance` 里，早就 `user-select:none` 了（探针也量了：真实双击后 `getSelection()` 为空）。

**做法**：

- 旋转钮的 `dblclick` → 写回 `Granular.defaults[key]` 并调 **`setParam()`**（停自由流动、钳范围、刷读数与 `--dial-angle`、同步 XY 点，与拖拽同一条路；四个常驻旋钮的默认值 180 / 24 / 0.8 / 0 都是 step 的整数倍，写回 input 不会吸附跑偏）。
- `.core-parameter,.parameter,.core-parameter input{-webkit-tap-highlight-color:transparent}`。

**验证**（`layout-check` 退出码 0）用 **CDP 真实鼠标事件**双击（合成事件没有双击语义、也不会触发选中）：

```
密度 40 → 双击 → 24（默认 24）  读数 "24 /s"  指针角度 -32.59deg
双击后的文字选中: ""（应为空）  tap highlight: rgba(0, 0, 0, 0)  user-select: none
```

★ 顺带一条：菜单里的五个滑杆**没有**加双击回默认（用户只要求四个常驻旋钮）；要加就是把同一段监听挪到 `if(core)` 外面，但 `spray` 的默认值跟素材时长有关（`Granular.defaultSpray(buffer.duration)`），不能直接取 `defaults.spray`。



### XY pad 上下标签只留「聚焦 / 散开」（同日）

用户要求「xypad 上下文本，只保留 聚焦 散开，文档里记录正方倒放的相关功能就好」。

- 标签：`聚焦 / 正放` → **`聚焦`**，`散开 / 倒放` → **`散开`**（左右仍是「起点 / 终点」）。

### 随机键的灯跟着播放状态（同日第三调）

用户要求「随机 icon，从播放切换到暂停时，随机 icon 也要关掉」。

灯的条件原来是「素材是随机选的」（`materialBuiltin && sourceRandom`），所以停下来了它还亮着。现在加上播放状态：

```js
const playing = !!engine || starting;
sourceButton.setAttribute('aria-pressed', String(materialBuiltin && sourceRandom && playing));
```

`stop()` / `play()` / `load()` 三处都调 `syncSourceMark()` —— 引擎状态变了灯就得跟着变，少一处就会出现「停了还亮」或「播了不亮」。

★ 两个实现细节：① 初始调用 `syncSourceMark()` **必须放在 `engine` / `starting` 声明之后**（它读这两个 `let`，放前面会撞 TDZ）；② 语义上「灯 = 这段随机素材正在响」，所以**再按播放会重新亮**——素材还是那一段。要改成「灭掉就等到下次点随机」是另一种语义，改一行即可（把 `playing` 从条件里去掉，改成在 `stop()` 里把 `sourceRandom` 置假）。

实测（`live-check` 退出码 0）：

```
随机键的灯：播放中=true → 暂停后=false（应灭） → 再播放=true（素材仍是随机选的，应回亮）
```

### 轴标签与坐标线：拖动时更实、不拖动时更淡（同日）

状态不用新造：pad 上那个 `.pressing` 类本来就是「拖动中挂着、松手/取消/切后台摘掉」（拖尾与控制点放大也用它）。四组颜色收进 pad 的两个变量对：

### XY pad 的层序：控制点必须在最上层（同日）

用户反馈「现在 xypad 坐标在控制点上层，应该是控制点在【最】上」。

先量再说（临时脚本读 `elementsFromPoint` 的命中顺序，装饰元素平时 `pointer-events:none`，量之前临时打开）：

| 控制点位置 | 命中顺序（上→下） |
| --- | --- |
| 正中（十字线交点） | `xyDot > xy-trail > cross vertical > cross horizontal` ✓ |
| 顶边 | `xyDot > xy-trail > xyPad` ✓ |
| **左边** | **`axis-label left > xyDot > …`** ✗ 被「起点」盖住 |

所以十字线本来就在控制点下面（DOM 顺序里 `.cross` 在 `#xyDot` 之前），真正压住控制点的是**轴标签**：它为了盖住底下的点阵带了不透明底色，而 `z-index:2` 又比控制点的 `auto` 高。

修法：`.xy-trail{z-index:3}`、`#xyDot{z-index:4}` —— 拖尾与控制点都在标签之上，且保持「拖尾贴着控制点」的连贯（贴边拖动时标签会短暂被盖住，这是拖动反馈优先，静态装饰让位）。

探针新增断言（`layout-check` 交互回归）：把控制点拖到左边缘，读它中心的命中顺序，`stack[0]` 必须是 `xyDot`：

```
控制点滑到「起点」底下时的层序（上→下）：xyDot > xy-trail > axis-label left
OK：控制点在最上层（标签盖不住它）
```

★ 这条和「十字线不越过轴标签」是一对：**标签之间的空白**归十字线，**标签本身**归控制点让路 —— 别把 `z-index` 一起调了（把标签压到控制点下面，它那层不透明底色就白留了）。

### 控制点加拖尾（同日，返工三次）

用户要求「xypad 点，拖动的时候增加拖尾」。

**第一版做错了**（用户原话「你是在敷衍还是真的没懂，目前实现的完全不是拖尾」）：做成 **6 个渐隐渐小的残影圆点**（DOM span）。残影点和拖尾是两回事 —— 拖尾是一条连续的、由头部向尾部逐渐变细变淡的带子；一串离散的点无论怎么调间距、尺寸都不会变成带子。

**第二版仍然错**（用户原话「拖尾极差，能看到一个一个圆点」）：改成 canvas 折线，但**分成 20 段分别描边**，每段自己的线宽 + 透明度 + `lineCap:'round'` —— 每段的圆端帽就是一颗颗胶囊，段间透明度差让它们更明显。

**第三版还是不行**（用户原话「像是一个蝌蚪，触发的时候按钮会变大你忘了吧，还有拖尾的曲线要圆滑处理，不要有硬折角」）：两处硬伤 ——
① **头宽写死 6.4px**，而按住时控制点已经被放大到 1.5 / 2.5 倍（19.5 / 32.5px），于是"大圆头 + 细尾巴"= 蝌蚪。宽度剖面必须**读控制点当前直径**：`dot.getBoundingClientRect().width`（它已经含放大后的尺寸），头宽 = 该直径，尾部收到 0。
② **折线直接连一定有硬折角**，前面加两遍 3 点平滑也去不掉"一段一段直"。改成 **Catmull-Rom 插值**（穿过所有采样点的光滑曲线，不是逼近）把稀疏样本重采样成每 ~3px 一个点的密集路径，再算左右边界。

**现在这版**（`app.js` 的 `paintTrail` + `resamplePath`）：密集光滑路径 → 每个点按前后邻居求法线、左右各偏 `halfW(i)`（`(dotW/2)·(i/(m-1))^0.9`）→ 填成一个多边形（一次 `fill`）→ 透明度走一条沿带子的线性渐变（头 `.5` → 45% 处 `.18` → 尾 `0`）。

**填充多边形在结构上就不可能有端帽与接缝** —— 这是核心认识：*描边* 天然带端帽（`lineCap:'butt'` 在拐角露缝，`'round'` 就鼓成一颗颗点），要"连续的带子"就得用**填充**；而**光滑**只能靠插值重采样，不能靠平均平滑。

探针判据也补到能挡住这两类错误 —— 上一版只量「墨迹横跨多少列」，**验不出胶囊链**（胶囊彼此相连，列是连续的）。现在同时量**连续墨段的段数**：

```
控制点拖尾（canvas）：拖动中 16726 个墨点 / 横跨 371 列 / 1 个连续段  松手 1.5s 后 0 个墨点
控制点 静止 13x13  →  触摸按住 32.5（×2.50）
```

（分段描边那版会给出 20 段。）

★ 三次返工的教训：**判据要贴着用户能看见的形态**（连不连续、有没有一粒粒的鼓包、拐角圆不圆、头部跟不跟得上放大的控制点），而不是贴着自己的实现（有几个元素、横跨多少列、写死的头宽）。第一版数"点数"、第二版数"列数"，都能在自己的错误目标上全绿。


### 波形改成「稀疏竖线」（同日）



用户要求「就用竖线，但不用这么密集」。

原来 `peaks` 是 1000 列，画的时候 `colW = max(1, w/1000)` → **1px 宽的柱子按 0.36px 的间距重叠**画，所以糊成一整块实心波形，看不出是一根根线。

改法：**按固定像素间距取线**，不看数据点数 —— `lineCountFor(w) = clamp(round(w/6), 24, 96)`（手机 390 宽 ≈ 61 根、间距 6px；桌面宽屏封顶 96 根），每根线**聚合它覆盖的那几列的真实 min/max** 再画。

★ 关键：**不能改成「每 g 列取一列」那种抽稀** —— 只取单列的极值会丢掉组内的峰值，弱音处线条会整体变矮（包络看着比真实的小）。聚合 min/max 才是"少画线、但仍画真实包络"。

录制中的立柱**同一套**（否则一开始录制，条带会突然从稀疏线变成实心块）：按同样的间距把 `recorder.columns()` 分组取 min/max，未录到的列不画 —— 2.5 秒录到 7 根，形状与静态波形同构。

实测（临时截图脚本，390×844 dpr 3，数画布上半部分的连续墨段）：

| 状态 | 竖线段数 | 段宽（设备像素） |
| --- | --- | --- |
| 静态（播放中） | 61 | 2 |
| 录制中（2.5s） | 7 | 2 |

`live-check` 的录制墨量断言仍绿：`1.2s 有笔画列=7 → 2.7s=15`（判据是「后 ≥ 前 × 1.5 且起点只占左侧一小段」）—— 稀疏化之后这个比值从 ~2.1 掉到刚好过线附近，所以这条判据的余量比原来小了，将来再调密度要一起看它。

### XY 控制点：手指按住放大 2.5 倍、松手慢回落（同日第二次调）

用户反馈「移动端拖动的时候尺寸要更大，现在的尺寸已经被手指覆盖住了……还有手指离开恢复尺寸的时候过渡要慢一点，现在看得出来是有过渡的，但是太快了」。

- **尺寸分档**：原来只有一档 `scale(1.5)`（13px → 19.5px）。手指肚比这大得多，所以按 `pointerType` 分档：**触摸 2.5 倍（32.5px）**、鼠标/笔保持 1.5 倍。类在 pad 的 pointerdown 里 `classList.toggle('pressing-touch', e.pointerType === 'touch')`，CSS `.xy-pad.pressing.pressing-touch #xyDot`（比 `.xy-pad.pressing` 更具体，不受书写顺序影响）。
- **松手要慢**：原来是 `transition:transform .09s` 一条管两头，按下和松手一样快。改成**两档过渡分别写在两个状态上**：`.pressing` 里写 `.08s ease-out`（放大跟手），基础态写 `.45s cubic-bezier(.22,.61,.36,1)`（松手回落）。类加上时用前者的过渡、类摘掉时用后者的 —— 这是 CSS 里做「按下快、松开慢」的标准手法。

探针（`layout-check` 交互回归，退出码 0；`fire()` 现在带 `pointerType` 参数，触摸与鼠标各按一次做对照）：

```
控制点 静止 13x13 描边 0px none
      触摸按住 32.5 (×2.50, touch=true, 过渡 0.08s)
      鼠标按住 19.5 (×1.50, touch=false)
      松手 160ms 后 19.5（过渡 0.45s，应仍大于静止值）→ 500ms 后 13
```

★ 注意「松手 160ms 后仍是 19.5」这条断言的意义：它证明回落**真的在慢慢走**，而不只是「过渡时长写了 0.45s」——只读 `transitionDuration` 会被「属性写了但没生效」骗过去。

### 点 XY pad 不该长描边（同日）

用户要求「点击 xypad 周围会有一个描边，去掉这个描边」。先量清楚是谁画的（不能猜）：

- 点 pad 之后 `:focus` 确实落在 `.xy-pad` 上（`document.activeElement` = `div#xyPad`）；
- **无头 Chrome 里 `:focus-visible` 是 false**（指针焦点不匹配），所以探针里看不到环 —— 但 **Safari 会把手指点出来的焦点判成 `:focus-visible`**，于是 `.xy-pad:focus-visible{outline:2px solid var(--accent);outline-offset:-3px}` 那个内缩主色环就出现在真机上；
- 另一个同源的东西：`.xy-pad` 带着浏览器默认的 `-webkit-tap-highlight-color`（点击时的一层高亮）。

做法：

- 焦点环**只留给键盘**（pad 支持方向键与空格，环不能一起删掉）。在 `pointerdown` / `keydown` 上切 `.pointer-focus` 类，CSS 加一条 `.xy-pad.pointer-focus:focus{outline:none}`（比 `:focus-visible` 那条更具体，点出来的焦点一定没有环；按任意键摘掉类，环回来）。
- `-webkit-tap-highlight-color:transparent`，去掉点击高亮。

★ **不要把这个类挂在 `focus` 事件上**：第一版写的是 `pad.addEventListener('focus', …)`，探针实测 `.pointer-focus` 从来没挂上 —— 无头里 `document.activeElement` 已经是 pad 了，**但 pad 的 `focus` 事件一次都没触发**（页内计数器为 0）。改挂 `pointerdown` / `keydown` 后立刻成立（类挂着而 pad 没焦点是无害的，CSS 用 `:focus` 限定）。

探针（`layout-check` 的交互回归段，退出码 0）：点击后 `outline: none` 且 `.pointer-focus=true`；再点一次仍然如此；派发一次键盘事件后类被摘掉（关环规则退出，环交回 `:focus-visible` 决定）。

### 随机键的「触发状态」：常亮（外加 400ms 过渡）（同日）

用户反馈「随机 没有触发状态」。确实没有：自由流动有 `aria-pressed`（开着时图标是主色）、录制有红块三态，而随机键是一次性动作，点下去只有异步的换素材，界面上什么也没变。

**第一版（错，只做了过渡）**：点击处理器的同步段挂 `aria-busy="true"`，CSS 把它点成主色，换完撤掉。★ 加最小时长是必须的：探针实测「换素材 + 重建引擎」只要 **75ms**（连测四次都是 75），亮 75ms 肉眼看不见 —— 所以 `SOURCE_LIT_MS = 400`，`finally` 里补足差额再撤。

★ **量它时踩的坑**：第一版探针用 `while (busy) { await setTimeout(25); lit += 25 }` 计时，算出 175/350/200/275ms 这种数——嵌套到第 5 层后 `setTimeout` 被浏览器降频到 ~4ms，按次数累加出来的毫秒数没有意义。改成在**固定时刻读属性**（点下那一帧 / 300ms 后各读一次），断言才有意义。这条也写进了 `AGENTS.md`（和「无头里 rAF 被节流」并列）。

`live-check` 现在断言四件事：换素材前（素材是录音采样）不该亮；点下那一帧 `aria-busy === 'true'` 且计算色 = 主色；300ms 后仍亮着；**换完保持 `aria-pressed="true"` + 主色**（不再自己熄灭）。

★★ **同一天又被纠正一次：我把它做成了「动作反馈」，用户要的是「状态」** —— 原话「随机 icon 触发有逻辑问题，现在只是亮了一下，就又成未触发状态了」。也就是说亮完自己熄灭本身就是 bug：这个键应该像自由流动那样是**一盏灯**。

改成两层语义（`app.js`）：

| 层 | 属性 | 含义 | 时长 |
| --- | --- | --- | --- |
| 过渡 | `aria-busy="true"` | 这一次点击正在换素材 | 换素材 + 重建引擎的时间，**最少 400ms** |
| 状态 | `aria-pressed="true"` | **当前这段素材是随机键选的** | 一直亮着，直到素材被别的路径换掉 |

状态由两个布尔量决定：`sourceRandom`（这段内置素材是随机选的；启动时的 0 号不算）与 `materialBuiltin`（当前素材是内置音源；导入文件 / 麦克风录音之后就不是）。`load()` 里更新 `materialBuiltin` 并调 `syncSourceMark()`，随机键在换之前把 `sourceRandom` 置真 —— 两个入口写**同一处**状态，不各写一份。

探针实测（`live-check`）：

```
换素材前（素材=麦克风采样）：pressed=false 色=rgb(37,38,36)   ← 录音素材，不该亮
点击瞬间：true/rgb(237,91,42) ×4                              ← 过渡态立刻亮
换完之后：true/rgb(237,91,42) ×4                              ← 常亮，不再自己熄灭
300ms 后仍亮着：true ×4
```

★ 教训：**「加个反馈」和「加个状态」是两件事，先问清是哪一种**。一次性动作的反馈可以闪一下，但用户说「触发状态」时指的往往是能持续指示当前状态的那盏灯；两次都猜错说明该在动手前用一句话确认语义（这次连改两轮，代价比问一句大）。



### 主色调收成一个变量（同日）

用户要求「主色调的这个橙色用一个变量表示，告诉我在哪，我自己调下颜色」。查下来 `--accent` 早就存在，但橙色族有 **4 处写死**：CSS 的旋钮指针 `#ed5b2a`、app.js 的录音波形柱与 `REC / LIVE INPUT` 文字 `#ed5b2a`、倒放粒子 `#f37944`、录制中的播放头 `#ffd9c6aa` —— 改变量只影响焦点框、按下态图标和 XY 圆点，**画布上的橙色不会跟着变**。

做法：`0.3.2/style.css` 里 `:root{--accent:#ed5b2a;--accent-reverse:#f37944;--accent-soft:#ffd9c6}` 成为唯一定义（原来 `--accent` 在大 `:root` 行里还有一份，**删掉了** —— 留两份的话改第一处不生效，正是这个需求要避免的坑），旁边一段注释写清每个变量管什么。`app.js` 顶部启动时读一次，得到 `ACCENT / ACCENT_REVERSE / ACCENT_SOFT`（括号里的十六进制只是读不到变量时的兜底），画布只用这三个常量，JS 里不再有颜色字面量。播放头的 66% 透明度改成 `globalAlpha=.67` 画，不再靠 `aa` 后缀拼字符串（那样用户一旦写 `rgb()` 或 8 位 hex 就会拼坏）。

**验证**（一次性探针）：让探针把发出去的 `style.css` 当场改写成 `--accent:#0f0; --accent-soft:#f0f; --accent-reverse:#00f` 再加载 ——

| 检查 | 注入覆盖 | 默认 CSS |
| --- | --- | --- |
| 变量读回 | `#0f0 / #f0f / #00f` | `#ed5b2a / #ffd9c6 / #f37944` |
| XY 圆点（CSS 侧） | `rgb(0,255,0)` | `rgb(237,91,42)` |
| 录音画面（画布侧） | 纯绿 1400 像素（波形柱 + 文字）、品红 208 像素（播放头） | 0 / 0 |
| 播放画面（倒放粒子） | 纯蓝 150 像素 | 0 |

★ 探针踩的三个坑，都不是被测代码的问题：(1) 覆盖 CSS 变量不能靠注入 `<style>`（插在 `<head>` 之前会被页面的 `style.css` 按源码顺序压掉），也不能靠 `addScriptToEvaluateOnNewDocument` 里写内联样式（那一刻 `document.documentElement` 还不存在）——**最可靠的是直接改发出去的 CSS**；(2) 扫画布必须在**录制中**，停下来之后 `draw()` 会切回采样波形，录音柱与播放头就没了（第一次扫出 0 就是这么来的）；(3) 需要 `--use-fake-device-for-media-stream`，否则无头里 `getUserMedia` 拿不到设备、录制根本不开始（`live-check` 一直带着这两个 flag）。


**验证**：

- `check.cjs` 新增一段内置音源库断言（三个版本都跑）：4 段都非静音、峰值 ≤1、互不相同、可复现（同号两次逐字节相同）、段尾不硬切、索引取模回绕；**并用首版公式复算 0 号，逐样本比对** —— 这是「不许因为加了音源而改原有声音」的钉子。
- `engine-sync-check.cjs 0.3.1/engine.js 0.3.2/engine.js` 仍全绿（导出面 14 项：`demoNames` 进了清单；12800 计划事件 + 1200 对八度派生 + 36 次 `BufferSource.start` 逐字节一致）→ 两版引擎仍逐字节相同（删掉噪声气流后 MD5 `1bbd12ea…`）。
- `live-check.mjs --version 0.3.2` 一轮浏览器：命中区全部 ≥44×44、垂直中心偏差 0、录制仍居中 195、顺序「流动 36 ＜ 随机 ＜ 录制 195 ＜ 播放 354」、控制台无错误；点四次随机音源实测每次都换到另一段、换完仍在播（当时序列里还有噪声气流），**单击整体耗时 609–722ms**（含 500ms 的落定等待，真实开销约 110–220ms，其中大头是换素材后重建引擎时的混响脉冲响应）。
- 「点了就出声」也在同一轮里断言（`=== 点一下直接出声 ===`）：停着的状态下点自由流动 **74ms** 起播、关掉流动后仍在播；再停着点随机 **67ms** 起播。

### 探针的假红：录制波形断言（同日修）

加完「点了就出声」后跑 `live-check`，`=== 录制波形与 pad 同轴 ===` 报了 `1.2s 有笔画列=714 / 2.7s 有笔画列=9` 并判失败。**不是代码回归**：录制按钮点下去之后，app 要先把引擎 `stop()`、再 `await getUserMedia`，那一轮真正进入 `recording` 用了 **>1.2s**，于是第一次采样量到的是「还没进录制」时的采样波形（铺满整宽 714 列），第二次才量到刚开始录的 9 列 —— 两个数字一颠倒，`grew && startsLeft` 必然假红。

修法：采样前先轮询 `#record[aria-pressed="true"]`（它只在 `state === 'recording'` 时为 true）等录制真的开始，再等 1.2s / 2.7s 各采一次。修完实测「录制在 408ms 后真正开始；1.2s=9 列 → 2.7s=19 列」，退出码 0。

★ 教训：**凡是「点一下 → 异步准备好 → 才有现象」的断言，都要先等状态位翻转再采样**，不能掐固定 sleep（`getUserMedia` 的启动时间在不同轮次能差一个数量级）。

**被否掉 / 踩到的**：

- ★ **查表 sin 没有意义**：担心 `Math.sin` 撑不住（钟形泛音 8.5M 次、人声共振 5M 次），实测主 realm 里 8.5M 次只要 **63ms**，换成 4096 点查表反而 **145ms**（更慢）。不做。
- ★ **在 `vm.runInNewContext` 里量性能会差约 20 倍**：`source-stats` 脚本在 vm 沙箱里量到钟形泛音 1543ms、人声共振 1494ms，一度以为点一下会卡 1.5 秒；同样次数的 `Math.sin` 在主 realm 是 63ms。**离线桩适合验结构，不适合量性能** —— 要量耗时就在页面的探针里量（本例 609–722ms/击）。
- **噪声气流整段删掉**（见上）：它的电平标定（乘 3.2 → 1.6）已经没有意义了，留在这里只是记录它曾经到达过峰值 0.786。
- **段尾硬切**：钟形泛音 / 拨弦余韵的衰减到素材末尾还没归零，最后一个粒子会「啪」。新音源统一加 0.3 秒淡出；0 号不加（它的 `sin²` 包络本来就在整秒归零，且必须与首版逐字节相同）。

### 随机音源的图标：为什么第一版「不成套」（同日修正）

第一版用 lucide 的 `shuffle`（5 条路径：两条交叉曲线 + 两个箭头）。用户一眼看出「和其他都不和谐」。原因不在语义，而在**墨水密度**：把每个图标的笔画长度 ×2 估一下覆盖面积 ——

| 图标 | 字形范围 | 墨水/外框 |
| --- | --- | --- |
| 自由流动（∞） | 20 × 8 | ~70% |
| 播放（尖三角 `m8 5 11 7-11 7z`） | 11 × 14 | ~50% |
| **shuffle（第一版）** | 20 × 20 | **~18%** |
| 骰子（现在） | 18 × 18 | ~53% |

∞ 和三角都是「小而密」的粗壮字形，shuffle 却是「铺满整格、线条又细又碎、还带两个箭头」。同一条 `stroke-width="2"` 在三个字形上读出来的重量完全不同 —— **笔画宽度一致 ≠ 视觉重量一致，后者由字形范围与笔画密度共同决定**。

**定下来的做法**：换成 lucide 的 `dice-5`（圆角方框 + 五个点，官方 path 数据原样内联）。它 53% 的密度与三角同档，圆角方框 + 实心点的词汇也跟「录制」的圆角药丸 + 圆点一家。

★ **方法上的教训：成套与否必须截图看，不能凭 path 数据判断。** 这次是写了个脚本把 4 个候选**注入真实顶栏的同一个按钮**（连同左右邻居一起），390 宽、dpr 3 截图放大对比：

- 候选 1 原 shuffle：细碎、不成套
- **候选 2 骰子（五点）：选中** ✅
- 候选 3 骰子（三点）：太散、偏空
- 候选 4 把 shuffle 缩放 0.72 + `stroke-width` 3.2：箭头和曲线糊成一坨，最差

★ **页面上的图标未必来自 HTML**：`#mainPlay` 的图标是 `mobile.js` 在运行时 `innerHTML` 替换的（尖三角 `<path d="m8 5 11 7-11 7z"/>`，且**没有** `stroke-linecap`），`index.html` 里写的那个圆角三角只在 JS 失效时才会露出来。只改 `index.html` 会白改，比对重量也会量错对象。
