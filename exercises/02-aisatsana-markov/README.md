# 02 · aisatsana 式极简钢琴（Markov 乐句重组）

第二份练习：复刻 Generative.fm 的 [piece-aisatsana](https://generative.fm/music/alex-bainter-aisatsana) 的生成机制——**记忆 + 重排**：音符素材固定，乐句顺序由马尔可夫链重组。

版本：[`0.1`](0.1/)（固定乐句 + 段落链）；[`0.2`](0.2/)（增加段落内音高马尔可夫链，节奏和宏观结构不变）；[`0.3`](0.3/)（视觉重做：乐句之间从"切换"变成持续变形）；[`0.4`](0.4/)（当前版本：起点是 0.3 的完整实现副本，音频一字未改，用来承载下一轮需求）。版本目录只保存实现文件，本 README 统一记录整个练习的设计与演进。

> **视觉规则已经抽成本目录里的 [`视觉规则.md`](视觉规则.md)。**
> 那份文档只讲规则（分层、时间基准、节点与连线的状态机、力学、参数表、禁区、验收清单），
> 不依赖本练习的实现细节 —— 想把这套观感用到别处时，直接读它即可；本 README 只记录本练习的演进与实测数据。

## 学习内容

- 谱面数据 → 八分音符网格量化 → 乐句切分（32 步一组）
- **段落化乐句库**：10 个乐句分 4 段（A 安静 → B 主题 → C 发展 → D 结尾），段落感知转移矩阵模拟原版衔接
- 马尔可夫链训练乐句转换概率，`walk()` 沿概率重组顺序
- 提前 1 秒触发 + ±25ms 人性化抖动
- 乐句素材的**律动设计**：节奏不均匀（切分/附点）、力度重音（0.4~0.8）、双音和弦块、音区对比——模仿人写的旋律而不是机械琶音
- **演奏版本系统**：同一乐句可被弹成完整、骨架、回声或迟到回应；留白来自“这次说多少”，不是插入空白段
- **0.2 实时视觉**：每个音高显示为状态节点，素材中学到的转移显示为有向边；静态乐句历史在底层依次排列，力导向网络在其上方游动，实际发声通过 `Tone.Draw` 同步高亮当前节点与刚走过的边；A/B/C/D 四个段落使用不同的当前状态色
- **0.2 背景 texture**：复用 03 的 Moodist 环境素材（包含 Jungle），以独立随机源、低增益和最多两层并发的方式淡入淡出，不改变钢琴的种子路径
- 与 01 的对照：**从零生成 vs 记忆 + 重排**（两种生成范式）

## 运行

运行当前版本请打开 [`0.4/index.html`](0.4/index.html)；历史版本入口是 [`0.3/index.html`](0.3/index.html)、[`0.2/index.html`](0.2/index.html) 与 [`0.1/index.html`](0.1/index.html)。页面通过 CDN 加载 Tone.js、钢琴采样与环境音，因此首次运行需要联网。

**总音量**（0.4 新增，用户 2026-09："总音量有什么控制吗，怎么感觉音量还是偏小"）：以前**没有**总音量 ——
钢琴自己带一个 `Limiter(-1)` 再直连 `Destination`，环境层连限幅都没有，想整体调响只能分别改
钢琴 `volume` 和各层 `targetGain`，而且推过 −1 dB 就会削顶。现在是一条**母带链**：
`钢琴 + 环境层 → masterGain → Limiter(-1) → Destination`，总音量只有一个来源 **`MASTER_VOLUME_DB`**（默认 +6 dB），
而且**限幅在最后一级**，所以往上推不会削顶（峰值被压住、换来更实的响度）。
要"某一部分更响"而不是整体更响，就去改它自己的增益：钢琴 `volume: 12`（Sampler，dB）、
环境层各层的 `targetGain`（**线性** 0–1，`0.1` ≈ −20 dB，本来就是很小的值）。

**钢琴采样**：`vsco2-piano-mf`（VSCO2 免费钢琴库，CC0）经 jsDelivr GitHub 镜像远程加载——首次约 50MB（之后走浏览器缓存），加载失败/超时自动回退 FM 合成钢琴，不会卡死。官方 CDN `samples.alexbainter.com` 对直连返回 403（有访问控制），故不走它。0.2 与 0.3 还会远程加载 Moodist 环境音效，单个音效失败或超时会静默跳过。也可在仓库根目录运行 `python -m http.server 8000` 后访问 `http://localhost:8000/exercises/02-aisatsana-markov/0.3/`。

**触发**（音频一行未改）：`createMoodistTextures` 新增一个**纯通知**回调
`options.onStart(texture, time, duration)`（第三项是这一响的实际时长，视觉要用它排整段声音里的几发）；
视觉侧 `onTextureStart()` 判断 `texture.name === 'birds'` 才排程，
**并且走 `Tone.Draw.schedule(..., time)`** —— 那个回调本身是预排的（lookAhead 会提前跑），
只有 Draw 到达那一刻才是真正听到声音的时刻。

**一段鸟叫里来好几发**（第二轮要求）：开场立刻一发，之后每隔 `fade × 0.9`（钳到 3–6 秒、再叠 ±22% 种子抖动）
续排一发，排到"这一响还能听到的时间窗"（`duration + fade`）里为止，且每发至少有一半扩张落在窗内。
实测：`duration 12s`（窗 17s）→ **4 发**（0 / 5.2 / 9.1 / 13.2 秒）、`duration 25s`（窗 30s）→ **7 发**、`jungle` → 0 发。
后续几发同样排在音频时刻上，停止播放时 `Tone.Draw.cancel(0)` 会把没到的那些一起取消。

**几发会同时在场**（第四轮要求："**允许同时发射几个，而不是明显一个接一个的出现**，这也是为了贴近鸟鸣的随机感"）：
一次"击发"有 `BURST_CLUSTER_CHANCE(0.55)` 的概率**不是 1 发而是一簇 2–4 发** ——
在 `BURST_CLUSTER_SPREAD_S(1.1)` 秒内陆续炸开，各自位置不同（`pan` 当锚点 + `BURST_X_JITTER(0.13)` 横向抖动，
否则几发会叠成一个点），而它们寿命 1–4 秒，所以**必然同时可见**。**开场那一发也能成簇**（击发时刻从 0 开始排）。
一次把整段鸟叫的击发时刻**先算完再排**（簇的成员和它所属那次击发一起确定，不会出现"排到一半被打断"）。
实测：25s 的鸟叫排 **17 发**（旧版 7 发）、分成 **2 次单发 + 5 次成簇**；
跑 12 段统计"同时在场发数"的峰值：**4,4,4,4,4,3,4,4,4,4,4,4（均值 3.9，最大 4）**；
相邻**两发**的间隔（**含簇成员**，所以能低到 0.04 秒）**0.04–4.64 秒、均值 1.69 秒**（旧版是 4.5 秒等距）—— 不再是队列。
★ **击发与击发之间**恒 ≥ `BURST_INTERVAL_MIN_S(2.2)` 秒（第七轮加的下限，200 段鸟叫零违例）——
"0.04 秒"永远只出现在**同一次击发的簇内部**：后者是"同时几发"的来源，前者是"某一刻不会突然炸一片"的保证。

**一发内部也不再"一个接一个地冒出来"**：参考是**一次性全部创建**（`addObjs()` 里 20+50+2+10 个对象同一帧出生，
差异全来自各自的随机寿命），所以这里把各元素起始时刻的抖动收到很小
（圈 `BURST_RING_STAGGER_MAX_S(0.25)`、线 `BURST_ORB_STAGGER_MAX_S(0.12)`、痕 `BURST_SPARKLE_STAGGER_MAX_S(0.18)` 秒；
实测一发里最后一个元素最晚 **0.244s** 启动，旧版是 0.5–0.8s）—— 一发就是"一下炸开"。

**调试入口：按 `s` 手动来一发**（用户先要"增加一个调试……不然还得专门等着"，第六轮又改成
**"测试发射保留吧，但不是鼠标点击，改成 s 键，位置按照已有的算法计算"**）：
birds 每 55–115 秒才来一次，调观感等不起，所以留一个手动入口（`DEBUG_BURST_KEY = 's'`，设成空字符串即关掉）。
三条规矩：① **参数同参** —— 取 `MOODIST_TEXTURES` 里 birds 那一份，所以看到的就是真鸟叫那一发；
② **落点也同参** —— 不给位置参数，走 `spawnBurst` 内部那套安全区算法（原来"鼠标点击处起爆"那套
`getScreenCTM()` 坐标换算**整套删掉了**，不留没人用的分支）；
③ **每按一下换一条按按键序号派生的独立随机流** —— 于是每一下形态都不同，但"第 N 下"永远可复现
（要对比改动就按同样几下），而且**不消耗 `burstRng`**，按与不按都不影响真鸟叫那几发。
它**不是**新的声音映射，"只认 birds"那条没动。
★ 键盘防护与 `f` 全屏共用一套：带 Ctrl/Meta/Alt 放过、焦点在输入框里跳过、`preventDefault` ——
**而且"跳过输入框"必须用 `event.composedPath()`**：种子输入框在 `exercise-controls` 的 shadow root 里，
`window` 上的监听只看 `event.target` 会拿到宿主元素（不是 `INPUT`），于是"在种子框里打 `s` 会被吞掉"。
**顺带发现 `f` 全屏键一直有这个 bug（在种子框里打 `f` 会切全屏），这次一起修掉了。**

**规模与时长的依据**（用户："大小和 birds 的声音关联"）：整体尺度 = 外圈半径的基准按该层
`targetGain / BURST_GAIN_REFERENCE` 在 `BURST_RING_RATIO_MIN..MAX`（短边的 2.3%–7.2%）之间取值，
其余所有量都是它的倍数（**再各自乘一个偏置随机**）；时间尺度 = 该层 `fade × 0.5` 后钳制到 0.9–2.6 秒
（birds `fade 5` → 2.5 秒，各元素寿命是它的 0.3–1.8 倍）；
**落点铺满整块屏幕、只留边缘安全距离**（用户 2026-09 第六轮："目前发射的位置都过于靠中间，
不用限制的这么紧，到屏幕边缘有一定安全距离就行"）：旧版是 `0.5 + pan×0.35 ± 小抖动`，
于是所有落点都挤在 `fx 0.48–0.74 / fy 0.32–0.68` 这条窄带里。
现在**在安全区里均匀抽**：安全区 = 视口四周各留"短边的 `BURST_EDGE_MARGIN(0.12)`"（≈70px）——
这个余量差不多正好是一发自己的伸展（实测墨迹峰值 43–78px），所以最外那道短痕也基本不会被切掉；
`pan` 从"位置本身"降级为**偏置**（`BURST_PAN_BIAS(0.28)`，"声音偏右 → 落点整体偏右一点"这条关系还在，
但不再锁死一个点）。实测 200 发：`fx 0.150–0.923`、`fy 0.127–0.880`，屏幕 3×3 **九块全用到**；
30 发**墨迹零越界**；pan 偏置方向正确（−0.5 → 0.358 / 0 → 0.467 / +0.5 → 0.579，差 242px）。
★ **随机的边界**：随机只负责"在声音定好的范围**之内**怎么分配"，不替代音乐决定的关系 ——
判据与理由写在 `视觉规则.md` **§15**（用户："不要随机的原则保留，允许在明确需要使用随机的时候使用"）；
**允许的三个条件**也在那里：① 有非随机的外框（范围由声音给，随机只在框内分派）；② 种子派生、可复现；
③ 这个量本来就该各不相同。

### 疏密跟 birds 每一段的响度（第七轮）

用户的原始要求：**"能否让发射和 birds 音量关联，音量大的时候相对多，小的时候相对少，先别改，判断一下性能或者其它问题"**，
紧接着又补了最关键的限定：**"判断音量不是判断某一刻，而是一段，不要某一刻音量大就突然发好多"**。

所以这不是"实时跟响度"，而是**段响度**：整条时间表在开场**一次性算完**（`planBurstOffsets()` 是纯函数），
结构上不存在"某一刻响了一下 → 临时插几发"这条通路。四条一起才成立：

| | 规则 | 常量 | 实测（birds.mp3 115.1s / 48kHz） |
| --- | --- | --- | --- |
| ① 量一段 | 素材能量（0.1 秒一格 RMS，只是测量分辨率）先做 2.5 秒滑动平均 | `BURST_ENERGY_WINDOW_S = 2.5` | 相邻格密度最大跳变 **0.153**（刻度 0.5–2） |
| ② 相对、有界 | 参照取素材能量的中位数，每响 9 dB 密度翻倍，再钳到 0.5–2 | `BURST_DENSITY_DB_PER_OCTAVE/MIN/MAX` | 密度 **0.500–2.000**（均 1.036） |
| ③ 间隔硬下限 | 间隔再钳到 2.2–9 秒 | `BURST_INTERVAL_MIN/MAX_S` | **min 2.200s / 中位 3.937s / max 9.000s，违例 0** |
| ④ 同时性只由簇负责 | 响度只调节奏，不碰簇的概率与成员数；归一化保证总发数不变 | `burstDensityNormalise` | 发数 **11.02 发/段**（旧逻辑 11.29）；`normalise 0.892` |

**量的是素材自己，不含我们排的 5 秒淡入淡出**（否则就成了"跟我们的 fade 关联"，而且两端 10 秒会被清空）；
开场那一发另有**保底**（从 0 开始），所以开头不会空。

**这一版唯一一处音频改动**（用户明确同意）：`player.start(time, startOffset)` —— **每次鸟叫从素材的不同位置开始播**。
原来 `player.start(time)` 的 `offset` 缺省取 `loopStart`（= 0，Tone.js 的 `Player.prototype._start` 里就这么写），
而窗口只有 17–30 秒、素材有 115 秒，于是每一段鸟叫听到的都是素材开头那一截、响度曲线逐次相同 ——
那样"密度跟响度"会把每一段的击发节奏也变成同一条（正是用户两次抱怨过的"每一个都一摸一样"）。
起点用**又一条独立流**（`startRng`）抽取，最多取到"素材时长 − 这一段窗口"，所以**永不环绕**；
`textureRng` 那条"哪一层什么时候出现、多久"的序列因此**逐位不变**（改动面被限制在这一处）。
实测起点落在 **0.3–93.6 秒**。

**性能（实测，真实时钟）**：同时在场 0/1/2/4/8/12 发 → DOM 改动 **0 / 67.0 / 144.8 / 274.9 / 536.9 / 804.2 条/帧**、
主线程 **0.000 / 0.113 / 0.180 / 0.303 / 0.662 / 1.132 ms/帧**（每帧强制 style+layout：0.005/0.070/0.130/0.255/0.413/0.607 ms）。
结论：**性能不是这个功能的约束**（12 发也不过约 6% 帧预算），但它同时说明"多发叠加"是有代价的 ——
所以加了 `BURST_MAX_CONCURRENT(10)` 作安全阀（实测最大并发 9，平时不生效）。

★ 另外这次判断过程本身有用：素材包络**离线算一次只要 6.2ms**（115 秒素材、1151 格），
所以选了"离线包络 + 预排"而不是实时读响度（AnalyserNode）—— 后者既会破坏"同一颗种子 → 同一场演出"，
又会**把瞬时峰值变成一簇发射**，正好撞在用户那句"不要某一刻音量大就突然发好多"上。

### 环境层"看得见"：加载重试、HUD 状态行、`b` 键（第八轮）

用户 2026-09 报：**"听了好久都没有鸟叫，也没有相应的触发了"**。查下来的结论是：**排程不是原因**，
而是两个**静默**问题（见下面"判断过程"）。

**判断过程（都不需要听）**：

1. **排程是不是太稀疏？** 把 `createMoodistTextures` 的调度逻辑原样复刻成离散事件模拟（3000 次 × 30 分钟）：
   首次 birds 中位 **1.6 分钟**、之后约 **3 分钟一次**、30 分钟里中位 **7 次**，一次都没出现的比例 **0%**，
   "前 10 分钟没有 birds"只占 **4.4%**。被挡下的原因：层数已满 26.6% / 别的 event 层在响 7.2% / 概率没过 33.0%。
   → **"听了好久都没有"不可能由排程解释**，一定是别的东西坏了。
2. **素材能不能加载？** 无头探针直接调 `createMoodistTextures`：**6/6 全部加载成功，2.5–2.7 秒**，无 warning。
3. **birds 能不能播、涟漪会不会来？** 端到端跑**和用户按播放完全一样**的路径
   （`window.exercise.activate(seed)` → `engine.schedule()` → `Tone.Transport.start()`，
   Chrome 加 `--autoplay-policy=no-user-gesture-required` 让上下文真的 running）：
   activate **4.3 秒**完成（钢琴采样 + 6 层环境音），birds 真的开始发声，涟漪元素 20–53 个、最多 4 发同时在场，
   `player.start(time, offset)` **没有抛异常**。→ **产品链路是通的**。

**于是真正的毛病是两个"静默"**（都已修）：

| 毛病 | 以前 | 现在 |
| --- | --- | --- |
| 某一层加载失败/超时 | 12 秒超时、**不重试**、只往控制台打一行 warning → 那一层**整场缺席**，画面上看不出来 | 超时 25 秒；失败自动重试（最多 3 次，退避 2s/5s，每次换全新节点）；就绪/最终失败写进 **HUD 里那行状态**（`环境层 6/6` / `环境层 5/6（失败：birds）`） |
| 不知道鸟叫来没来 | 只有控制台有 `[Moodist] texture in: birds` 一行 | **HUD 里那行小字**实时显示：`环境层 6/6 · 正在响 birds 9s · 上次 birds 1 秒前`；另外按 **`b`** 可以**立刻**让 birds 走一遍真实路径（音频 + 涟漪） |

★ **为什么放在 HUD：**用户 2026-09 看到第一版后说：**"环境层的信息不要出现在页面的文本中，可以放在 hud 中"。**
画面上那个日志只放**作品内容**（马尔可夫链的行走）；加载结果与"现在有没有在响"是**系统状态**，
放在 `.controls-hud` 里的 `.ambient` 行（跟 HUD 一起隐藏，也不占画面）。实测：画面日志里**一行环境层都没有**。
★ `b` 键与 `s` 键的分工：`s` 只放视觉那一发，`b` 连音频一起走完 —— 一键区分
**"排程还没轮到"** 和 **"播了但听不见"**。它走的是 `createMoodistTextures` 里**唯一**的播放实现
（`startTextureEvent()`），所以增益包络、`start(time, offset)`、`onStart` 通知与真鸟叫完全同参；
它用按按键序号派生的独立流抽时长与起点，所以**不消耗演出那两条流**（按与不按，之后真鸟叫的序列逐位相同）。
实测：按一下 → 涟漪 +1、HUD 那行变成 `… · 正在响 birds 7s · 上次 birds 0 秒前`、控制台 `[debug] 按 b 手动发声 #1`。

**还有一个只能靠耳朵确认的怀疑**（尚未定论）：环境层是**线性增益**作用在录好的素材上
（birds `targetGain 0.2` ≈ −14 dB），而素材自己的中位 RMS 是 **−28 dBFS**（115 秒 / 48kHz 实测）
→ 母带前约 **−42 dBFS**、加 `MASTER_VOLUME_DB(+6)` 后约 **−36 dBFS**；钢琴是采样器 +12 dB 的音量。
两者大概差 **10–25 dB**，所以"鸟叫在响但你听不出来是鸟叫"完全可能 —— 按 `b` 听一遍就能定论。

### 行内音符：字距 = 时间差（第九轮真正的需求）

用户在"日志行距"那版之后澄清：**"这并不是需求，先留着吧，真正的需求指的是音符间的距离，而不是乐句的行距"**。
也就是：一句一行的结构保留，但**行内的音名要按时间铺开** —— 现在相邻音名的字距 ∝ 这两个音的时间差，
一整行读起来像一小段"文字钢琴卷"（密的挤、疏的拉开）。

- 等宽字体下**用空格实现**（保住"日志是纯文本"这个性质），分辨率 = 一个字符宽（13px 下 **7.147px**）；
- 尺度 `LOG_NOTE_CHARS_PER_SECOND`：**当前 4**（曾经 10）。★ 这个值决定"多大的间隔才看得出差别"：音名每推进一个要占 `2 字符 + 最小 1 空格 = 3 字符`，所以当 `每秒字符数 × 步长 < 3` 时，密集处的字符推进会**追上并超过**时间轴，间距就全落到最小值。实测（相邻两音）：**4 → 0.3/0.6 秒都是 1 个空格（分不出来）**、0.9 秒 2 个、1.2 秒 3 个、1.8 秒起触顶（5 个）；**6 → 0.6 秒才分得出**；**10 → 0.3 秒正好一个空格（原始密度）**。
  所以**默认密度和改动前逐字符一致**，只有更疏的地方才拉开（0.6s → 4 空格）；
- 同拍和弦至少留 1 个空格；一行超出可用宽度（窄屏）时整体压缩，相对疏密不变。

**实测**（静音探针）：字宽 7.147px、1200px 视口可用 **151 字符**（一句最多约 115 字符，桌面端不压缩）；
真实运行末行 `9/15 ← E4              C4      G3          B4    C5 …`，
音名起始位置 `[7,22,31,43,49,70,79,91,97]`、相邻间距 `[15,9,12,6,21,9,12,6]` ——
**全是 3 的倍数**，正落在 0.3 秒步长网格上。

（上一节的"日志**行距** = 演奏间隔"用户说不是需求、但**先留着**：它管行与行，本节管一行之内。）

### 日志：行距等距、行内音符按时间铺开（第九轮）

两种"间隔"要分清 —— 用户先提"文本间的间隔就是演奏的间隔"，实现后澄清 **"这并不是需求"**，
并明确 **"去掉乐句间不同的行距，恢复到之前"**；真正的需求是**音符间的距离**：

| | 现状 | 说明 |
| --- | --- | --- |
| **行与行**（乐句之间） | **等距（一个行高）** | 试过"行距 ∝ 两次演奏的时间差"，按要求**已撤销**（实现与实测数字留在 `视觉规则.md` §16 当历史） |
| **一行之内**（音符之间） | **字距 ∝ 音与音的时间差** | 等宽字体下用空格实现，间隔夹在 **[1, 5] 个空格**（音名间距 3–7 字符），一行读起来像一小段"文字钢琴卷" |

**尺度与边界**：`LOG_NOTE_CHARS_PER_SECOND` 现在是 **4**（曾经 10，那次是"默认密度与改动前逐字符一致"）；用户手调成 4 之后整行明显变紧（实测 19 音的句子最长只有 **56 字符**，移动端 65 字符可用宽度轻松放下）。
所以默认密度与改动前逐字符一致）；上限 `LOG_NOTE_MAX_GAP = 5` 是后来加的 —— 用户反馈
**"音符间的间隔要限制一下间隔的范围，现在有点太多了，移动端甚至出现了一行乐句断行"**。
另外一整行如果超过可用宽度，会二分找"刚好放得下"的每秒字符数（相对疏密不变，只是整体变紧）。

**实测**（静音探针）：桌面 1200px → 字宽 7.147px、可用 151 字符、音名间距全在 `[3,7]`；
390px 移动端 → 字号自动 10px、字宽 5.498px、可用 65 字符、**无断行**（行盒 `17.8/17.8/17.8` 恒为单行、溢出 0）；
合成最坏情况（19 音 × 跨 9 秒）长度：桌面 92、65 字符宽 59、48 字符宽 56（= 理论最短，320px 级屏幕遇到最密句仍会断行，属已知边界）。

**尺寸一律以"短边"为单位**（`unit = min(视口宽, 视口高)`，逐帧现算，参数存的是比例）——
参考整篇都建立在 `minSide` 上，而且这样换视口/全屏时整发按同一比例缩放，
不会出现"圈跟着变了、线没跟着变"。★ "太大了"提了三轮，每轮只动这一个基准（比例全不变）：
147 设计单位（21%）→ 49（7%）→ 36（5%）→ **约 28px（4%）**。

**实测**（无头探针，手动驱帧）：

  12 段鸟叫的"同时在场发数"峰值 **4,4,4,4,4,3,4,4,4,4,4,4**（均值 3.9）；相邻间隔 **0.04–4.64s、均值 1.69s**；

  落点 **fx 0.150–0.923 / fy 0.127–0.880**（安全区里均匀抽，边缘留 12% 短边）→ 同时几发不叠在一个点上，
  而且 3×3 九块都用得到；
  一发内部最后一个元素最晚 **0.244s** 启动（旧版 0.5–0.8s，所以过去看起来是"一个个冒出来"）；
- **每发都不一样**（跑 40 发统计）：圈数 **0 圈 13 发 / 1 圈 18 发 / 2 圈 9 发**（"不一定永远有"成立）；
  圈的半径 **25.6–48.8px**、**圆心离爆点 0.1–18.4px**（不再同心）、起始时刻 0.06–0.69s、寿命 1.14–3.70s；
  **同一发里两圈的半径比** `0.72 / 0.99 / 1.00 / 1.24`（旧版恒为 1.62）；
- **有大有小、有快有慢**（450 根线统计）：寿命 **0.88–4.29 秒**（旧版全部落在 1.25–3.0 秒）、
  一生走 **9.1–92.0px**、游走速度 **2.55–92.90 px/s（36× 差）**、自转半径 5.5–25.4px、自转角速度 231–1485°/s；

  1.5s:29px/10个 → 2s:40px/5个 → 2.5s:17px/1个 → 3.8s:0px/0个`；
- 出现/消失都走几何：`t=1ms` 时外圈 `r=0.07`、线的 `points` 还是空的 → 是"从 0 长出来"，不是淡入；
  走完（本发最长 3.9s）后 `bursts=0`、层内 0 个子元素；

  连按 6 下（序号 0–5）落点 `0.923,0.168 / 0.324,0.148 / 0.183,0.692 / 0.374,0.285 / 0.525,0.222 / 0.923,0.682` → **互不相同 6/6**；

  打 `f` → `defaultPrevented=false`（**这条以前是坏的**，原因见上面的 composedPath 说明）；

- **调试按键不消耗随机流**：同一颗种子下，"中间按两次"与"一次都不按"，之后两发真鸟叫的整发签名**逐位相同**；
  ⚠️ 调试发走的是 `MOODIST_TEXTURES` 里的**原始** birds 配置（**没有** `energy`），
  所以 `burstDensityAt` 在那里恒返回 1 —— 这条**兜底路径**就是靠调试验证过的（缺数据时退回固定节奏，不崩不乱）；

  —— 涟漪不参与节点/连线的力学，"同一段音乐同一张图"没被破坏；

- 停止播放时 `clearBursts()` 清空（不留残影），还没到点的后续几发由 `Tone.Draw.cancel(0)` 一起取消。

⚠️ **还没人工确认的一件事**：真实的"鸟叫起来 → 涟漪同时出现"只能靠听（无头环境跑不了音频），
接线本身是代码检查确认的（`createMoodistTextures` 里 `options.onStart` 存在且走 `Tone.Draw`、
`activateEngine` 传了 `onStart: onTextureStart` 与 `startRng`、`createMoodistTextures` 在加载时算好 `energy` 并随 `onStart` 一起报给视觉侧）；

## 0.3 视觉：乐句之间是“变成”，不是“切换”（只动视觉，音频未改）

0.2 给人的直接感受是“每一句的过渡很生硬”。原因在 `renderPhraseVisual()`：每个乐句开头都执行 `markovMapEl.replaceChildren()` 重建整张 SVG。

- 节点与边被删除再创建，CSS 过渡失去起始状态可补间 → 当前状态与活动边只能硬切；
- 节点环形坐标由视口与音高索引决定（确定性），重建等于抹掉力导向漂移 → 图每 9.6 秒（32 步 × 0.3s）弹回初始位置；
- `previousVisualNote = null` → 跨乐句的转移永不显示；`graphMotion.energy = 1` → 布局每句被重置；
- 重建时刻正是首音前 0.01 秒，所以“跳”永远砸在乐句重拍上。

0.3 把图改成**一个持续存在的对象**，乐句更替不再是一件事，而是一次重组：

- 节点 = 四个段落用过的音高并集（14 个），建一次、永不重建；环上的基准位置由视口与音高索引决定，每次换句再叠加一点相位 / 半径微扰（见下），**所以换句时所有点都会移动**；
- 边 = 所有段落出现过的转移（48 条），同样预建，DOM 之后不再增删；
- **连线的生长只由“有新点冒出来”触发**（用户明确要求的规则）：一端刚变成乐句点的转移，**朝那个新点生长过去** —— 新点在起点端时从终点端长过来（`stroke-dashoffset` 取负值反向揭示），新点在终点端时从起点端长出去；**两端本来就是乐句点的连线不做生长动画**，直接画满、只是跟着点移动；A、C 都有的连线完全不动（`setEdgePresence` 幂等）。收回：**反向生长**（不是消失、也不是透明度递减 —— 用户明确要求），揭示区间沿与生长相反的方向退回，**全程保持满透明度**，只有几何在缩。
- **生长/收回的时长与音符间隔挂钩，而且重组发生在首音那一刻**（先是用户指出固定时长会“一条还没长完、另一条已经开始”，后又指出旧的窗口让变换跑在无音的空白里、观感很干）：重组从**本句首音前 `MORPH_LEAD_S = 0.05` 秒**开始，时长基准是**本句内部第一个音程**（首音 → 第二个音，`clamp(M, MORPH_MIN_S = 0.32, MORPH_MAX_S = 1.6)`）；每条线再用**它自己那个点**的速度倍率细分。实测时长基准 0.3 / 0.6 / 0.9 / 2.4 秒 → `0.32 / 0.60 / 0.90 / 1.60` 秒，对应飞行 **600–798ms / 1004–1496ms / 2200ms**；而旧版（基准取"上一句尾音 → 本句首音"的空白、常驻上限 1.6 秒）飞行 2.2 秒中**约 73% 没有新音**。`EDGE_GROW_S = 0.7` / `EDGE_RETRACT_S = 0.6` 退化成“拿不到间隔时的兜底值”；**箭头只在画满之后才挂上**，否则线还没长到新点箭头就先出现了；画满后移除 dash（节点一直在呼吸漂移，留着就得每帧重算路径长度）；
- **不属于当前段落的音高收进下层（藏身层），精确贴在一个在场的宿主节点背后**（偏移 3px、半径收到 9px、**透明度压到 0**、音名隐藏）——宿主半径 17px，所以它是被真正挡住的；谁当宿主按“离自己环位最近的在场节点”分配；
- **变成本段落的音高时，它从宿主背后一次弹出**：搬到在场层（压在所有藏身点之上），沿 **easeOutBack**（`WAKE_BACK = 2.0`）落位 —— 起步速度约为平均的 5.7 倍（很猛），临到落点前**单次过冲约 13%** 再收回，收回之后不再有任何来回。
- **连线的明度 = 该转移在马尔可夫链里的概率**（用户提出：连线本来就是概率算出来的，能不能用灰度表达）：`walkNote` 是从当前音的后继数组里等概率挑一个（重复项就是权重），所以 **from→to 的概率 = 该转移出现次数 ÷ 该音后继总数**，明度按 `EDGE_OPACITY_MIN = 0.16 ~ EDGE_OPACITY_MAX = 0.72` **线性**映射。素材里既有大量 `p = 1` 的确定转移、也有 `p ≈ 0.07` 的偶然转移，所以线性映射能把灰度铺开（实测 A 段 0.272–0.72、跨度 0.448；C 段 0.20–0.72、跨度 0.52；若改用开方，低概率被抬到 0.39 附近，对比反而更弱）。**这两个常量里已经折算掉旧版写在 CSS 里的 `stroke-opacity: .8`**（旧元素值 0.2/0.9 × 0.8 = 屏幕上本来就是 0.16/0.72），所以线的观感和以前一模一样，但箭头的明度现在跟着线走（见下“线与箭头同明度”）。旧实现只有"出现次数 > 2"的两档提示，现已由概率灰度取代；
- **每句的点分布不同，但依据只能是这一句的音乐（2026-09，用户："不想让每一句的音符点分布在视觉上完全固定，每次要不一样，但整体逻辑还是要有的 —— 不要随机，完全的随机毫无意义"）**：旧做法是每次换句取一个 ±0.1 弧度 / 0.95–1.05 倍的**随机**微扰 —— 可复现但没有依据，而且幅度小到每句几乎一样，已删除。现在两条规则：**A 朝向 = 本句首音的槽位转到正上方**（但每句最多转半个槽位 `RING_ORIENT_STEP`）；**B 半径 = 本句该音发声次数的归一化值**（`RING_ACTIVITY_PULL = 0.22`，弹得最多的音比外圈靠内 22%），本段落在场但这句没弹到的音留在最外圈 —— 于是每句的点分布是一张不同的"密度云"：内圈是这句的骨干、外圈是没用上的可能。★ A 必须限速：实测本素材乐句首音是 A: C3/C3、B: C4/C5/C4、C: C3/C4/E4、D: C5/E4（槽位 1/5/7/11），C4↔C5 差 6 个槽位，一次摆过去最远那颗点要跑约 **720px**；限速后每句位移 **≤ 90.8px（实测最大 87.1–90.8、平均 67px）**，而首音在几句之内逐渐转到正上方（实测第 4 句 C3 正好落在 270° = 正上方）。★ 两条都是确定性的：**同一形状重算两次，所有环位偏差 0.000px**（视觉侧因此彻底不再需要随机流，`visualRng` 已删除）；★ 环位槽点自身只留 ±4% 的固定抖动（`RING_SLOT_JITTER`），不能再放大 —— 过去的 ±12% 会盖过"活跃度"这个真正的信号；
- **飞行有三类，按“点的角色变化”选缓动**：刚变成乐句点用 `mode: 'pop'` + `easeOutBack`（起步猛、单次过冲 13%，是“弹出来”）；本来就是乐句点用 `mode: 'glide'` + `easeInOutCubic`（平滑滑到新环位、不过冲，它们只是换位置而不是飞过来）；变回收起点用 `mode: 'retreat'` + `easeOutCubic`（滑到宿主背后，见下）。三者共用同一套按音高固定的速度倍率与时长公式；
- **飞行时长 = 音符间隔 × `WAKE_FLIGHT_SCALE = 2.0` × 该音高自己的速度倍率**，钳到 `WAKE_FLIGHT_MIN_S = 0.6` ~ `WAKE_FLIGHT_MAX_S = 2.2` 秒（用户两次反馈“太快”，从 0.32 固定 → 1.5 倍 → 现在 2.0 倍）；
- **视觉侧不再使用随机数**：环的朝向与半径都由本句的音乐算出（首音 + 发声次数），所以"同一段音乐必然画出同一张图"；也因此不需要再维护一条视觉随机流（原来的 `visualRng` 已删除）。⚠️ 若将来又要给视觉加随机，仍必须像 texture 那样**从种子派生一条独立流**，绝不能消耗钢琴的 rng（0.2 踩过这个坑）；
- **视口与响应式（2026-09 调整，用户反馈"窄屏下很好，宽屏下四周的空白太大"）**：原因是环的半径写了两条**绝对上限**（`min(380, W*0.36)` / `min(330, H*0.32)`），窗口一大就再也不长 —— 实测 2560×1440 的窗口里只有 **760×660** 一圈（横向 30%、纵向 46%）。改法不是把常量逐个乘系数（那会变成"环变大了、点和字还是 17px/12px"），而是把内部坐标定义成**设计单位**：`viewBox` = 窗口尺寸 ÷ `scale`，由浏览器把整张 SVG 等比放大，于是环、节点、音名、连线粗细、箭头尺寸、弹的幅度**全按同一比例**缩放。`scale = clamp(sqrt(窗口面积 ÷ 1100×700), 1, 2.5)`——**下限 1** 保证参考尺寸以内的窗口渲染结果与改造前逐像素一致（窄屏观感不变）。环半径改为纯比例 `0.36W / 0.32H`，实测各视口横向填充都是 **0.68**、纵向 **0.63**、节点屏幕半径 = `17 × scale`、间距/半径稳定在 **10.3–14.6**（1440×900 → scale 1.30 / 节点 22.1px；1920×1080 → 1.64 / 27.9px；2560×1440 → 2.19 / 37.2px；3440×1440 → 封顶 2.50 / 42.5px）。HUD 是 HTML 覆盖层、故意不缩放，保证文字始终可读；
- **`f` 键全屏 / 退出全屏**（2026-09 增加）：键盘事件算"用户手势"，所以不需要额外按钮；全屏的是整个文档（HUD 与控制还在），想只看画面再点一下画面隐藏界面 —— 两件事故意不合并。焦点在种子输入框里时不处理（否则打不出 f）；`requestFullscreen()` 的 Promise 会 `catch` 掉，避免控制台出现未捕获错误；`fullscreenchange` 后调用 `updateGraphViewBox(true)` 重算视口（浏览器不一定会派发 `resize`）；
- **退场的连线是"反向生长"，彩色层跟着线一起退（2026-09 修复）**：用户发现换句时"激活的连接线直接通过透明度消失"。查下来是两个原因叠加：① `applyPhraseVisual` 发现某条转移不再属于本段落时顺手把它的概率明度写成 0，而 `updateEdgePresence` 又把明度每帧写进 `opacity` —— **整段收回过程是看不见的**（实测收回途中 `presence` 0.653、`opacity` 已经是 **0**）；② 彩色行进层保持满长、`opacity` 1，直到下一条转移开始才用 1.2 秒退色，于是画面上只剩"停在原处、慢慢变淡"的彩线。现在：明度只在"它属于本段落"时更新（退场保留上一次的明度，`presence` 到 0 才压到 0），彩色层的可见区间裁成 **扫过区间 ∩ 灰线可见区间**，收回时跟着灰线逐帧反向生长、**全程满透明度**、收完即结束高亮（实测两者 `dashoffset` 逐帧相同：`89.81487141927084` vs `…83`，`opacity` 全程 1，箭头在收回途中为 `null`）。
- **高亮的"退场"也是反向生长，不是退色**（用户 2026-09 的规则："所有连接线的出现/消失都要生长/反生长的动态，而不是透明度控制"）：一条**留在本段落**的转移被下一条取代时，彩色层沿原路**退回去** —— 揭示区间从全长缩回 0（终点端先消失、起点端最后消失），时长与它走过来时相同（= 该音的 I，即 `pulse.duration`），**全程满透明度**，退场一开始就摘掉箭头。实测区间 `256 → 231.8 → 204.1 → 176.4 → 148.8 → 121.1 → 93.4 → 65.7 → 38 → 10.4`（0.576 秒内线性缩回 0，速率 ≈ L ÷ I）。旧的 1.2 秒 `opacity` 退色（常量 `EDGE_SWEEP_FADE_S`）已删除 —— 至此**连线的出现/消失（底边与高亮）全部由几何表达，没有一处用透明度**；`opacity` 只承担"概率明度"这个静态量；
- **箭头跟着"正在移动的头部"走（2026-09）**：用户指出"箭头一直在目的地等着曲线过来"，要求生长/反向生长时箭头跟随曲线头部，并且方向要按曲线算、不能固定或固定成结尾朝向。做法：每条边多一条 `.chain-head` 路径（描边不可见、`stroke-opacity: 0`，只承载 marker —— marker 的 fill 是 `context-stroke`，实测不受 `stroke-opacity` 影响，所以描边不显示、箭头照常显示），每帧把它的 `d` 重算成"头部前 12 个用户单位的一小段曲线"，于是 `orient="auto"` 给出的就是**该点切线**。**箭头底边取在头部那一点**（参考点是底边中点，所以折线末端就放在头部）—— 这一点很关键：线头（含 2.4 宽描边的圆头）全落在箭头较宽的身体里，不会露出来，而且颜色到位时这支箭头与"停在终点的那支"逐点重合。方向：行进时沿曲线正向（θ = 0），反向生长时**掉头指回起点端**（θ = π）—— 用户明确肯定过这个转向（"回退箭头转向回退的方向是对的"），但要求**慢慢转过去、不能一瞬间翻**。做法是显式算出方向 `u = 切线·cosθ + 法线·sinθ`（切线/法线取头部处局部值），θ 逐帧从 0 爬到 π：实测 8ms 一帧 `4 → 8 → … → 176 → 180`、**0.36 秒转完**（= 高亮时长 0.6s × `HEAD_ARROW_TURN_RATIO = 0.6`，钳制 0.22–0.5s），转向期间**底边中点始终钉在头部**，所以线的端点一直在箭头身体里（横向宽度实测：头部 8.5 → +1 时 7.5 → +2 时 6.5 → +4 时 4.5 → +8 时 0.5）。彩色层同时用**平头描边**（`stroke-linecap: butt`）：圆头会比算出来的端点再多伸 1.2，反向生长时那截会露在箭头外面。同时**一条边只显示一支箭头**：颜色还在走时终点那支不挂（否则就是"在目的地等着"），颜色到位后骑行箭头收起、改由停在终点的那支（明度与线一致），反向生长退完再把底边箭头挂回来。实测：行进 `dotWithTangent = +1`、反向生长 `−1`；箭头底边到彩色头部 0.00–0.01、尖端到头部 8.8（正好一个箭头长度）；两种运动期间 `path.marker-end` 与 `pulsePath.marker-end` 都是 `null`。★ 两个坑：①取样顺序必须"从后往前排到头部"，写反会让箭头掉头 180°（实测 −1）；②**不要把尖端放在头部上** —— 那会让线头露出、并在交接时"往前弹一下"（用户报的两个现象都出自这里：细步实测"箭头底边到静止位置的距离" 应当线性单调减到 0，`12.11 → 10.39 → 8.66 → 6.94 → 5.22 → 3.49 → 1.77 → 到位`，每帧恒 1.72）；
- **变回收起点时是“滑到宿主背后被挡住”，不是原地消失**（用户报的 bug：下一次音符变少时，有点突然不见了）：收起也是一个飞行（`mode: 'retreat'`），动效用 `easeOutCubic`（立刻起步、稳稳落进宿主背后），不透明度用 `1 − easeInCubic(t)` —— **前段几乎全亮**（所以看得出它在移动），**末段迅速淡掉**，而末段正好是它钻进宿主背后的时刻，于是观感是“被挡住了”。结束时它停在离宿主 3px 处、半径缩到 9px（宿主半径 17px），完全被遮挡；连线的反向生长用同一个时长，所以线是和它一起退进去的；
- **换句的弹是“通过连线传开的”，不是整体外扩**（用户明确否定过整体径向外扩的版本）：换句那一刻给在场节点一次**切向**冲量（方向按索引交替），位移再**沿连线传给邻居** —— 连线在这里是弹簧（“铰链”，`EDGE_COUPLING = 0.012`），静止长度取环上的原始距离，所以环的平衡位置不变、只是把运动传出去。阻尼 `NODE_DAMPING = 0.92`（阻尼太大扰动传不出去）；
- **行程（振幅）的调整记录**：用户反馈“速度够、范围不够，像是很短的弹簧，把弹簧放长一点”。离散模拟给出的结论是：本系统阻尼很重（0.92/帧），**单把弹簧变软只值 1.25× 行程**；放松阻尼虽然能加行程，却会把方向反转从 3 次推到 9 次、变成乱抖。所以采用“软一档 + 适度加冲量”：`NODE_HOME_SPRING` 0.012→**0.009**、`EDGE_COUPLING` 0.016→**0.012**，并把推挤 / 漂移按同比例降到 **900 / 0.038**（静态偏移 = 力/弹簧，必须一起调，否则环会变松），换句冲量 6→**8.5**。合计行程 **≈1.6×**，起步速度只涨约 40%；
- **弹的力度分两级**（用户明确要求，之前两级太接近以至于听着只有一种）：
  - **换句级**：`PHRASE_KICK = 8.5`（实测单点峰值 **27.3px**，84ms 到峰）、段落切换 `SECTION_KICK = 12.5`（**40.1px**）—— 整句的重音；
  - **音符级**：`NOTE_KICK = 1.7`，每个音发声只轻轻推一下（实测 **5.9px**）—— 两级之比 **4.6 : 1**，听得出来“换句”才是重音；
- **转移的激活是“行进”，不是整条变色**：彩色覆盖层与灰边同曲线，`stroke-dasharray` = 全长、`stroke-dashoffset` 从全长推到 0，于是颜色从**起点一路长到终点**，走完保持彩色，等下一条转移开始时再退色 1.2 秒。颜色到达终点的那一刻做两件事：给底边加 `.active`（**只换 `stroke` 颜色、绝不改 `stroke-width`** —— 箭头是 `markerUnits="strokeWidth"`，描边一变粗箭头就会跟着放大），**并且给行进层挂上第二支几何完全相同的箭头**（`userSpaceOnUse` 版本，尺寸不随 2.4 的粗描边变化）—— 因为线本来就是“底边 + 行进层”两层叠出来的，箭头只挂一层就会出现“线是实心的、箭头还半透明”（用户 2026-09 报的问题），两层都挂之后箭头与线的明度逐帧相同（颜色用 0.12 秒快速切换，让箭头“到点亮起”；退色时随底边一起回到 1.2 秒的灰）；
- **一个音程驱动三件事**（用户要求：音点的“亮 → 暗”不能每个音都一样）：上一个音到这个音的实际音程 `clamp(间隔, EDGE_SWEEP_MIN_S = 0.16, EDGE_SWEEP_MAX_S = 1.5)` 同时决定 ——
  1. **彩色行进**走多久（到点箭头亮起）；
  2. 该音点**从亮到暗**用多久（`flashDuration`，线性退回常态色）；
  3. 于是两者天然同步：音密处一闪即暗、留白处余韵长，而不会出现“行进还在走、点已经暗了”。
  时长由 `showVisualNote(phraseId, note, audioTime)` 传入的发声时刻与 `previousVisualTime` 相减得到；第一个音没有“上一个音”可参照，用 `FIRST_NOTE_INTERVAL_S = 0.5` 兜底（行进与点亮都用它，避免开场第一个音闪成 0.16 秒）；

**位置不用 CSS 过渡，也不用欠阻尼弹簧**：节点要在“藏身层 / 在场层”之间搬动，而 DOM 搬动会重启动 CSS 过渡，所以半径、透明度、颜色、音名可见性全部由 `paintNode()` 逐帧写入。

- **弹出/收起用一次性“飞行”**：`easeOutBack`（`WAKE_BACK = 2.0`，单次过冲约 13%），时长由音符间隔决定（见上）。欠阻尼弹簧（k=0.012 / 阻尼 0.94）会在到达后继续过冲并来回弹几下；而纯缓出（`easeOutQuart`）又完全不弹、看起来像平移 —— 用户把这两个极端都否掉了，**单次小过冲**才是要的手感；
- **静止时的呼吸仍用弹簧**（`NODE_HOME_SPRING = 0.009` / 阻尼 0.92；阻尼不能太大，否则扰动传不出去）；
- **连线既是视觉也是“铰链”**：作为弹簧参与动力学（`EDGE_COUPLING = 0.012`，静止长度 = 环上的原始距离，所以平衡位置仍是那个环），但**不作布局依据** —— 早期版本给边设了 170–280px 的绝对“理想长度”，结果把环整个撑开、平衡点偏移 30px 以上。区别就是静止长度取“环上的距离”还是“一个常数”；

**踩过的坑之二**：行进层一开始在 CSS 里写了 `opacity: 0`，而 JS 又用 `setAttribute('opacity', 1)` 去点亮它 —— SVG 呈现属性会被任何 CSS 规则覆盖，于是**属性写着 1、画面完全不显示**，用户看到的就是“彻底没有彩色连线”。现在：CSS 里不再声明透明度，全部由 JS 写**内联样式**（`style.opacity`），内联样式不会被样式表覆盖。教训是验证方式也得跟着改：只读 `getAttribute('opacity')` 会误判为通过，必须读 `getComputedStyle(...).opacity`。

**踩过的坑之三**：转移边一开始还参与布局（把两端拉到 170–280px 的理想长度），但环的间距只有约 130px，于是边一直在把环撑开，弹簧平衡点被推偏 30px 以上，节点弹出后会在 72%~117% 之间来回摆、停不下来。现在的结论是：**边只做视觉，不参与布局**；布局完全由环位弹簧决定。

  - **参考点取箭头底边中点（`refX = 0`，2026-09 调整）**：marker 的 `refX/refY` 就是“路径末端落在箭头坐标系里的哪个位置”，把它放在**底边中点**，线尾就正好停在箭头最宽的那条底边上 —— 既不可能再从收窄的锥面里露出来（用户报过“连接线超出了箭头”：旧版 `refX = 7` 时实测线尾处箭头宽度只有 **1.10**，恰等于线宽 1.1），也不需要上一版那套“线尾回缩 `ARROW_TAIL_INSET = 3.2` + 同步缩小 `refX` 补偿”。箭头位置与旧版实测一致：底边 **28.7px**、尖端 **≈20px**（都指离目标节点圆心的距离），线的起点端仍是 `R + 2 = 19px`。标定实测：`refX = 0` 时线上的点、线尾附近的点、箭头身体内部的点**同为 0.502**（单层、无叠加），三种声明方式（`userSpaceOnUse` / `strokeWidth` 单位 / 换描边宽度）结果完全一致。
  - ⚠️ **量箭头像素前先查旁边有没有别的连线**：48 条边都汇到少数几个节点，实测 `C4|G3`（明度也是 0.72）从采样点旁 **2.9px** 穿过，像素被叠乘成 `1−(1−0.72)² = 0.92` 而不是 0.72 —— 差点被误判成“箭头比线更实”。现在探针会把每条在场连线到采样点的最小距离一起打出来（对每条边采样 160 个点）。
  - **可见性一律用计算样式核对**（属性不算数）：行进中 `getComputedStyle(行进层).opacity = 1`（内联样式），在场节点 `0.995`、收起节点 `0.000`/音名 `0.000`；下一条开始后行进层计算样式回到 `0`。这一项正是补上“属性写了 1 但画面不显示”那个坑之后加的断言。
  - 切换段落后节点 DOM 未重建（`dataset` 标记仍在），三层子元素数守恒（藏身层 10 + 在场层 18 = 14 圆 + 14 音名）；发声染色走 `flash` 并在 30 帧后衰减到 0.64；`window.exercise.activate` 仍存在。
- **我这边看不到画面也听不到声音**，以下是现在真正可调的旋钮（都写在 `0.3/index.html` 顶部与视觉一节）：
  - 飞行快慢：`WAKE_FLIGHT_SCALE = 2.0`（相对音符间隔的倍数）、`WAKE_FLIGHT_MIN_S = 0.6`、`WAKE_FLIGHT_MAX_S = 2.2`；
  - 点与点的速度差：`WAKE_SPEED_MIN = 0.8` / `WAKE_SPEED_MAX = 1.25`（按音高用黄金比小数固定）；
  - 弹出的过冲：`WAKE_BACK = 2.0`（≈13%；想更含蓄 1.6 ≈ 9%）；
  - 连线的生长/收回：跟着 `morphSeconds`（= `clamp(间隔, MORPH_MIN_S = 0.32, MORPH_MAX_S = 1.6)`）与各自点的速度倍率；`EDGE_GROW_S = 0.7` / `EDGE_RETRACT_S = 0.6` 只是兜底；
  - 连线灰度：`EDGE_OPACITY_MIN = 0.16` / `EDGE_OPACITY_MAX = 0.72`（元素 `opacity`，也是箭头跟着走的那个值）；
  - 每句的朝向与形状：`RING_ORIENT_STEP = 2π/14 × 0.5`（每句最多转半个槽位，朝"首音在上方"）、`RING_ACTIVITY_PULL = 0.22`（活跃度对半径的拉伸）、`RING_SLOT_JITTER = 0.04`（槽点固定抖动）；
  - 换句的两级力度：`PHRASE_KICK = 8.5` / `SECTION_KICK = 12.5` / `NOTE_KICK = 1.7`；
  - 收起的透明度：`HIDDEN_NODE_OPACITY = 0`（想留一点暗示就调 0.05，但宿主遮挡会因此失效）；
  - 主题配色：**画面那部分**（`--stage-bg` / `--graph-edge` / `--graph-node-base` / 段落色 / 音名两个候选字色）全部集中在 `index.html` 里带 `★★` 的 `PALETTE` 块（两套主题各一份），由 `applyTheme()` 推成 `<html>` 的内联 CSS 变量；**HUD 那部分**（`--bg / --panel / --fg / --dim / --line / --hairline / --log-fg / --code-* / --control-*`）仍在 `<style>` 的 `:root` 与 `html[data-theme="light"]` 两块里；
  - **画面配色集中在 JS 的 `PALETTE` 里**（2026-09 用户要求"把非激活点 / 音符字 / 连线 / 背景色这些变量和段落色写到一块，我边看边调"）：`PALETTE.dark` / `PALETTE.light` 各有一份 `stageBg`（画面底）、`edge` + `edgeFadeFrom` / `edgeFadeTo`（连线的墨色与两端浓度 = 方向）、`nodeBase`（点本来的颜色）、`labelInkLight` / `labelInkDark`（音名的两个候选字色）、`sections[4]`（段落色 = 被激活时的颜色）；`applyTheme()` 把它们推成 `<html>` 上的内联 CSS 变量（`--stage-bg` / `--graph-node-base` / `--section-color`），CSS 规则照旧用 `var()` 取值，**CSS 里不再声明这几个变量**（内联样式优先级更高，写在那边改了也不生效）。非法色值会被跳过并在控制台点名，所以手调时打错不会把画面弄坏。页面 HUD 的配色（面板、正文、控件、`code`）不是画面的一部分，仍在 `<style>` 的两个变量块里；
  - **常规连线去掉箭头，方向改用沿线灰度渐变**（2026-09 用户："去掉常规连线的箭头，显得很乱，能否用渐灰度代替箭头的方向。激活线的箭头还保持啊"）：每条边在 `defs` 里有一条**自己的** `linearGradient`（轴 = 这条边的弦，每帧跟着点更新），两端用 `stop-opacity` 做出浓度差 —— `edgeFadeFrom`（起点端 1）→ `edgeFadeTo`（终点端 0.3）。默认"起点亮、终点淡"，所以终点端那 `ARROW_TAIL_OFFSET = 11.7` 的"箭头位"正好被渐隐吃掉，不会显得线被截断（想反过来就对调两个值）。**"方向"和"概率"因此是两个独立通道**：元素 `opacity` 管概率明度，`stop-opacity` 管线内两端差。**激活线的箭头全保留**：生长/反向生长时是骑行箭头（`#arrowhead`），颜色到位后是行进层停在终点的那支（`#arrowhead-pulse`）。连带删掉三样：`syncEdgeArrow` / `edge.arrowOn`（底边不再有箭头，没有读者了）、`.chain-edge.active`（底边本来就**永远被 2.4 宽的彩色层完整盖住**，所以"到位换色"在画面上没有效果；`pulse.recolored` 仍保留，它管的是箭头的交接）、`--graph-edge`（CSS 里已无人读它）。★ 两个坑：**几何必须只有一份**（`edgeGeometry()` 同时给出 `d` 与渐变轴；分开算会让渐变和线错开），以及**自环要特殊处理** —— 本素材 48 条边里有 1 条 `C3|C3`，起终点重合会让 `x1,y1 == x2,y2`，按 SVG 规范**整条渐变不渲染 = 那条线直接消失**，所以自环用它那圈"上抛"的两端当轴。实测：`stroke` 与 `getComputedStyle` 都是 `url("#edge-C3-E4-grad")`、两条 stop 是 `#71717a@1` / `#71717a@0.3`、轴的起点与路径 `d` 的第一个坐标逐位一致、挪动终点 40px 后轴跟着变、**48 条边的轴无一退化**、常规线 `marker-end` 恒为 `null`、生长中骑行箭头 = `url(#arrowhead)` → 到点后 `null` + 行进层 = `url(#arrowhead-pulse)`；
  - **点的颜色是两个状态、两种来源**（用户 2026-09："乐句点有本来的颜色和被激活的颜色（跟随乐句颜色）"）：平时就是点**本来的颜色** `nodeBase`（不随段落变），刚发声时插值到**本段落色** `mix(nodeBase, 段落色, flash)`，flash 由该音的 I 决定衰减时长 —— 所以"被激活的颜色"是算出来的、不是配置项。旧结构里 `nodePresent`（在场点的灰）与 `nodeBase` 重复，`nodeIdle` 则完全看不见（休眠点透明度 0、靠宿主遮住，用户实测"两边 nodeIdle 都没有作用"），两个键都删掉了；`PALETTE` 现在 7 个键，每个都能在画面上指出来。★ 中途我曾把这条误读成"平时也该带一点段落色"并加了 `nodeTint` 混合，结果整圈都变成段落色，用户指出"现在全部都成乐句颜色了"，已回退 —— **平时的点必须是它自己的颜色**。★ **点不再画描边**（用户："音符点不要描边"）：`stroke` 固定 `none`，`--graph-node-stroke` 与图例上的描边一并删除。★ **音名的字色是 `labelInk` 一个键**（用户先要求"音符点的字色也要在这里"，我做成"浅墨/深墨两个候选 + 自动挑，结果被读成"浅色主题的字色 / 深色主题的字色"，两边各填了一组同明度的值，两套主题里音名都糊在点上（实测深色 `#18181b` 压 `#414149` = 1.8:1、浅色 `#ffffff` 压 `#C2C2C2` = 1.6:1）—— 现在就是一个明确的字色，只有压在 `nodeBase` 上对比度低于 3:1 时才退回白/深墨并在控制台点名。**键名要说清"它是什么"**。实测八种组合（两套主题 × 四段）：平时恒为 `nodeBase`、刚响恒为本段段落色、`stroke` 恒为 `none`、flash=0.5 落在两者中点；
  - **修掉"切主题只有背景变"（2026-09 用户报的 bug）**：症状看起来像"其它颜色没跟着换"，实际是点击按钮时**抛了异常** —— 那句"把当前段落的颜色接到新主题上"用的是 `currentSection`，而**这个名字在顶层不存在**（两处 `let currentSection` 分别在段落链工厂与 `activateEngine` 内部），于是 `ReferenceError`；它又正好是 handler 的**最后一句**，所以 `applyTheme()` 已经跑完（背景、面板、点、连线都换了），只有段落色停在旧主题上，而段落色管着**刚发声的点、彩色连线、图例彩点、日志文字** —— 正好是最显眼的那部分。修法：加顶层状态 `currentVisualSection`（由 `applyPhraseVisual` 写），并用它重定位；同时给这段包了 `try` + 报警 + 退回 `sections[0]`，主题切换不会再变成"静默半切换"。实测修复后：暗→亮时段 C 的段落色 `#FF7904` → `#FF741E`（新主题里段 C 的值）、图例彩点同步、切回来再变回去，`console.warn` 为空；
  - **已经打印出来的日志行也要跟着换色（2026-09 用户："打印的乐句颜色没跟上吧"）**：日志每行按**它所属段落**着色，而段落色是分主题的 —— 旧实现只在打印那一刻取一次色（`log(msg, sectionColors()[section])`），切主题后老行就永远留在旧主题的配色里。现在 `logLines` 存的是**段落号 + 当前 RGB**，切主题时 `repaintLog()` **逐行**从自己的旧色插值到新主题里同一个段落的色（时长同样 `SECTION_COLOR_MORPH_S`）；不能复用 `tweenSectionColor`，因为它插的是"**当前**段落色"这一个值，而每行有它自己的段落。实测：暗→亮时四行 `#624DFF/#8DFE03/#FF7904/#FA2251` → `#FFC228/#2558FF/#FF741E/#45C674`，切回逐字复原；切完后新打印的行直接用新主题的色（行数上限 80 的逻辑不受影响）；
  - **容错实测**：把 `labelInk` 设成与 `nodeBase` 同色 → 控制台报"只有 1.00:1，音名会看不清；已临时改用 #ffffff（10.11:1）"，`nodeLabelInk` 变为 `#ffffff`；
  - **踩到的顺序坑（本轮）**：把"音名墨色"接进 `applyTheme()` 之后整页视觉直接不建起来 —— `applyTheme()` 在脚本中段就被调用一次，而它间接用到的 `mixRgb` 声明在更后面，于是 `Cannot access 'mixRgb' before initialization`。修法是把 `mixRgb` / `rgbToHex` 提到颜色常量之前（与"edge.rest 在边创建之前算"那次是同一类问题）；探针里表现为 `ensurePhraseGraph is not defined`（脚本中断，后面的声明全没执行）；
  - 段落色：`PALETTE.dark.sections` / `PALETTE.light.sections` 各四个（A/B/C/D）；换一整组色时按**色相最近一一对应**，不要凭感觉指派；

## 0.2 背景 texture

环境层取自 Moodist，目前包含 Brown Noise、Wind in Trees、Jungle、Birds、Busy Street 与 Crowd。Jungle 使用官方 `public/sounds/nature/jungle.mp3`，作为较长的自然底层随机出现，而不是随每个乐句触发。

- texture 使用由演出种子派生的独立 RNG；增加、删除或加载失败都不会改变钢琴的 Markov 行走路径。
- 各层按照自己的出现周期、持续时间和概率调度，并以 5–9 秒淡入淡出；同一时刻最多保留两层，避免环境声掩盖钢琴。
- Jungle 当前周期为 75–145 秒、持续 28–58 秒、出现概率 0.62、目标增益 0.14；听感调整优先改这些参数，不改乐句与段落结构。
- 音效采用并行加载和单项 12 秒超时。某一素材失败时只跳过该层，不阻塞整首作品启动。
- `schedule()` 启动 texture 调度；`end()` 停止播放并清理 Transport 事件；`deactivate()` 释放 Player、Filter、Gain 与 Panner，避免再次播放时复用已停止资源。

## 0.2 视觉与交互

- 马尔可夫状态网络占满窗口并保持响应式居中；节点代表音高，箭头代表素材中存在的转移。
- 节点只有“当前”与“非当前”两个状态。刚弹过的节点逐渐退回非当前色，不额外保留第三种历史状态。
- 乐句历史是网络下方的静态 z 层；新乐句从视窗底部进入，将旧行平滑向上推。移动端历史位于上半屏。
- A/B/C/D 四类乐句分别使用紫、绿、橙、粉色，节点高亮、活动边和乐句文字保持同一主题色。
- 点击舞台可显示或隐藏 HUD；HUD 包含标题、播放控制、状态、图例和机制说明，不参与网络布局。
- 音频由 Transport 预排，视觉只在 `Tone.Draw.schedule(..., audioTime)` 到达实际发声时刻后更新，避免 lookAhead 造成提前高亮。

## 机制说明

```
乐句库（10 句，分 4 段：安静/主题/发展/结尾）
→ 段落感知马尔可夫链：段落层按转移矩阵选段（主循环 A→B→C→A），句层段内选句
→ 每 32 步选择一种演奏版本播放乐句（完整/骨架/回声/迟到回应）
```

- **音符 100% 来自素材**（记忆），**段落与乐句顺序被概率重组**（重排）——听感是"同一首曲子每次演奏段落顺序不同"
- **段落感来自素材结构**：原版 301 秒谱面含 intro→主题→发展→结尾的性格差异，马尔可夫链保留了段落衔接规律；本练习用 10 个带段落性格的乐句 + 段落转移矩阵模拟
- **留白来自演奏方式**：句尾会自然降密度，双音只在较满版本保留；C 发展段之后会短暂降低整体密度，让段落有回落
- 段落转移矩阵实时显示在页面上，可观察"当前段落 → 下一段落"的概率
- 换一版（新种子）改变行走路径；改 `SECTION_TRANSITIONS` 可调整段落性格（如让发展段更常回落安静）
