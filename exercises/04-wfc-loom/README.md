# 04 · Constraint Loom

第四份练习：把 Wave Function Collapse 的“候选、约束、坍缩、传播”转成一块可演奏的矩阵织物。每个格子不是单个音符，而是一枚带有声音和视觉双重定义的音乐瓦片；WFC 先让整块织物从可能性中收束，再由梭子按蛇形路径读出。

版本：[`0.1`](0.1/)（8×8 矩阵织机，最小分层 WFC，先坍缩后播放）；[`0.2`](0.2/)（二维单音 tile WFC，边坍缩边发声 —— 后来陆续补上了时钟节拍、句法留白、跟着音长走的坍缩节奏、BPM、动态时值线、钢琴采样与和声进行，见下面各节）；[`0.3`](0.3/)（当前版本：在 0.2 上把"时间"这一层拆到最小 —— 去掉时值线、拍内延迟归零、**时值全部统一 1 拍**）；[`0.4`](0.4/)（**最小 WFC 实验**：按用户规格 [`0.4/实验说明.md`](0.4/实验说明.md) 从最小功能重建 —— 一维 16 格时间序列、候选**只由调与音阶派生**（A minor 7 个音）、只两条规则（max interval 5 / max repeat 2）、**边坍缩边发声**（第 1 圈听到的是熵顺序的生成过程，之后按时间顺序循环成品旋律）；**不继承** 0.1–0.3 的任何规则。理由与"一条规则一验"的协议见 [0.4/README.md](0.4/README.md)）；[`0.5`](0.5/)（**当前版本**：在 0.4 上只加三个机制 —— **rolling window**（16 格未来窗口，播完最左格就滚动、右端补入新格，从有限序列变成可以一直跑的时间系统）、**register drift**（缓慢漂移的音区中心，只给合法候选加权、不删远处的音）、**density drift**（缓慢漂移的全局疏密，控制窗口整体该有多少个 note，只有 note 格进入音高坍缩、rest 只是时间空位）；实测与设计取舍见 [0.5/README.md](0.5/README.md)）。

## 当前定位

- 生成范式：约束坍缩。它不同于 02 的 Markov 行走，也不同于 03 的相位错位；WFC 面对的是一整片尚未确定的空间，某个格子的坍缩会改变邻居的候选集合。
- 视觉形式：矩阵基础上的“约束织机”，不是几条横向轨道。横向隐含时间，但播放路径是蛇形梭子；格子之间的线表示邻接约束和传播张力。
- 音乐形式：每列是一枚分层乐句柱，而不是一格一声的 step。低音、和声、旋律、节奏、纹理和留白共同决定这一柱如何发声。
- 0.1 采用“先坍缩后播放”：先看整块织物被解出来，再听梭子读谱。初版曾把 64 个格子都当作直接发声的 tile，听感过于僵硬；0.1 已改成最小分层 WFC，每个时间柱同时坍缩 `section / chord / bass / melody / rhythm / texture / accent`，声音按 8 个乐句柱读出，而不是逐格硬触发。视觉也从“发光网格”改为哑光织物和线束张力：不靠假发光表示状态，播放时牵动相关层而不是整列当作音序器亮起。
- **当前基线**（[`0.5/index.html`](0.5/index.html)，根索引指向它）：0.4 的最小 WFC + 三个机制 —— **rolling window**（16 格未来窗口持续滚动，播完最左格就补新格 ⇒ 可以一直跑的时间系统）、**register drift**（缓慢漂移的音区中心，只给合法音高候选加权）、**density drift**（缓慢漂移的全局疏密，控制窗口整体该有多少个 note，rest 只是时间空位）。设计取舍、实测与被否掉的做法见 [0.5/README.md](0.5/README.md)。
- **0.3 的基线**（[`0.3/index.html`](0.3/index.html)，保留）：0.2 的副本，但把时间这一层拆到最小 —— **去掉了时值线**、**拍内延迟归零**、**每个音的时值都统一成 1 拍**（于是坍缩也固定每 1 拍一次，64 格 = 64 拍 = 16 小节 = 4 句）。和声 / 权重 / 留白 / 音色 / 母带链与 0.2 逐字相同。
- **0.4 的最小 WFC 基线**（[`0.4/index.html`](0.4/index.html)，保留）：按用户规格 [`0.4/实验说明.md`](0.4/实验说明.md) 从最小功能重建 —— 一维 16 格时间序列、候选只由调与音阶派生、只两条硬规则、边坍缩边发声；0.5 就是在它上面加机制。协议见 [0.4/README.md](0.4/README.md)。
- **0.2 的基线**（[`0.2/index.html`](0.2/index.html)，保留）：二维单音 tile WFC，**边坍缩边发声**。时间来自时钟（**每次坍缩都踩在拍上**：步长 1–3 整拍、跟着音长走，4 拍一小节、16 拍一句，BPM 可调）；音高来自**时间轴上的和声进行**（六个 F 小调三和弦，每 8 拍换一次，强拍锁和弦音、弱拍留经过音、带倾向解决）；音色可选**钢琴采样**或合成器；视觉是「候选小方块 → 坍缩成音高 tile」，格底的时值线**跟着音一起长出来**。完整规则与实测见下面「0.2 …」各节。

## 学习内容

- 把 WFC 从图像瓦片转写成音乐瓦片。
- 用局部邻接约束控制音乐片段的横向连接和纵向密度。

## 0.3 · Note Tile Collapse（保留的二维基线）

0.3 是 **0.2 的副本**，按用户指令分两步把"时间"这一层拆掉（其余逐字不动）：

1. **完全去掉时值线 `.time-mark`** —— 连同它脚下的 5 拍标尺 `.time-lane`、CSS 里的两层刻度、以及整套运行期逻辑（`growing` 队列、逐帧写 `--time-w`、`growMark` / `freezeMarks` / `stopMarks`）。格子里现在只剩"候选小方块 → 坍缩成 tile"。
2. **每个音都正好落在拍点上** —— 0.2 的拍内延迟（0 / 0.5 拍，由 `(row*2+col*3) % 4` 派生）**全部归零**，于是"听觉上的起音间隔 = 坍缩步长 = 整拍"。
3. **（第二步）连时值系统也去掉，全部统一 1 拍** —— 用户看了 0.2 的时值规则之后的原话是"2 的时值也不要"，并在"A 按乐理给不同时值 / **B 全部统一 1 拍**"之间选了 **B**。于是 `RHYTHM_CELLS`、`cellTime()`、`noteDuration()`、`WAIT_SCALE`、`LEGATO_S`、`CADENCE_S`、`STEP_BEATS` 整套删除，只留一个常量 `NOTE_BEATS = 1`：**每个音响 1 拍，每 1 拍坍缩一次**。

**统一 1 拍之后的直接后果**（这也是选 B 最该知道的）：时值 = 步长 ⇒ `pruneRinging` 在下一步就剔掉上一个音 ⇒ **任何两个音都不叠置**，于是 0.2 的**协和兜底**（与仍在响的音撞小 2 度 / 三全音 / 大 7 度 ×0.03）与**同音退场**（`tieOver`）在 0.3 里**恒不触发**（逻辑保留在代码里，注释写明"恢复时长时才会重新生效"）；反重复只剩 `PITCH_RECENCY` 这一条在起作用。另外 64 次坍缩 × 1 拍让整曲长度变成常量：**64 拍 = 16 小节 = 4 句**（第 k 次坍缩正好在第 k 拍；★ 注意是"第几步"不是"哪一格" —— 哪一格坍缩仍由熵决定），120 BPM 约 32 秒。

实测（离线 16 种子共 1024 步 + 真实浏览器整曲，种子 12345）：

| 项 | 0.2（第十二轮之后） | **0.3** |
| --- | --- | --- |
| 音头在正拍点的占比 | 87% | **100%**（1024/1024 离线、54/54 浏览器） |
| 听觉起音间隔是整拍的占比 | 75% | **100%**（最小 1 拍；休止处自然是 2–3 拍） |
| 音符时值 | 0.25–4 拍（平均 1.74–2.04） | **恒为 1 拍**（808/808 离线、54/54 浏览器 0.5s） |
| 坍缩步长 / 最大离拍 | {1,2,3} 拍 / 0 | **恒为 1 拍** / **0.000000** |
| 模型里的叠置 | 同时最多 2 个音 | **0**（每个音都在下一步之前结束） |
| DOM 里 `.time-lane` / `.time-mark` | 每个 cell 一个 | **0 / 0**（播放中也 0） |
| 留白拍上的起音 / 调外音 | 0 / 0 | 0 / 0 |
| 整曲拍数 | 79–92（随种子变） | **恒为 64 拍**（16 小节 = 4 句，约 32 秒） |
| 画面激活对齐 | 排在「步 + 拍内延迟」 | 与发声同刻：相对自己那一拍的最大偏差 **0.0027 拍（≈1.4ms）**，与发声差 **+10ms**（一个动画帧；`Tone.now()` 还含 Tone 的 `lookAhead 0.1s`） |

其余一切照 0.2：和声进行（六个 F 小调三和弦、每 8 拍、强拍锁和弦音、倾向解决）、`PITCH_RECENCY` 时间重复降权、留白不掐音、钢琴采样 / 合成器、BPM、以及**已经删掉半拍延迟**的母带链（`voice → Gain → Reverb → masterGain → Limiter`）。控制台 error / `unhandledrejection` / 未捕获异常全为 **0**（只有 Tone.js 自己的一条 `ScriptProcessorNode` 弃用警告）。

★ 连带说明：因为音头归零，**画面「激活」与发声就同刻落在步时刻上**（0.2 要把它排到 `步 + 拍内延迟`）；状态栏也不再显示"延迟 +X 拍"和"时值 X 拍"（两者都成了常量）。

★ **BPM 与坍缩时间的关系**（0.3 里最简洁的一条公式）：**每次坍缩隔 1 拍 = `60 / BPM` 秒**，第 k 次坍缩在 `0.25 + k × 60/BPM` 秒，整曲 64 拍 = `3840 / BPM` 秒 —— 120 BPM 是 0.5s / 32s，40 BPM 是 1.5s / 96s，240 BPM 是 0.25s / 16s。跟着变的只有"一拍多长"（以及音长和整曲长度），小节 / 乐句 / 和弦周期的**拍数**与同一颗种子的音符序列都不变。★ 但**钢琴 `release` 1.5s、混响 decay 3.6s、`START_LEAD_S` 0.25s 都是写死的秒数、不随 BPM 缩放**，所以速度会顺带改变"干湿感"：240 BPM 时 1.5s 的 release = 6 拍，颗粒被尾巴糊住；40 BPM 时刚好等于一拍，音与音分得开（约 90 BPM 以下"颗粒分明"、180 BPM 以上"洗成一片"）。播放中改 BPM 从**下一次坍缩**起生效（`secPerBeat` 每步现算），已排好的那一步不变；`stepAt` 是累加的，所以中途改速度不会把已播部分重新量化到新网格。完整口径见 [算法规则.md](算法规则.md) §8.1。

★ 待办（0.3 之后的方向）：0.3 暂时**不把时值画出来** —— 要表示时值得换一种形式（例如坍缩后 tile 的色深、或候选区里的一根小竖线），不要再把 `.time-mark` 加回来。若要把"长短"找回来，两条路写在 [算法规则.md](算法规则.md) 的 §15：① 把 `NOTE_BEATS` 换成一张按乐理决定的常量表；② 恢复 0.2 的 `max(1, ceil(时值 × 0.6))` 步长公式（那就得连协和兜底与同音退场一起恢复）。

## 0.1 · 矩阵织机

- 矩阵大小为 8×8。视觉上仍是一块织物矩阵，不画成几条横向轨道；内部把 8 列视为 8 个乐句柱，每列包含 `section / chord / bass / melody / rhythm / texture / accent / space` 八个层级。
- WFC 坍缩时优先选择候选最少的位置；`section` 和 `chord` 稍微优先，因为它们会向下约束其他层。若并列，用种子随机打散。
- 传播规则来自音乐关系：`section → rhythm / texture / accent`，`chord → bass / melody`，`chord → chord` 控制和声连接，`melody → melody` 限制相邻音程，密集 rhythm 会压低 texture 的厚度。
- 播放阶段不再读 64 个格子。梭子按 8 个乐句柱移动；每柱时长由 rhythm 与 section 推导，不再固定等距。同一柱内部由 rhythm 决定低音、和声、旋律和点缀的进入时刻，允许持续、重叠和留白。
- 视觉读取不再使用发光播放头。播放时只把当前乐句柱的相关层临时拉起，稍后把张力交给 `space` 行，表示织物回弹；这只是读取状态，不改写已经坍缩好的算法状态。
- 总输出遵守根 README 的母带链约定：`voices → delay/reverb → masterGain → Limiter(-1) → Destination`，默认 `MASTER_VOLUME_DB = 6`，淡入终点为 `10 ** (6 / 20)`，淡出仍回到 0。这个总增益只补齐整体电平，不替代后续对瓦片相对音量和音色的实际试听调整。

## 0.2 · Note Tile Collapse

> **现行规则看 [算法规则.md](算法规则.md)**：那是"现在到底怎么算"的完整规格（数据模型、每步顺序、完整权重表、时间/和声/时值/视觉/生命周期、现行实测指标与已知边界），描述的是**当前入口 0.3**，开头有一张「0.2 vs 0.3」差异表。本 README 从这一节往下记**各轮演进与当时的实测数字**（都是 0.2 的历次修改），两边冲突时以 `0.3/index.html` + 算法规则为准。

0.2 是一次有意的回撤：暂时放下 0.1 的矩阵织机和多层 HWFC，只做二维单音 tile WFC。参考 Kavin Bharathi 的 WFC 文章中最小模型：每个 cell 保存候选 options，选择低熵 cell 坍缩，再根据邻居约束删除不合法候选。

- 8×8 二维 cell，候选集合重新收敛为 8 个音高 tile + 1 个 `rest`。发声时间不是每个音高的一部分，而是 cell 自己的属性。
- 未坍缩 cell 显示 9 个候选 options；候选小 tile 的颜色 / 标签表示音高或休止。候选区下方是一条 **5 拍**的时间标尺（刻度每 1 拍），标记的起点是该 cell 接进来的延迟、长度是它**实际响多久**；标记在音开始响时从 0 **逐帧长出来**（见「时值线是动态的」一节）。坍缩后整个 cell 被对应音高 tile 填满，时间标记保留在底部。
- 左右邻居限制横向音程；上下邻居限制纵向音高距离。连续重复降权，休止作为兜底。
- 视觉核心：未坍缩 cell 里的小 tile 就是当前候选集合。某个 cell 坍缩成音高 tile 后，邻近 cell 里不再合法的候选小 tile 会消失，这直接显示 WFC 的 constraint propagation。注意当前“同音连续”等音乐偏好主要是**降权**而不是硬禁止：候选消失表示局部兼容性不成立；候选仍在但之后不一定被选中，则可能只是权重较低。
- 目的不是马上生成完整作品，而是把 WFC 的基本观感做干净：cell 如何被 tile 填满，候选集合如何因上下左右关系减少，以及每次坍缩如何直接变成声音。

### 0.2 的节奏规则（2026-09-20 修复）

修复前的触发**没有时间轴**：整条坍缩链跑在 `window.setTimeout(tick, 170 | 310ms)` 上（间隔由「上一个坍缩结果是休止还是音高」决定），cell 自己的时间标记只是加在「它那次 observe 的时刻」上的延迟，而 observe 顺序由熵决定。实测后果：相邻发声间隔有 11–14 个互不成倍数的值；以界面自己画的 0.5s 单位当拍子，落点相位是**均匀的**（10 个桶 25–37，理论 29.4）—— 也就是完全没有拍感；57–60 个音里 **73–83% 被下一个音抢断**（64 格共用一个 `Tone.MonoSynth`，attack 中位间隔 0.31s 而时值 0.125–0.93s）。

现在的规则只有三条，全部来自时钟：

| 规则 | 值 | 说明 |
| --- | --- | --- |
| 一拍 | `STEP_S = 0.5s`（120 BPM） | 每次 observe 占一拍，排在 `Tone.Transport.scheduleOnce` 上；休止**不再**改变步长 |
| 拍内位置 | cell 自己的 `offset`（0 / 0.125 / 0.25 / 0.375s） | 就是一拍里的第 1–4 个十六分位置；time-lane 的一整条宽度 = 这一拍；时值 `dur` 同源（0.125–0.75s，终止列 +0.18s） |
| 力度 | 0.40–0.80 | 小节第 1 拍 +0.22、第 3 拍 +0.10，再叠一层 4 小节（当时的 16 步 = 16 拍）的呼吸弧；沿用 02 记录的力度区间 |

- 整块织物 = 64 步 × 0.5s = **32 秒 = 16 小节 = 4 句**；四句各自呼吸一轮，力度实测 0.427–0.760，按拍位均值 0.709 / 0.487 / 0.589 / 0.490。
- 声部按音区分两个 `Tone.PolySynth(Tone.MonoSynth)` 池（F4–Bb4 / C5–F5），每池最多 8 个音，同池的音可以叠着响；音色选项与原单声部完全一致。
- **音画同刻**：算法在 Transport 回调里同步推进（预排回调受 lookAhead 影响会**提前**执行），DOM 改动一律交给 `Tone.Draw.schedule`，而且**激活画面落在这个音真正发声的时刻上**（`步时刻 + 拍内偏移`，不是拍点）—— 拍内偏移最大 0.375s，画在拍点上就会出现「先亮后响」。休止不发声，所以它仍然画在拍点上，让网格继续可读。真实浏览器用 MutationObserver 抓真实 DOM 变更时刻实测：60 个音的激活都落在发声之后 **−0.008 ~ +0.012s**（就是 `Draw` 的 `anticipation` 与动画帧对齐的量），只有 4 次激活远离任何音符，正好是 4 个休止。**顺带删掉了 `.playing`**：这个类在 0.2 里只有 JS 在加删、CSS 里从来没有规则，所以「激活」在画面上只有坍缩这一层 —— 这也是它此前看起来「永远在第一下激活」的原因（同 02 那条「只剩内部状态、画面上无差别」的机制）。整曲实测：步间隔只有一个取值 **0.500s**，60 个音的拍内偏移**全部**落在 {0, 0.125, 0.25, 0.375}。
- 停止 / 换版会 `Tone.Transport.cancel()` + `Tone.Draw.cancel(0)`，并清掉 Tone 排队中的 voice 回调（`dropPendingVoiceCallbacks`，同 03 的做法），所以停止后控制台不再刷 `Synth was already disposed`（实测 0 条报错、0 条未捕获异常）。
- **已知的边界**：WFC 的空间坐标与播放时钟**没有关系**。observe 顺序由「候选最少」决定，所以「横向相邻 = 时间相邻」只在语法层面成立，听感上不成立；重音因此只能来自时钟而不能来自 `col`。要让横向真的成为时间轴，属于 README「后续想法」里 0.3 的「边坍缩边播放 / 按时间读谱」方向。
- 时间标记只用到 5 种基本 subdivision（`0 / 1/8 / 1/4 / 3/8 / hold`）：早先列过的 `skip` 从未被 `cellTime()` 选中，已删除；要加节奏型必须同时改 `cellTime()` 的 pattern 公式，只往表里加一项不会生效。`phraseAllowed` 里恒为真的分支也已去掉。

### 0.2 的时值与句法（2026-09-20 第二轮）

第一轮把节奏立住之后，听感问题变成「**全是单音、全是短音**」：实测 60 个音里只有 6 对叠置、同时最多 2 个音，平均音长 0.25–0.5s，32 秒里只有 4 个休止。这一轮不动 WFC 结构、不动候选视觉，只用四条规则让单音线有长短与呼吸：

| 规则 | 值 | 说明 |
| --- | --- | --- |
| 级进延长 | 与**上一个发声的音**同音或级进（≤2 半音）→ `LEGATO_S = 1.2s` | 连续级进会串成一条线；跳进 → 用 cell 自己的基本时值断开 |
| 终止延长 | `col === 7` → `CADENCE_S = 2.0s` | 终止列收句 |
| 句尾留白 | 每句最后 `PHRASE_REST_BEATS = 2` 拍强制休止 | 起先还**放掉仍在响的音**（怕长音尾巴盖过休止）；⚠️ **第十一轮把"放掉"取消了** —— 那一放会把横跨乐句末尾的长音掐断，就是用户报的"下一个是空拍时前一个音被突然截断"。现在留白只表示"不再有新起音" |
| 协和兜底 | 与仍在响的音撞上小 2 度 / 三全音 / 大 7 度 → 权重 ×0.03 | 长音一叠，这三类音程会打拍子 |

★ **用「进入音程」决定当前音的长短，而不是去延长上一个音**：上一个音的 release 已经排好了，要延后释放就得把 `triggerAttackRelease` 拆成 attack + release 两次调用，既脆又依赖 voice 池内部状态。现在的做法在触发那一刻就能算完，不需要预知未来，也不破坏「边坍缩边听」。

实测（离线 3 个种子 + 真实浏览器整曲跑完）：

- 音符 45–47 个、休止拍 **17–19**（原来 4）；平均音长 **0.79–0.85s**（原来主体 0.25–0.5s），长音档 1.2s / 2.0s 都真的出现。
- 同时最多 **3–4** 个音（原来 2），叠置对 18–23；有声时间占比 **75–82%**（其余是留白）。
- 叠置音程：协和 78–94% / 温和 6–22% / **刺耳（小2·三全音·大7）0%** —— 随机叠置本来有 8–10%。
- 句尾留白：4 句的 1 秒窗口里**没有新音起音**（浏览器按步号断言 `step % 16 >= 14` 的音符数为 0）。
- 网格不受影响：拍内偏移仍全部落在 {0, 0.125, 0.25, 0.375}，步间隔仍只有 0.500s，控制台 0 报错。
- **两个边界要说清**：① 句尾是「收掉」而不是硬切 —— 放掉之后仍走 1.15s 的 release 衰减，所以那两拍是「没有新音 + 余音渐弱」；② time-lane 只有一拍宽，**画不出跨拍的长音**，横条画的始终是这个 cell 自己的基本时值。
- 这一轮仍然是**一条单音线 + 长音的叠置**，不是分声部的多声部（每步仍只坍缩一个 cell）；「每步同时坍缩 2–3 个音区」留在后续版本。

### 0.2 的坍缩节奏与时间标记（2026-09-20 第三轮）

前两轮把坍缩做成固定 0.5s 一拍：音长完全不影响坍缩节奏，一个 2.0s 的终止音会跨过 4 次坍缩。这一轮让**坍缩跟着音长走**，并把时间标记改成真实时长。

| 规则 | 值 | 说明 |
| --- | --- | --- |
| 坍缩间隔 | `max(1 拍, ceil((延迟 + 实际时长) × WAIT_SCALE))`，`WAIT_SCALE = 0.6` | 短音仍是一拍；长音后面等到 2–3 拍。**取 0.6 而不是 1.0**：等满就没有叠置、退回单音线；0.6 让长音与下一个音重叠约 40%。第三轮原本不取整，第九轮补上 `ceil`（见「坍缩踩在拍上」一节） |
| 时间标记 | 5 拍线性标尺（刻度每 1 拍）+ **逐帧生长** | 起点 = 接进来的延迟；宽度从 0 长到实际时长，长满即结束并保持为这次演奏的记录；休止 → 保持 0 |

### 时值线是动态的（2026-09-20 第五轮）

原来这条线是「静态基本值 → 坍缩瞬间跳到实际时长」，之后就一直不动。现在它**跟着音一起长出来**：

- 音一开始响（`startAt`）就把这一格的线清成 0 并登记进生长队列；此后**每帧**按音频时钟（`Tone.getContext().currentTime`，与音符同一条轴）算进度写 `--time-w`；长满即出队，之后保持。
- 生长与声音**同刻开始**：登记动作本身排在 `Tone.Draw.schedule(..., plan.startAt)` 里，和这个 cell 的填色/音名是同一刻。
- **被同音退场提前放掉的音**（`releaseNotes`）会把线**冻结在截断处**，不会继续长满 —— 看和听都停在同一个时刻。（第十一轮起句尾留白不再放掉任何音，所以那里的线照常长满。）
- 停止播放时冻结生长进程；下一次播放由 `resetVisual()` 恢复成静态基本值。
- ★ 宽度**只有一个来源**（`--time-w`）：静态渲染写基本值、生长写进度；`.time-mark` 的 `width` **不能挂 CSS transition**（会和逐帧写入打架）。

实测：

- 离线 3 个种子：47 / 46 / 46 个格子有生长段，**非单调帧 0、起点非 0 的 0、末值没到目标的 0**，生长起点与音符起点 **100% 对齐**（对不上任何音符的 0 个）；被句尾截断的每场 1–3 个。
- 真实浏览器：一个 2.0s 的音 = **122 帧 / 2.011s（≈61fps）**、末值精确 80%；1.2s 的音 = 73 帧 / 1.200s、末值 48%；控制台 0 报错、未捕获异常 0。

### 音色：钢琴采样（合成器保留）（2026-09-20 第六轮）

右上角多了一个 `音色` 下拉框：**钢琴采样**（默认）/ **合成器**（原来的 PolySynth(MonoSynth) 双池，一字未改）。

- 钢琴沿用 02/03 的同一套素材：`generative-music/samples-alex-bainter` 的 `vsco2-piano-mf`（CDN 为 jsdelivr）。只取覆盖 F4–F5 的 **4 个采样点**（F4 / A4 / C#5 / F5），Tone.Sampler 在期间变调，所以音名不用改。
- 4 个 wav 共 **约 13MB**，首次播放要联网（之后走浏览器缓存）；加载期间状态栏显示"加载钢琴采样…"。**超时 20s 或加载失败 → 自动回退合成器并在状态栏点名**，不会让整首曲子听不到。
- ★ **同一颗种子 → 两种音色完全相同的演奏**（音名、时值、坍缩顺序、时值线都一样），所以可以直接 A/B 对比音色。实测同一颗种子下两种音色的**前 10 个音逐位相同**。
  - 播放中/暂停中切换音色 → 用**同一颗种子**重建并立刻重放；
  - 已经停止时切换 → 记下选择，并仍然锁定同一颗种子，所以按播放听到的还是这首。
- **响度对齐**：`PIANO_VOLUME_DB = 14` 不是猜的。在**真实输出链路末端**（`Tone.Destination` 上挂一个只读分析器）、用同一颗种子各放 16 秒实测：钢琴的有声帧 RMS 比合成器低 **8.2 dB**、峰值低 11.9 dB，所以按"有声帧 RMS 对齐"补 +8 dB（6 → 14）。改后两者 **RMS 只差 1.1 dB**，峰值 0.50（钢琴）/ 0.81（合成器），都低于母带链的 `Limiter(-1)`（≈0.89），没有削顶。
- 两个实现约定：① 两套音色共用同一个演奏接口 `trigger / releaseNotes / releaseAll / dispose`，引擎构建时按常量选一套，所以**换音色不影响任何音乐逻辑**；② 采样加载失败时**不要 dispose 那个还在加载的 Sampler** —— 它没连到 destination 留着无害，而中途 dispose 会让它自己的 `onload` 回调去写一个已销毁的对象。

### 音符与和声逻辑（2026-09-20 第七轮）

**先查后改**。原来的音高设定是「F 小调 8 个音（F4 G4 Ab4 Bb4 C5 Db5 Eb5 F5）+ rest，独立抽选，只有级进偏好和两个音区偏置」。用 5 个种子、320 次坍缩量出来：

| 指标 | 原来 | 对照 |
| --- | --- | --- |
| 落在 F/Ab/C（主三和弦）上的音 | 60% | — |
| 强拍（每 4 格第 1 格）落在和弦音 | **67%** | 02 的手写乐句里强拍几乎全是和弦音（C4-E4-G4-C5、C3+E4） |
| 倾向解决（Db→C / Eb→F / G→Ab / Bb→Ab,C） | **31%** | 02 有明确的 **B4→C5** 导音解决 |
| 音域 | **12 半音**，只有 C4/C5 | 02 是 **C3–C6**；03 是 **A2–F6** |
| 音高集合的性质 | 一条**音阶**（40% 是随便撒的非和弦音） | 03 整首只用**同一个和弦**（F/A/C#），任何叠置都协和 |

结论：**0.2 原来没有"和声"这个概念** —— 只是"在 F 小调里随机走音阶"，所以听不出和声进行，也没有落音与解决。这一轮照 02/03 补上和声层：

- **和弦挂在时间轴上**：六个 F 小调三和弦（`Fm Db Ab Eb Bbm Cm`，直接借 0.1 的 `CHORDS` 与 `next` 进行图），**每 8 步**换一次，用**种子派生的独立 rng** 走 next 图 —— 绝不动 WFC 那条随机序列（否则增删和弦会改变整块织物）。状态栏实时显示当前和弦。
- **强拍锁和弦音、弱拍放开经过音**：强拍和弦音 ×8 / 非和弦音 ×0.4；弱拍和弦音 ×4 / 非和弦音 ×1。
- **倾向解决**：只有「上一个音是**当时的非和弦音**」才要求解决（是和弦音的倾向音不需要解决），而且只在**当前和弦的和弦音内部**优先解决目标（×2.5）—— 这样它不会和和声骨架打架。
- ★ **和弦必须挂在步号（时间）上，不能挂在格子的 row/col 上**：空间坐标与播放时刻无关，那样等于在和声上撒随机（与"重音不能来自 col"是同一条）。

实测（5 种子，同一套脚本）：

| 指标 | 改动后 |
| --- | --- |
| 落在**当前和弦**和弦音上（全体） | **85%** |
| 强拍落在和弦音 | **95%** |
| 非和弦音（经过 / 辅助音） | **15%**（原来 40% 随机撒） |
| 倾向解决（规则生效时命中目标） | **50%**；单元级实测目标音概率 26% → **47%** |
| 候选集大小（选音时） | 平均 **6.48**（传播有收窄，但没到"没得选"） |
| 同一颗种子两次播放 | **逐位相同**（浏览器实测前缀 17/17） |

★ 顺带修掉一个隐患：`schedule()` 原来会丢掉上一批 `eventIds` 却**不 clear**，于是重复调度会留下一条 `end()` 永远清不掉的旧坍缩链（外部播放器连发两次 play 就会变成两条链）。现在先 clear 再重置，实测连发两次 play 的音符数与单次相同。

**还没做的（下一轮的杠杆）**：音域仍然只有一个八度、**没有低音与音区对比**（02 是 C3–C6、03 是 A2–F6）。要补这一块需要扩采样集（每个 wav 约 3MB）或按行移八度 —— 那属于下一轮。

### 同音重复不再"连坐"截断（2026-09-20 第八轮）

用户报「有的音断的特别突然」。**先用输出包络定位是哪一类音**：在 `Tone.Destination` 上挂只读 analyser，每帧采 RMS，按分组量"某个音的释放点之后 250ms 掉了多少 dB"（对照组才是判据）：

| 分组 | 释放后 250ms | 80ms |
| --- | --- | --- |
| **同音重触发** | **−11.5 dB** ← 最陡 | −3.2 |
| 被句尾放掉（第十一轮已取消这个行为） | −11.5 dB | −3.2 |
| 长音 dur>0.75s | −6.8 dB | −2.4 |
| 短音 dur≤0.25s | −10.4 dB | −3.0 |
| **对照组**（不长不短、不重触发、不被句尾放） | −2.8 dB | −0.7 |

根因在 `Tone.Sampler` 的语义（读 14.7.58 源码确认）：**`triggerAttack` 每次都新建一个 `ToneBufferSource` 并堆在同一个音高下；而 `triggerRelease(note, t)` 会把该音高**全部**活动 source 一起 `stop(t)` 然后清空列表**。所以后一个同音——哪怕它自己只有 0.125s——**自己的释放点会把前一个还在响的长音一起停掉**。和声改成"强拍锁和弦音"之后同音重复从 13/60 涨到约 31%，这个连坐就变得常见了。

修法：**同音重复时，先让旧音在新音的起音处退场**（钢琴上这正是"重新按下同一个键"，合成器上就是干净地重发音），并把它的 `endsBeat` 收到此刻，于是协和判断也不再把它算作"仍在响"。实测同音重触发组从 **−11.5 dB 回到 −4.1 dB**，与对照组（−3.4）和长音组（−5.0）齐平；全曲最陡的单帧下跌只剩 5.4 dB 且发生在 −66 dBFS 的电平上（听不见），**没有硬切**。（这里提到的"同音重复率涨到约 31%"，第十轮已经从权重层压到 5–7%，见「时间同音降权」一节。）

★ **一个被数据否掉的修法也记下来**：我先把"短音的 release 放长（软着陆）"当作候选修法实现了一版，实测只把短音组从 −10.4 改到 −9.6 dB —— 说明短音掉得快是**钢琴采样自身前 250ms 的自然衰减**，不是包络尾巴的问题；而且软 release 会让 0.125s 的音拖到近 3 秒、把"跳进即断开"的句法糊掉。**已回退**。

现在只剩两处**设计上**的"收掉"：① 短音按自己的时值被 damp（这就是乐理上的断句）；② 每句末尾把仍在响的音一起放掉（让留白听得见）。两者都是有意为之 —— 若觉得还要更软，再单独谈。

实测（离线 3 种子 + 真实浏览器整曲）：

- 步间隔取值 **{0.5, 0.72, 0.795, 0.87, 0.945, 1.2}s** —— 与当时的公式逐项核对 **0 例外**。（★ 这组数字正是第九轮的问题所在：它们是 1 / 1.44 / 1.59 / 1.74 / 1.89 / 2.4 拍，**非整拍**，所以步时刻会累积偏离拍点。第九轮取整后步长只有 {1, 2, 3} 拍。）
- 整曲从 32s 变成 **38–41s**；同时最多 2 个音（`WAIT_SCALE=0.6`）、叠置对 14–16、刺耳仍 **0%**。
- 标记写入宽度 **{0, 5, 10, 20, 30, 48, 80}%** = {休止, 0.125, 0.25, 0.5, 0.75, 1.2, 2.0}s ÷ 2.5，**全部相符**；拍内延迟仍严格是 {0, 0.125, 0.25, 0.375}s；句尾留白步里的音符数 0；控制台 0 报错。
- ★ 想同时响更多音就把 `WAIT_SCALE` 调到 0.45–0.5（实测同时最多回到 3 个、整曲约 35s）；它是**一个常量**，调它不需要改任何规则。

**两处语义随之改变，别按旧说法读代码**：

2. 状态栏不再显示"小节"（同上原因），改为显示这一步的延迟、实际时值与传播格数。

### 0.2 的坍缩踩在拍上（2026-09-20 第九轮）

用户第三次报同一件事：「还是觉得坍缩没有在节奏上」。**先把"离拍点有多远"量出来**（离线桩跑整曲，只取 Transport 上排出的步时刻，3 个种子 / 195 步）：

| 指标 | 修复前 |
| --- | --- |
| 步间隔取值（拍） | **{1, 1.44, 1.59, 1.74, 1.89, 2.4}** —— 6 个互不成倍数的值，只有 60% 是整拍 |
| 步时刻偏离拍点的量（拍） | 中位 **0.23**、90 分位 0.42、最大 **0.49** |
| 偏离 >0.01 拍的步占比 | **90%** |

根因不是"间隔不够好听"，而是**步长是连续量、而且步时刻是累加的**：`(延迟 + 时长) × 0.6` 会算出 1.44 / 1.59 / 1.74 拍这种非整数值，**一旦出现一个长音，之后每一次坍缩都永久偏离拍点**（偏差还会继续累积）。所以哪怕 60% 的单步间隔"看起来是一拍"，听者也抓不到脉冲。

修法只有一句：**把步长向上取整到整拍**，连带把三处"按格子数"的时间结构全部改成"按拍数"（步长不等距之后，`step % n` 与"每 n 拍"就分家了）：

| 改动 | 旧 | 新 |
| --- | --- | --- |
| 坍缩步长 | `max(1 拍, (延迟 + 实际时长) × 0.6)` 拍（连续值） | `max(1 拍, ceil((延迟 + 实际时长) × 0.6))` 拍 ⇒ **只能是 1 / 2 / 3 拍** |
| 重音 | `step % 4`（每 4 个格子） | `stepBeat % 4 === 0`（**小节第 1 拍**） |
| 乐句留白 | `step % 16 >= 14`（每 16 个格子） | `stepBeat % 16 >= 14`（**每 16 拍 = 4 小节**），并且**长音不许跨过留白窗口**（`waitBeats` 被钳到窗口起点，否则乐句周期会被一步跳过去） |
| 和弦变换 | 每 8 步 | 每 `CHORD_BEATS = 8` 拍（2 小节），进行图长度从 8 项扩到 `CHORD_SLOTS = 24` |

实测（离线 4 个种子，整曲跑完）：

- 步间隔**只有 {1, 2, 3} 拍**，步时刻偏离拍点 **最大 0**；重音落点与小节位置**逐一对上**（18/18、19/19、17/17、18/18）。
- 音符起音全部落在八分网格 {0, 0.25, 0.5, 0.75} 拍（`offset` 0/0.125/0.25/0.375s ÷ 0.5）；**留白拍上的音符 0**。
- 力度分成两档：小节第 1 拍均值 **0.68–0.70**，弱拍 **0.53–0.55**。
- **叠置没有丢**：同时最多 2 个音、平均时值 1.74–2.04 拍（`WAIT_SCALE` 的取舍不变，只是等待量被取整）。
- 整曲 **92–99 拍**（120 BPM 时 **46–50 秒**，原来 38–41s）；`PIECE_BEATS` 由 82 改成 96。（★ 第十轮改音高权重后时值分布也变了：现在是 **79–92 拍 / 40–46 秒**，16 个种子均值 86，`PIECE_BEATS` 已改回 86；拍网格那几条不变量在第十一轮复验仍成立。）
- BPM 扫描 40 / 60 / 72 / 120 / 180 / 240：**拍域序列 md5 全同**（拍域模型没被这次改动破坏）。

★ 两条通用教训：

1. **连续量驱动时间轴时，必须检查"累积漂移"，不能只看单步间隔**。1.44 拍这类值单看像是合理的音乐呼吸，但步时刻是 `stepAt += wait` 累加出来的，一个非整数值就把后面**全部**推离网格（实测 90% 的步都偏了）。判据要落在**步时刻相对拍网格的偏差**上，而不是间隔的分布。
2. **"音乐上的时间结构"（小节 / 乐句 / 和声变换周期）只能数拍，不能数"第几个格子"**。步长一旦不等距，`step % n` 与"每 n 拍"就完全是两件事。这一轮一次改了重音、留白、和弦三处 —— 改动前先全局搜 `step %` 把所有"把步号当时间用"的地方找齐。

### 音头不能落在十六分位（2026-09-20 第十二轮）

用户听完第九、十一轮之后说：「问题不是等 2–3 拍，那种也是正常的，现在是听感上**很多音根本不在拍子上**」。这句把方向指对了：前几轮我盯的是**坍缩步长**（已经全是整拍），而耳朵听的是**音头**。

量"听觉上的节奏"要量两件事，缺一不可（16 种子 / 757 个音）：

| 量 | 第十二轮之前 | 之后 |
| --- | --- | --- |
| 音头相对拍点：正拍点 / 八分位(+0.5) / **十六分位(+0.25 或 +0.75)** | 57% / 18% / **24%** | **87% / 13% / 0%** |
| **实际起音间隔**是整拍的占比 | **38%**（其余是 1.25 / 1.5 / 1.75 / 2.5 拍这类半拍错位） | **75%**（其余是 0.5 / 1.5 / 2.5 拍） |
| 最小起音间隔 | **0.25 拍**（十六分） | 0.5 拍 |

**关键认识：听觉间隔 ≠ 步长。** 步进是从**拍**推进的（`stepBeat += waitBeats`），但音头要再加这一格自带的拍内延迟，于是

```
听觉间隔 = 等待拍数 + (下一格的延迟 − 这一格的延迟)
```

延迟差可以是 −0.5 拍 → 1 拍的等待听起来只剩半拍，甚至出现 0.25 拍的空档。所以"步长全是整拍"完全不能保证"听起来在拍上"——**我前几轮一直在量错的那个量**。

**根因是同一个坑的第四例**：拍内延迟由格子的 `row/col` 派生（`(row*2 + col*3) % 4` → 0 / 0.125 / 0.25 / 0.375 秒 = 0 / 0.25 / 0.5 / 0.75 拍），而**坍缩顺序是熵顺序**，于是延迟落在随机时刻上。前三个例子是重音不能来自 `col`、和声不能挂 `row/col`、同音降权不能只看左邻格 —— 这次是"拍内延迟"。

修法（用户选的 B 方案）：**拍内延迟只剩两档 —— 0（正拍点）与 0.25s = 0.5 拍（推后半拍）**；型名也从 `1/8 / 1/4 / 3/8`（描述"拍内第几个位置"）改成如实描述（`正拍·半拍 / 推后·16 分 / 正拍·1.5 拍`）。型 1 与型 2 因此等价，保留两格只是为了不动 `pattern` 公式。

实测：
- 离线 16 种子：步长仍然只有 {1,2,3} 拍、最大离拍 **0.000000**、留白拍上 0 个音符、调外音 0；音头 87%/13%/0%，听觉间隔 75% 整拍、最小 0.5 拍。
- 真实浏览器（种子 12345 界面种子）：48 个音，音头只有 {0, 0.5} 两档（43 + 5），最小间隔 0.5 拍、整拍占 79%，留白步上被放掉的音 **0**（第十一轮的修复没被破坏），控制台 0 报错。

★ 附带确认：**步长/等待那一层没有被这次改动影响** —— `waitBeats = ceil((延迟 + 时值) × 0.6)` 在四档延迟下算出的结果与新两档一致（短音都保底 1 拍、2.4 拍都给 2 拍、4 拍都给 3 拍），所以改的纯粹是音头落点。同一颗种子因此仍是"同一首"，只是音头对齐了（精确说：时值/等待不变，音高可能因为"仍在响的音"集合变化而略有不同）。

★ **视觉跟进：标尺补了半拍刻度**。原来格底的 5 拍标尺只有每 1 拍一根刻度（`repeating-linear-gradient(..., 20%)`），而延迟收成 0 / 0.5 拍之后，那 8 个"推后半拍"的格子（0.5 拍 = 标尺的 10%）起点正好落在两根刻度**中间**，看起来像"没对齐"。改成两层背景：**深刻度每 1 拍（20%）、浅刻度每半拍（10%）** —— 两档起点都落在刻度上，一行 CSS，不动任何逻辑。

### 删掉半拍回声（2026-09-20，效果链清理）

用户问「是不是加了音频效果器，怎么感觉有回响」。查 git：**混响与半拍延迟是 0.2 首次提交（`d857a93`）就有的**，不在第九～十二轮的改动里 —— 但"感觉有回响"是真的，而且**恰好是第十二轮之后才明显**：那个 `Tone.FeedbackDelay(delayTime = 半拍, feedback 0.12, wet 0.1)` 会给每个音在**正拍之间**加一份很轻的副本；音头对齐到拍点、拍间清干净之后，它就成了拍间唯一的能量。

- **效果链全清单**（原样只有这四个 + 音色节点）：`Limiter(−1)` → `masterGain(淡入 +6 dB)` → `Reverb(decay 3.6, wet 0.26)` → ~~`FeedbackDelay(半拍, fb 0.12, wet 0.1)`~~ → `input(Gain 1)`；音色是 `Tone.Sampler`（钢琴，默认）或两个 `Tone.PolySynth(Tone.MonoSynth)`。**没有**压缩、EQ、失真等。
- **本会话在音频链上真正改过的只有两处**：① 上面那行 `delayTime`（原来是 Tone 的 `'8n'`，本练习不用 `Transport.bpm`，所以永远 0.25s；改成 `(60/bpm)/2` 想让它跟着练习的 BPM —— 但它是**建引擎时**算死的，播放中改 BPM 会漂成一整拍 / 八分之一拍）；② 本次**删掉这个延迟**。
- 实测（浏览器，种子 12345）：48 个音照常触发、控制台与页内错误 **0**；静态清点确认文件里已无 `new Tone.FeedbackDelay`，节点只剩 `Limiter / Gain / Reverb / Gain / PolySynth×2 / Sampler`。混响参数**未动**（`decay 3.6 / wet 0.26`），若仍觉得糊，可再收成 `decay 2.2 / wet 0.15`。

★ 三个方案的选择依据（都实测过）：**A 延迟全 0** → 音头 100% 在拍点、间隔 100% 整拍，但节奏完全靠步长与长音，听感偏机械；**B 只到八分**（采用）→ 87% 在拍点、保留一点八分切分；**C 延迟交给时钟**（0/0.5 且 0.5 只出现在弱拍）→ 能顺带修掉"空间坐标当时间用"，但要新写一条按拍位的规则。用户选了 B。

### 句尾留白不再掐断前一个音（2026-09-20 第十一轮）

用户报「如果下一个是空拍，前一个音会被突然截断」。**先用调用栈把"谁放的"钉死**，再改：

- 在浏览器里给 `Tone.Sampler.prototype.triggerRelease` 打桩并抓 `new Error().stack`，每个音的 `triggerAttackRelease` 与每次**外部**（非 `triggerAttackRelease` 内部）释放都带时刻与调用栈；再用状态栏（`onStep` 写的，含"休止"）标出每一步的类型。
- 结论：**只有句尾留白那一步会主动放掉还在响的音**（`plan.phraseRest && plan.ringing.length` → `voice.releaseNotes`）。普通休止一格都不碰 —— 但"空拍"在听感上就是留白（普通休止时通常还有音在响，只有留白是真的空）。实测这一首里有 **3 个音是在留白处被掐的，最多提前 2 拍**。
- 库的语义（读**实际加载的** 14.7.58 源码，`Tone.Sampler.prototype.triggerAttack.toString()`）：`new ToneBufferSource({ …, fadeOut: this.release })`，而 `triggerRelease(note, t)` 是 `sources.forEach(s => s.stop(t))`。所以那一下是**从满音量开始的 1.5s 线性淡出**（`_stopGain` = `linearRampTo(0, _fadeOut)`）—— 音本来还要再响最多 2 拍（终止列的 4 拍长音常常横跨乐句末尾），听感就是"被截断"。

实测（浏览器，同一颗种子 12345，整曲）：

| | 修复前（读的是缓存旧页） | 修复后 |
| --- | --- | --- |
| 留白步上被放掉的音 | **3** | **0** |
| 外部释放总数 / 落在音的起音上的 | 8 / 2 | **2 / 2**（只剩同音退场） |
| 留白窗口内的新起音 | 0 | 0 |
| 控制台报错 | 0 | 0 |

★ 这一轮踩的三个探针坑，都值得记住：

1. **不带 cache-buster 的本地页面会命中 Chrome 的启发式缓存**：我前几次探针读的一直是**改之前**的页面（表现为"改完还有 3 个音在留白处被放掉"，而且这些释放点找不到对应起音）。发现方式是**在页面里 `fetch(location.href)` 检查标记字符串**，并给 URL 加 `?cb=Date.now()`。

### 0.2 的时间同音降权（2026-09-20 第十轮）

用户问「这种算法是把下一步相同的音，权重降低对吧，怎么现在有大量的重复」——**一半对**：规则**在**，但它管的是**空间上的左邻居**，不是时间上的上一个音。

```js
const previous = cellAt(cell.row, cell.col - 1)?.value;   // ← 左邻格，不是上一个发声的音
if (previous && previous === id) weight *= 0.48;
if (previous && previous !== 'rest' && id !== 'rest') { /* 级进 ×1.6 / 跳进 ×0.44，同样是左邻居 */ }
```

**选格由熵决定，发声顺序与网格行顺序不是一个序列**，所以这三条"旋律"权重作用在你听不到的那条序列上 —— 实测一整首只命中 **7.6 对**。时间上（`noteState.prevMidi`）当时只用于两件事：级进给长音、倾向解决标记，**没有任何同音约束**。

实测（离线 5 种子，`相邻同音 / 2 音内重复`；参考点：**8 个候选里均匀乱抽 = 12.5% / 23.4%**）：

| 规则 | 相邻同音 | 2 音内重复 | 最长连击 | 强拍和弦音 | 用到的音高 |
| --- | --- | --- | --- | --- | --- |
| 无（第十轮之前） | **27.6%**（最高 38%） | 43.3% | **4.2**（最高 7 下） | 86.4% | 7.6 |
| 只压相邻 `[0.2]` | 5.3% | 30.0% | 2.0 | 90.8% | 7.8 |
| **最近 3 个音 `[0.2, 0.5, 0.75]`** | 7.5% | **24.7%** | 2.2 | **94.3%** | **8.0** |

- **★ 判据要用"最近 2 个音之内重复"，不能用"最近 3 个"**：完美地 A-B-C 轮流在"最近 3 个"下面会被记成 100% 重复 —— 指标本身会把好旋律判成坏的。
- **★ 只压相邻同音不够**：改完相邻重复只剩 4.3%，但真实浏览器里前 12 个音是 `F5 Ab4 Bb4 Ab4 F4 Ab4 Bb4 G4 F4 Ab4 Bb4 Ab4`（Ab4 出现 6 次）—— **隔一个音又回来**，听感仍是"大量重复"。所以按"多久以前"分级：age 0 = 0.2、age 1 = 0.5、age 2 = 0.75，3 个音以前不管（那时是呼应，不是卡带）。
- **★ 重复全部是权重选出来的，不是传播逼的**：记录每一步**选择之前**的候选数量，13.4 次重复**没有一次**来自"只剩 1–2 个候选"，全是在候选 ≥3 时选的 —— 所以必须在权重层解决。
- **强拍和弦音反而变高（86.4% → 94.3%）**：以前强拍反复落在同一个和弦音上，现在换到和弦的另一个音 —— 重复少了、骨架更稳，与第七轮记录的 95% 齐平。
- 被否的方案：**再加第 4 个音**（0.85）→ 2 音内回到 30.5%，无收益；**连击按次数加乘方**（第 3 次同音 = 0.2²）→ 相邻 7.5%→5.0%、最长连击 2.2→1.8，但强拍和弦音 94.3%→89.1%，收益只落在"少见的连击 3 下"，不值这条复杂度，**已回退**。
- 相邻重复用"只看上一个音"（`[0.2]`）在相邻这个指标上更低（5.3%），但**听感上更差**（隔音回来没被管），所以最终取三音窗口。
- 真实浏览器整曲（种子 2024 的界面种子）：50 个音、相邻重复 3 次（6.1%）、最长连击 3、用满 8 个音高、控制台 0 报错。
- ★ **探针口径**：页面把种子**字符串**哈希成数字（`hashSeed(text)`，djb2），所以"在输入框里填 2024"与"直接给 `collapseLine` 传数字 2024"是**两首不同的曲子**。做 A/B 时各变体用同一批种子即可；但**不要**拿探针的数字去对页面上某个种子字符串的结果。

### 0.2 的 BPM 输入框与"拍域模型"（2026-09-20 第四轮）

控件在右上角控制面板里：`BPM` 数字输入框（40–240，默认 120）+ 一行提示（第 1 拍多少秒、整曲约多少秒）。按 Enter 或失焦生效；**非法输入（空、非数字、越界）会回到上一个合法值并在状态栏点名**，不把 NaN 带进调度。播放中改也有效 —— 每个 cell 的时长与下一步的间隔都是现算的，从下一次坍缩开始生效。

★ **BPM 只改绝对速度，不改音乐结构**，为此模型整体搬到了**「拍」域**：

- 所有音乐判断（延迟、时值、仍在响的音、坍缩间隔）都在**拍**里算；`RHYTHM_CELLS` 里写的秒数除以 `STEP_S` 就是拍数（120 BPM 时 1 拍 = 0.5s）。
- 只在两个地方换算成秒：排下一步（`stepAt += 拍数 × STEP_S × 120/BPM`）和排声音（`Tone.Draw` / `triggerAttackRelease` 的时刻与时长）。
- 时间标尺也是 5 拍，所以**标记在任何 BPM 下画出来都一样**（实测：改 BPM 前后静态标尺逐格相同）。
- **不要改 `Tone.Transport.bpm` 来代替这个缩放**：本练习用绝对秒数排事件，改 Transport 的 BPM 会把它已经排好的事件按新速度重新解释，正在飞的下一步会跳。

实测（离线 6 档 BPM × 3 个种子 + 真实浏览器整曲）：

- **同一颗种子在 40 / 60 / 72 / 120 / 180 / 240 BPM 下，音符序列的 md5 完全相同**（第九轮复验：拍域的音符、时值、力度、起音拍号逐位相同），整曲拍数也相同。
- 绝对长度严格成比例：120 BPM 39.8s、60 BPM 79.5s、240 BPM 19.9s（那是第八轮以前的长度；第九轮取整后整曲 92–99 拍 = 120 BPM 下 46–50s，比例关系不变）。
- 浏览器整曲复验：步间隔 `{0.5, 0.72, 0.795, 0.87, 0.945, 1.2}s` 与公式 **0/64 不符**；拍内延迟仍是 {0, 0.125, 0.25, 0.375}s；句尾留白步里的音符 0；标记宽度 {0, 5, 10, 20, 30, 48, 80}% 全对；控制台 0 报错。
- 输入框行为：设 60 后间隔精确翻倍（0.5→1.0、0.87→1.74、1.2→2.4）；输入 9999 后回退到 60 并提示"BPM 需在 40–240 之间，已保留 60"。
