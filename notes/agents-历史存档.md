## 03 音乐衔接补充（2026-09-18）

0.3 已开始音色时长与力度呼吸实验，详见练习 README 同名小节：钢琴时长参考采样 RMS 衰减并补偿变调速率；Drone 按周期预算扣除 8s release；时长一场内固定。力度按音频预调度次数推进 5–8 轮余弦呼吸，不能用 Draw 的视觉触发计数。测试 HUD 可切换呼吸，圆角与单面印字继续保留。旧文“音频沿用 0.2”仅适用于早期基线。

**Tone.Sampler 的 `release` 是逐音的，不要为它复制采样器**：14.7.58 的 `triggerAttack` 对每个音**即时新建** `ToneBufferSource`，并把 `fadeOut: this.release` 当场读进去 —— 也就是说 **Sampler 没有 voice 池**（曾担心「池化 voice 会保留旧 release」，读源码后证伪）。所以「每个音自己的 release」只需在触发前写 `piano.release = x`，一次 `triggerAttackRelease` 一个值，**不需要按音复制采样器，也不需要额外增益节点**。0.3 的钢琴 release 以 `period × 比例` 为目标（HUD 滑杆 5%–60%，默认 25%；2026-09-19 加入 3.5s 下限和 `period − duration − 0.5` 上限），并把 `loop.release` 存成**函数**而不是冻结数值，滑杆就能在播放中从下一个音立即生效。★ 顺带一条读别人的库时的通用做法：**要判断某个属性是「共享参数」还是「每实例参数」，直接读 `triggerAttack` 里怎么用它是唯一可靠的办法** —— 光看文档（写「the release time」）会误以为它是全局包络。

## 03 引擎生命周期：构建中的引擎必须能被作废（2026-09-18）

用户报「有的时候钢琴没声音」并伴随 `Synth was already disposed` 疯狂报错。根因**不是**音乐参数，而是 `stop` 落在 `activateEngine` 还没跑完的时候：那一刻 `engine` 仍是 `null`，停止处理函数因此什么都不做，而构建完成后照样 `schedule()` + `Transport.start()` —— 于是产生一个界面再也够不着的**孤儿引擎**：它继续排音、播进已被 dispose 的节点，下一次播放再建第二个引擎，报错每秒 20 次并不停。三条规矩：

- **异步构建的东西必须有代次或取消机制**。`engineTransition` 这类「忙碌标志」只能挡住重入，**挡不住「构建中途被停止」**。做法：`engineGeneration` 计数器，`stop`/`restart` 时自增，构建完成后比对代次，不等就把这个引擎 `end()` + `deactivate()` 掉并 return，**绝不进入 `schedule()`**。构建中的引擎不可取消，只能作废后回收。
- **`stop` 不能只看 `engine`，还要看「正在构建」**（`pendingBuild`）。只判 `engine` 的停止逻辑在构建期间等于没接上。
- **注意 `result.value` 这类「包装之后忘了传值」的坑**：本轮我在重构时把 `settled()` 写成 `try { await promise; return { ok: true } }`，**丢掉了 resolve 出来的值**，于是 `engine = result.value` 赋成 `undefined`，表现为「播放失败：Cannot read properties of undefined (reading 'schedule')」。包装函数一定要把值带出来（`return { ok: true, value: await promise }`）。

`Tone.Synth._scheduleEvent` 里 `assert(!this.disposed, 'Synth was already disposed')` 是 14.7.58 的唯一抛出点。两条独立来源：**①孤儿引擎**（上面那条）；**②凡是时长超过 Tone `lookAhead` 的音符，其 voice 用 `context.setTimeout` 安排未来的 release，而 `Synth.dispose()` 不取消这些回调** —— 引擎销毁后它们才到点，于是抛错并积压数十秒（实测 20 次/秒、最长 158 秒）。修法：`deactivate()` 末尾清空该 context 的待执行队列（`Tone.getContext()._timeouts._timeline`，私有 API，与本仓库已在用的 `_ticker` 同类，函数须注释「升级 Tone.js 要复查」）。★ 它是未捕获异常，**只污染控制台、不改变音频**，所以**不能拿「有没有报错」当作「有没有声音」的证据** —— 判断有没有声音要数 `triggerAttackRelease` 的调用次数。

**验证这一类竞态必须用真实浏览器**：本项目历史做法里「无头环境跑不了音频链」的结论作废 —— 加 `--autoplay-policy=no-user-gesture-required --headless=new` 后音频链能跑完（实测构建约 6–8 秒）。★ 三个环境限制：**Chrome 在当前文件沙箱下起不来**（`mojo platform_channel` 要命名管道），需要 `danger-full-access`；**探针要小心读的是不是真页面**（用 `Page.setDocumentContent` 会把文档变成 `about:blank`，相对路径的 `import('./stage.js')` 直接失败，于是你测的根本不是那个页面 —— 要改文档就用 `Fetch` 拦截响应体，保住 URL）；**测试脚本传 `{ requestStage: 'Response' }` 拦截时，`ws.onmessage` 里不能同步 await 处理**（会在 `Page.navigate` 上死锁，表现为「unsettled top-level await」且页面根本没重新加载，于是你一直在测旧内容）。


## 04 节奏：observe 顺序不是时间轴，而且 Tone 有两套时间轴（2026-09-20）

04 0.2 的触发原来跑在 `window.setTimeout(tick, value === 'rest' ? 170 : 310)` 上，`Tone.Transport` 一个事件都没排（违反 [`notes/piece-zed-注解版.md`](notes/piece-zed-注解版.md) 第 205 行）。但用户报的「完全没有音乐性」不止这一条，实测（把 0.2 的真实脚本放进假 DOM + 虚拟时钟 + 假 Transport 里跑完 64 次 observe）是三件事叠在一起，必须一起修：

- **触发顺序不是时间轴**：`chooseCell` 按「候选最少 / 熵最低」选格，是信息论顺序；cell 自带的 `offset` 只是「相对自己那次 observe 的延迟」。实测后果：相邻发声间隔有 **11–14 个互不成倍数的值**；以界面自己画的 0.5s 单位当拍子，落点相位**均匀**（10 个桶 25–37，理论 29.4）⇒ 没有拍感；发声时刻与 `col` 的相关在 5 个种子里从 −0.80 跳到 +0.67 ⇒ 列与时间没有稳定关系。★ 由此得出一条规则：**重音不能来自格子的 `col`**（空间坐标与播放时刻无关，用 col 当节拍位置只是在随机时刻撒重音），重音只能来自时钟或来自音乐结构。修法：一拍 `STEP_S = 0.5s`（120 BPM）=`time-lane` 的一整条宽度，`offset` 0/0.125/0.25/0.375 变成拍内第 1–4 个十六分位置，力度 0.40–0.80 由「小节第 1/3 拍 + 16 步呼吸弧」给出。
- **单声部会抢音**：64 格共用一个 `Tone.MonoSynth`，attack 中位间隔 0.31s、时值 0.125–0.93s、release 1.15s ⇒ **73–83% 的音在走完自己时值前被抢占**，既没有旋律线也没有真正的留白。修法是按音区分 `Tone.PolySynth(Tone.MonoSynth)` 池（保留原滤波包络音色）。★ `new Tone.PolySynth(voice, options)` 的**第二个参数是音色选项**，写进里面的 `maxPolyphony` 不会生效（`optionsFromArguments` 把整个第二参数放进 `options.options`），要构造之后 `synth.maxPolyphony = n` 赋值。
- **★ 两套时间轴不能混用**（本轮最大的坑，症状是「第一步立刻响、第二步要等三十秒」）：`Tone.Transport.scheduleOnce(fn, time)` 的 `time` 是**传输时间**，而 `fn` 收到的 `time` 参数是**音频上下文时间**（Tone 官方示例就是把回调的 time 直接喂给 `Tone.Draw.schedule`，Draw 用的也是上下文时间）。把回调的 time 再拿回去排下一步 = 上下文时间被当成传输时刻（实测：上下文 30.5 而传输位置只有 0.5）。做法：**自己维护传输时间轴上的 `stepAt`**，每次 `stepAt += STEP_S` 去排下一步；回调的 `audioTime` 只用于排声音与 `Tone.Draw`。★ 这同时解释了为什么不要用 `'+0.5'` 相对时间：回调执行时 `Transport.seconds` 比事件时刻**提前**约 lookAhead（实测排 0.75 的事件时读到 0.8），逐句累加就是漂移。★ 配套：`Transport` 停止时 `Transport.seconds` 读 **0**（页面开着 30 秒、从未播放过也是 0），所以 `startAt = Transport.seconds + 提前量` 是安全的；`Tone.Draw` 有 `expiration = 0.25`（过期超过 0.25 秒的事件被**丢弃**）与 `anticipation = 0.008`（最多提前 8ms、按动画帧对齐）。
- **离线桩必须忠实模拟这条约定，否则 bug 在离线验证里隐形**：我第一版探针的 `scheduleOnce` 桩直接把**传输时间**当回调参数传进去，于是上面那个两套时间轴的 bug 在离线全绿、只在真实浏览器里暴露。桩要模拟「上下文比传输位置早 N 秒」，并让回调收到 `N + transportAt`。★ 这也是「离线量结构、真机量行为」的分工：网格 / 力度 / 复音 / Draw 时刻可以离线量准，Tone 的 API 约定与报错必须在真实浏览器里验。
- 0.2 也照 03 的做法在 `deactivate()` 里清 `context._timeouts._timeline`（PolySynth 对超过 lookAhead 的音同样用 `context.setTimeout` 排 attack/release），实测「播放 6 秒 → 停止 → 等 5 秒」后 console 与未捕获异常**都是 0 条**。
- **画面「激活」必须落在发声时刻，不是拍点**（2026-09-20 用户第二次报：「视觉激活和实际的时间没对上，视觉现在永远是在第一下被激活吧，有的音符有等待时间的」）：我第一轮把坍缩画面（填色 + 音名 + 候选消除）排在**步时刻**、只把音符闪光排在 `步 + 偏移`，而 0.2 的拍内偏移最大 0.375s ⇒ 25/60 个音「先亮后响」。正确做法：**这一个 cell 的全部激活画面（填色、音名、候选消除、传播）都排在 `步时刻 + 它自己的拍内偏移`**；休止不发声，才留在拍点上。★ 顺带查出一条死代码：`.playing` 这个类在 0.2 里**只有 JS 在加删、CSS 里根本没有规则**，所以现象是「视觉永远在第一下激活」却找不到第二个视觉层 —— 又一个「只剩内部状态、画面上无差别」的机制（同 02 的 `.active`），已删除。★ 验收方法：用 `MutationObserver`（`attributeFilter: ['class'], subtree: true`）抓真实 DOM 拿到 `.collapsed` 的时刻，再与 `triggerAttackRelease` 的时刻相减 —— 实测 60 个音全部落在 **−0.008 ~ +0.012s**（`Draw` 的 `anticipation` 加上动画帧对齐），远离任何音符的激活次数正好等于休止数（4）。**只数「有没有加类」是不够的，必须量「加类时刻与发声时刻之差」**；而且 `MutationObserver` 的回调是微任务，读时间要写在校调里（不要用 `takeRecords()` 的批量计数去代表时刻）。
- 验收用的可量化不变量（真实浏览器，整曲 32 秒跑完）：步间隔只允许一个取值 **0.500s**；音符的拍内偏移必须全部落在 {0, 0.125, 0.25, 0.375}；每次激活必须落在「步 + 偏移」（休止落在步）；力度落在 0.40–0.80；每池同时发声数 < `maxPolyphony`（实测 low/high 各 2，上限 8）。

### 04 第二轮：长音要配协和约束，句法要真的放掉尾巴（2026-09-20）

用户听完第一轮的评价是「听感还是不好 —— 目前只用单音」，并允许更长的音。**先把「为什么难听」量出来再改**：当时 60 个音里只有 6 对叠置、同时最多 2 个音（**本质是单音线**），平均音长 0.25–0.5s，32 秒里只有 4 个休止；而时间相邻音程平均 2.83 半音、空间横向 2.92、纵向 2.98 —— **三者几乎相同，说明「8 个候选挤在一个八度里」让 WFC 的音高约束基本空转**（我原先以为「演奏顺序 ≠ 空间顺序」是主因，被数据推翻：随便抽也就是这个分布）。所以这一轮的**不是**调参数，而是解决「没有和声 / 没有留白」。

- **★ 长音必须配协和约束**：把时值拉长只是把「太干的单音线」换成「随机音簇」——离线模拟（保持每 0.5s 一个新音）显示 T=1.0/1.5/2.0/3.0s 时叠置对从 6 涨到 30/53/75/114，其中 **8–10% 是小 2 度 / 三全音 / 大 7 度**（同一八度里会打拍子）。做法：选音时对「仍在响的音」检查音程，撞上这三类就把该候选权重 ×0.03（软排除，不用硬禁）。实测三个种子**刺耳 0%**（协和 78–94% / 温和 6–22%）。
- **★ 用「进入音程」决定当前音的长短，不要去延长上一个音**：上一个音的 release 已经排进 Tone 了，要延后释放就必须把 `triggerAttackRelease` 拆成 attack + release 两次调用 —— 既脆，又依赖 voice 池的内部状态（`PolySynth._triggerRelease` 是按 midi 找第一个未释放的 voice）。改成「与上一个音同音或级进 → 给 1.2s，跳进 → 用基本时值断开」：在触发那一刻就能算完，**不需要预知未来**，也不破坏「边坍缩边听」。效果是连续级进自然串成一条线、跳进处留出空隙。
- **★ 句尾留白必须把仍在响的音一起放掉**，否则长音的尾巴会盖过休止，"留白"根本听不见。但要说清它是**「收掉」而不是硬切**：`release = 1.15s`，所以那两拍是「没有新音 + 余音渐弱」。验收方式是把每个音用 `Transport.getSecondsAtTime()` 换算回步号，再断言 `step % 16 >= 14` 的音符数为 **0**。
- **测量教训（这一轮踩的）**：① 探针分两轮跑（整曲 + 中途停止）却共用同一个数组，`firstStep`、句法窗口、最近匹配全被污染 —— 我因此误报过一次「句法窗口里有 1 个起音」，干净的单独一轮跑出来是 0。**每轮单独计量**。② 给 `PolySynth.prototype.triggerRelease` 打桩会把每个音记成**两次**：`triggerAttackRelease` 内部就会调用 `this.triggerRelease`。③ 用「最近的音符」给 paint 对齐时，**休止格的 paint 本来就没有对应的音**（按设计画在拍点），会全部落进"偏差过大"里 —— 实测偏差 >30ms 的正好等于休止数（17/64），所以判定前必须先把休止排除。
- 这一轮之后的实测（离线 3 种子 + 浏览器整曲）：音符 45–47、休止拍 17–19、平均音长 0.79–0.85s、同时最多 3–4 个音、有声时间 75–82%、刺耳 0%、网格与视觉对齐不变、控制台 0 报错。**它仍然是一条单音线 + 长音叠置，不是分声部多声部**；「每步同时坍缩 2–3 个音区」留给后续版本。

### 04 第三轮：坍缩节奏跟着音长走之后，标记必须按实际时长重画（2026-09-20）

用户问「坍缩并没有根据发声时长走，每一次间隔都一样吧」——确实如此（固定 0.5s），而且他随即选了「部分等」。**这一轮的关键认识：坍缩节奏与叠置是互斥的**。

- **等满音长 = 退回单音线**。`stepAt += 延迟 + 时长` 会让音与音不再重叠；而 0.2 现在的"和声"完全来自长音叠置（固定 0.5s 步 × 1.2–2.0s 时值）。所以只能取一个**折中系数**：`stepAt += max(STEP_S, (延迟 + 实际时长) × WAIT_SCALE)`，`WAIT_SCALE = 0.6` ⇒ 长音与下一个音重叠约 40%。实测：0.6 → 同时最多 2 个音、整曲 38–41s；0.5/0.45 → 最多 3 个音、整曲 34–36s；1.0 → 1 个音。**把这个系数写成一个常量并在注释里写清取舍**，下一个人调它时才知道自己在动什么。
- **静态时间标记必须允许在坍缩时被改写**：`cellTime(index)` 是页面加载时算的**基本时值**，而实际时长由级进/终止规则在播放中决定；所以标记要画**两遍** —— 静态画基本值，坍缩那一刻（`Tone.Draw` 里）按实际时长重画，休止则写成 0。顺带把标尺从"一拍"改成 **2.5s 线性刻度**（0.375 + 2.0 的跨度），于是"跨了几拍"可以直接数刻度。★ 这也说明：**凡是"显示的值由运行期规则决定"的地方，静态渲染只能算占位**。
- **★ 跨时间轴做归属比较会整体错位**（本轮踩的测量坑）：我想用 `Tone.Transport.getSecondsAtTime(ctxTime)` 把每个音换算回步号，结果间隔公式"不符 11/62"、句尾留白"违规 1 个"；改成**同一个上下文时间域的相减**（音的时刻 − 那一步回调收到的时刻）后，同一份代码跑出 **0/64 与 0**。教训：探针做归属/比较时**必须待在一条时间轴上**（音频与音频比、传输与传输比），跨轴换算会引入看起来像真实 bug 的系统性偏差。这与前面"两套时间轴不能混用"是同一条原则的测量侧版本。
- **公式类规则要逐项核对，不要只看分布**：步长不再等距后，"间隔看起来合理"完全不能证明规则对。做法是离线桩里记录每步的（延迟、时长、下一步时刻），逐项断言 `next - now === max(0.5, (off + dur) × scale)` —— 实测 64/64 相符。同理，标记的验收是"写入的 `--time-w` 集合 ⊆ {0} ∪ {实际时长 ÷ 2.5 × 100}"，实测 {0, 5, 10, 20, 30, 48, 80}% 全中。
- 连带语义变化要跟着改文案：重音从"小节第 1/3 拍"变成"**每 4 个格子**"（步长不等距后 `step % 4` 不再等于每 4 拍）；状态栏不再显示"小节"。**改了时间结构就要回头查所有"按步数当时间用"的地方**。

### 04 第四轮：速度参数要把模型放进「拍」域，只在排程时换算（2026-09-20）

用户要一个 BPM 输入框。**BPM 不能只改最小步长**：0.2 的时值（0.125–2.0s）、延迟、呼吸弧、乐句全是按秒写的，只改步长会让音乐变形。正确做法是**整体缩放时间基准**，但"整体乘一个系数"还不够稳：

- **★ 模型必须待在「拍」域，秒只在排程边界出现一次**。第一版把 `duration`、延迟、`endsAt` 都算成"已缩放的秒"，结果 180 BPM 下同一颗种子的音符序列变了（md5 不同）—— 因为"仍在响的音"这个判定是 `endsBeat <= noteStart` 的**边界比较**，秒域里乘了 0.667 后浮点在最边界处翻了一位，于是协和约束看到的"在响的音"不同，选音也就不同。改成：音乐判断全部用拍（`offsetBeats / durationBeats / endsBeat`），只在两处换算成秒（`stepAt += waitBeats × STEP_S × 120/BPM`、`plan.startAt / plan.duration`）。改完实测 **40/60/72/120/180/240 BPM × 3 个种子，序列 md5 全部相同、整曲拍数相同**，秒数严格成比例。★ 通用规律：**凡是"同一个音乐在不同速度下必须逐位相同"的地方，比较与判决都要在速度无关的单位里做**，缩放只放到最后一步。
- **单位换算漏一处，症状是"结构全对、只有绝对时长错"**：我把模型搬到拍域时漏了 `拍 → 秒`（`stepAt += waitBeats` 少了 `× STEP_S`），于是 120 BPM 的整曲从 40s 变成 79.5s —— 音符数、步数、序列 md5、间隔的**拍**值全都正常，只有绝对时长翻倍。所以速度类改动的验证必须**同时量两件事**：结构（序列 md5 / 间隔的拍值）与绝对时长（秒）。
- **静态渲染可以放心地放在速度无关的单位里**：时间标尺改成 5 拍、标记宽度用拍算，于是**改 BPM 前后每个格子的标记逐格相同**（实测 `staticSame: true`）。★ 反过来，只要标尺跨度与标记数值用了同一个单位，BPM 就不需要参与视觉 —— 这一轮没有再出现"改速度画面跟着变形"的问题。
- **不要用 `Tone.Transport.bpm` 代替自己的缩放**：Tone 的 `scheduleOnce(fn, 秒)` 是**排程时**把秒换算成 tick 的，改 Transport 的 BPM 会让已经排好的事件按新速度重新解释（正在飞的下一步会跳）。本练习全程用绝对秒数，所以 BPM 只作用于我自己的换算。
- 输入框的容错沿用仓库既有规矩：**非法就跳过、保留上一个合法值、并在状态栏点名**（实测输入 9999 → 回退到 60 + "BPM 需在 40–240 之间，已保留 60"）；数字框同时处理 Enter 与 change（失焦）。

### 04 第五轮：把「时值线」做成动态（2026-09-20）

用户要求「单元时值线做成动态」。原来那条线是"静态基本值 → 坍缩瞬间跳到实际长度"，之后不动；现在**跟着音一起长出来**。三条实现规矩：

- **静态渲染只能算占位，运行期决定的量要逐帧驱动**：音一响就把线清成 0 并登记进队列，此后每帧用**音频时钟**（`Tone.getContext().currentTime`，与音符同一条轴）算进度；长满出队、保持为记录。登记动作排在 `Tone.Draw.schedule(..., startAt)` 里，所以生长与声音**同刻**开始。★ 用 `requestAnimationFrame` 驱动、用 `Tone.Draw` 起步 —— 两者都按帧/按音频时钟走，不会引入第三条时间轴。
- **一个量只能有一个来源**：宽度只由 `--time-w` 决定，静态渲染写基本值、生长写进度；并且 **`.time-mark` 的 `width` 不能挂 CSS transition**（会和逐帧写入打架）。这是本仓库第 N 次撞上"单一来源"：这次的危险形式是"CSS 过渡 + 逐帧内联写入"。
- **音频被提前截断时，视觉要停在同一个时刻**：句尾留白会用 `releaseNotes` 放掉仍在响的音，对应的线也必须**冻结在截断处**（实测每场 1–3 条），不能自顾自长满。
- 验收：离线桩要把 `requestAnimationFrame` 也桩进虚拟时钟，然后按格子取"最后一次从 0 开始"的写序列，断言 ① 单调不减、② 起点为 0、③ 末值等于目标（被截断的除外）、④ **生长起点能对上某个音符的起音**。实测 47/46/46 格、四项违例全 0。真实浏览器再验一次帧率与跨度（2.0s 的音 = 122 帧 / 2.011s、末值精确 80%）。
- ★ 探针的 DOM 层级假设也要当心：`.time-mark` 的 `parentElement` 是 `.time-lane` 而不是 cell，按 `indexOf(cellsEl.children, el.parentElement)` 归属会把**所有**写入塞进同一个键（实测 1224 次写入全落在一个格子），表现为"只检查到 1 个格子"却毫无报错。归属要用 `parentElement.parentElement`，并且**要断言分组的数量**（应为音符数），不能只看违例计数为 0。

### 04 第六轮：换成钢琴采样，合成器保留（2026-09-20）

用户要「乐器换成钢琴采样，当前的也保留」。做法与三条经验：

- **换音色只换"生产者"，不碰音乐逻辑**：两套音色共用同一个演奏接口 `trigger / releaseNotes / releaseAll / dispose`，`createVoice(destination, kind)` 在引擎构建时选一套。采样沿用 02/03 的 `vsco2-piano-mf`（jsdelivr），只取覆盖音域的 4 个采样点（4 个 wav ≈ 13MB，首次加载 + 缓存），失败/超时（20s）**自动回退合成器并在状态栏点名**。★ 采样加载失败时**不要 dispose 那个还在加载的 `Tone.Sampler`**：它没连到 destination 留着无害，而中途 dispose 会让它自己的 `onload` 回调去写已销毁的对象（控制台报错）。
- **★ 量"两种音色等不等响"必须：真实输出链路末端挂只读分析器 + 同一颗种子 + 相同窗口 + 只算有声帧**。我第一版直接比 15 秒窗口的平均 RMS，得到"合成器响 14 dB"——**错**：钢琴那一轮包含 13MB 采样加载的静音，窗口里只有 8 个音（合成器 14 个），静音帧把平均值拉低了。改成「先预热加载 → 同一颗种子各放 16 秒 → 只统计 RMS > 0.003 的帧」后是 **8.2 dB**（峰值差 11.9 dB），据此把 `PIANO_VOLUME_DB` 从 6 调到 14，复测两者只差 **1.1 dB**。★ 教训：**只要两轮窗口里的"有效内容"不一样，平均值类指标就不可比**；要么对齐内容（同种子/同音数），要么换成分位数/只算有声帧。峰值与有声帧 RMS 的差（11.9 vs 8.2 dB）本身也有信息：钢琴起音尖、衰减快，峰值高不代表更响。
- **保留"同一颗种子"才能 A/B**：`lastSeed` 记住当前这版的种子，`pendingSeed` 让下一次构建强制复用它。于是"停止 → 换音色 → 再播放"听到的仍是同一首（实测两种音色的前 10 个音逐位相同），这是**听感对比**的前提；换一版/改种子时才清掉它。

### 04 第七轮：音高要有乐理逻辑（先查后改）（2026-09-20）

用户要「检查音符的设定……音符选择要有乐理逻辑，可以参考 02 03」。**先把 02/03 读成事实，再量 0.2**：02 的音乐性来自**手写乐句**（和弦琶音 + 导音解决 B4→C5 + 双音块 + 三音区 C3–C6 + 每句走势 + 低音收束）；03 更极端，全部音高都是**同一个和弦**（F/A/C#）跨 4 个八度，所以任何叠置都协和、音乐靠相位。而 0.2 是"F 小调 8 个音独立抽 + 级进偏好"，实测强拍只有 **67%** 落在和弦音、倾向解决 **31%**、音域只有一个八度 ⇒ **它根本没有"和声"这个概念**。

- **★ 检查"音符设定"要先定义指标再量，而且指标里的和弦必须取"每一步真实的和弦"**。我第一版用固定的 Fm 三和弦去统计，得到"强拍和弦音 74%"，看起来像没生效；改成按每一步的当前和弦统计后是 **95%** —— 是**指标本身错了**，不是代码错了。四个可量化的指标：① 落在当前和弦音上的比例（全体 / 强拍分开）② 非和弦音（经过音）比例 ③ 倾向解决命中率 ④ 音域跨度与八度分布。
- **★★ 权重类规则要"单元级 + 全曲"两个层次都测**。单元级：把候选集给满、直接反复调 `chooseValue`，量它产出的分布 —— 这样才分得清"权重写错了"还是"候选集早被收窄了"。本轮单元级实测：无和声 50.7% 和弦音、强拍 93.6%、Db 之后 C 占 47%；而全曲只有 85%/95%，差的正是**传播把候选集压到平均 6.48 个**。★ 没有这一层，你会一边调权重一边对着被别人主导的结果发愁。
- **强度要分强拍 / 弱拍两档**：单一组权重（和弦 ×8 / 非和弦 ×0.5）会把非和弦音压到 **5%** —— 那等于"只会弹琶音"，旋律的经过/辅助音全没了。拆成「强拍 8 : 0.4 / 弱拍 4 : 1」后：强拍仍 95%、非和弦音回到 **15%**，既有骨架又有经过音。**一个权重同时管两个位置，通常会在其中一处过头。**
- **倾向解决不能和和声骨架抢**：第一版对**所有**倾向音（Db/Eb/G/Bb）都要求解决、并对"不解决"降权，结果和弦的和弦音权重（×8）总是赢，解决率反而从 31% 掉到 23%。正确的模型是：**只有"上一个音是当时的非和弦音"才需要解决**（是和弦音的倾向音不需要解决），并且只在**当前和弦的和弦音内部**优先解决目标（×2.5）。改后规则生效时命中 50%、单元级把目标音概率从 26% 抬到 47%。
- **和弦这一层必须挂在"时间"（步号）上，不能挂在格子的 row/col 上** —— 与"重音不能来自 col"是同一条：空间坐标与播放时刻无关，用它会等于在和声上撒随机。进行用**种子派生的独立 rng** 走 `next` 图（独立流，不动 WFC 的随机序列）。
- **★ `schedule()` 要幂等**：它原来把 `eventIds = []` 直接重置而**不 clear**，于是重复调度会留下一条 `end()` 再也清不掉的旧坍缩链（实测在已播放时再发一次 play → 两条链在跑、音符数翻倍）。改成"先 `clear` 再重置"后，连发两次 play 的音符数与单次相同。**凡是"重置一个装着待清理资源的数组"的地方，都要先清资源再重置。**

### 04 第八轮：`Sampler.triggerRelease` 是按音高停的 —— 同音重复会"连坐"截断前一个音（2026-09-20）

用户报「有的音断的特别突然，不要这样」。**先用输出包络定位"是哪一类音"，再读库的源码找机制**：

- **★★ 用输出包络 + 分组对照来定位**：在 `Tone.Destination` 上挂只读 analyser，每帧采 RMS，对每个音取它的释放点，量"之后 80ms / 250ms 掉了多少 dB"，然后**按类别分组**（短音 / 长音 / 同音重触发 / 被句尾放掉 / 对照组）。实测一眼看出元凶：同音重触发组 −11.5 dB/250ms，而对照组 −2.8 dB。★ **一定要有对照组**：我第一版差点把"短音组掉 10.4 dB"当成 bug，其实那是钢琴采样自身前 250ms 的自然衰减。
- **★★★ `Tone.Sampler` 的释放语义（读 14.7.58 源码确认）**：`triggerAttack` 每次新建一个 `ToneBufferSource` 并 push 进 `_activeSources[midi]`（同一个音高会堆多个）；而 `triggerRelease(note, t)` 是 `sources.forEach(s => s.stop(t))` **然后清空该音高的列表**。所以**后一个同音的释放点会把前一个还在响的长音一起停掉**。`OneShotSource._stopGain` 确认 `stop()` 走的是 `fadeOut`（= 构造时的 `release`）—— 所以这不是"硬切"，而是"提前 fade"，听感依旧是"音被掐掉"。★ 通用规律：**换乐器/换音色时要查"释放"是逐音的还是按音高/按乐器的**（03 那条讲的是"release 在 attack 时读"，这条讲的是"release 的作用范围"），两者都会让"每个音自己管自己"的假设失效。
- **修法**：同音重复时**先让旧音在新音的起音处退场**（`triggerRelease(pitch, 新音 startAt)` 后再触发新音），并把模型里那个音的 `endsBeat` 收到此刻（协和/在响判断也不该再算它）。钢琴上这正是"重新按下同一个键"。实测该组从 −11.5 → −4.1 dB，与对照组齐平，全曲无硬切。
- **★ 被数据否掉的修法也要留档**：我先实现了"短音把 release 拉长到 1.9×（软着陆）"，实测只从 −10.4 改到 −9.6 dB —— 说明要改的不是包络尾巴；而且它会让 0.125s 的音拖近 3 秒、糊掉"跳进即断开"的句法，已回退。**候选修法要用同一套指标验证，不成立就撤回，别留下来当"顺手改的优化"。**
- 剩下的两处"收掉"是**设计**：短音按自己的时值被 damp（断句）、每句末尾放掉仍在响的音（留白）。⚠️ **后者已在第十一轮取消**（那一放会把横跨乐句末尾的长音掐断，见下）。要知道"哪些突然感是设计、哪些是 bug"，就得先把它们分组量出来。


### 04 第九轮：坍缩"没有在节奏上" = 步长是连续量、而步时刻是累加的（2026-09-20）

用户第三次报同一件事：「还是觉得坍缩没有在节奏上」。**这次先把"离拍点多远"量出来**（离线桩只取 Transport 上排出的步时刻，3 种子 / 195 步）：步间隔取值 **{1, 1.44, 1.59, 1.74, 1.89, 2.4} 拍**（只有 60% 是整拍）、步时刻偏离拍点中位 **0.23 拍 / 最大 0.49 拍**、**90% 的步都偏离**。

- **★★ 连续量驱动时间轴时，必须检查"累积漂移"，不能只看单步间隔**。`(延迟 + 时长) × 0.6` 算出 1.44 / 1.59 拍这类值，单看像"跟着音长呼吸"，但步时刻是 `stepAt += wait` 累加出来的 —— **一个非整数值就把之后每一次坍缩都永久推离网格**（偏差继续累积）。所以"间隔看起来合理"完全不能作为判据，判据要落在**步时刻相对拍网格的偏差**上（第三轮那条"公式类规则要逐项核对"的加强版：这里连间隔都对，错的是累积）。
- **修法**：`waitBeats = max(1 拍, ceil((延迟 + 实际时长) × WAIT_SCALE))` ⇒ 步长只能是 **1 / 2 / 3 拍**。取整后"跟着音长呼吸"变成"这一步等几拍"：长短变化还在（不是等距），而每一次坍缩都踩在拍上。
- **★★ "音乐上的时间结构"（小节 / 乐句 / 和声变换周期）只能数拍，不能数"第几个格子"**。步长一旦不等距，`step % n` 与"每 n 拍"就完全是两件事 —— 第三轮就是在这里被迫把重音降级成"每 4 个格子"的。这一轮一次改回三处：重音 `stepBeat % 4`（小节第 1 拍）、乐句留白 `stepBeat % 16 >= 14`（16 拍 = 4 小节）、和弦每 `CHORD_BEATS = 8` 拍换一次（原来是每 8 步，等于 8–24 拍，和声周期直接散掉）。**改动前先全局搜 `step %`，把所有"把步号当时间用"的地方找齐。**
- **乐句留白是结构标点，长音不许跨过它**：`waitBeats` 被钳到留白窗口起点（`min(desired, 16 − 2 − stepBeat % 16)`），否则一个 3 拍的步会从第 13 拍直接跳到第 16 拍、把留白整段跳过，乐句周期就散了。
- 实测（离线 4 种子整曲）：步间隔只有 {1,2,3} 拍、偏离拍点 **0**、重音落点与小节**逐一对上**（18/18、19/19、17/17、18/18）、起音全在八分网格 {0,0.25,0.5,0.75} 拍、留白拍上音符 **0**、力度第 1 拍 0.68–0.70 vs 弱拍 0.53–0.55、同时最多 2 个音（叠置没丢）、整曲 92–99 拍（120 BPM 46–50s，原来 38–41s）。BPM 扫描 40–240 的**拍域序列 md5 仍全同**。
- ★ 顺带记一条**探针参数错位的教训**：我把记录器当成 `onStep` 传了进去（`collapseLine` 的最后两个参数是 `onStep, onCollapse`），于是"收录到 64 个音"其实是 64 个步号、`plan.startAt` 全 undefined → 相位算成 `null`。**回调位置传错不会报错，只会给你一份看起来合理的假数据** —— 拿到"全曲每个 cell 都发声"这种与历史实测明显不符的结果时，先核对参数顺序，别急着解释音乐。

### 04 第十轮：同音降权管的是"左邻居"而不是"上一个音"（2026-09-20）

用户问「这种算法是把下一步相同的音，权重降低对吧，怎么现在有大量的重复」。**答案是"规则在、但管错了对象"**，这一类问题只能靠"读权重式子 + 量实际发声序列"发现：

- **★★ 权重里的"上一个"必须分清是空间还是时间**。`chooseValue` 里的 `previous = cellAt(row, col-1)` 是**左邻格**（WFC 的横向 tile 语法），而 WFC 的**选格由熵决定**，所以**发声顺序与网格行顺序不是一个序列** —— 那三条"旋律"权重（同音 ×0.48 / 级进 ×1.6 / 跳进 ×0.44）作用在一条**没人听**的序列上，实测一整首只命中 7.6 对。时间上（`noteState.prevMidi`）当时**没有任何同音约束**，实测相邻同音 **27.6%**、最长连击 **7 下**，而 8 个候选里均匀乱抽只有 12.5%。★ 教训：**空间坐标上的"相邻"，在"边坍缩边发声"的练习里不等于音乐上的"相邻"** —— 与"重音不能来自 col""和声不能挂在 row/col 上"是同一条，这是它的第三个面（前两个是重音与和声）。
- **★★ 判据本身要能通过"好旋律"的测试**：我第一版用"最近 3 个音之内是否重复"当指标，而**完美地 A-B-C 轮流在这个指标下是 100% 重复** —— 指标把好旋律判成坏的，用它调参会越调越糟。换成"最近 2 个"之后，均匀乱抽的参考值是 23.4%，A-B-C 是 0%。**给指标找两个极端参照（全随机 / 理想轮换）再决定用它。**
- **分级窗口而不是单点**：只压"与上一个音同音"，真实浏览器里相邻重复已经降到 4.3%，但前 12 个音是 `Ab4 Bb4 Ab4 F4 Ab4 Bb4 G4 F4 Ab4 Bb4 Ab4` —— **隔一个音又回来**，听感仍然是"大量重复"。改成 `PITCH_RECENCY = [0.2, 0.5, 0.75]`（最近 3 个发声的音，按远近降权，3 个以前不管）后：相邻 27.6%→7.5%、2 音内 43.3%→24.7%（= 均匀随机的水平）、最长连击 4.2→2.2、用满 8 个音高。★ 判据要用**"最近 2 个音之内"**，不要用"最近 3 个"。
- **★ 重复要先分清"权重选的"还是"传播逼的"**：记录每一步**选择之前**的候选数量，实测 13.4 次重复**没有一次**来自"候选只剩 1–2 个"，全是在候选 ≥3 时选的 —— 所以在权重层修，而不是去放松 WFC 传播（后者会动到整个算法的身份）。
- **★ 重复少了、和声骨架反而更稳**：强拍和弦音 86.4% → **94.3%**（与第七轮的 95% 齐平），因为强拍不再反复落在同一个和弦音上，而是换到和弦的另一个音。**"降重复"与"锁和弦音"不是对立面** —— 我一开始担心权重会让位给整池经过音，于是先写了个"只在同类里还有别的选择时才降权"的条件，用同一份源码 A/B 后发现它**一次都没改变结果**，按"不留没验证过的复杂度"删掉了。
- **★ 被数据否掉的方案留档**：窗口加到第 4 个音（0.85）→ 2 音内回到 30.5%，无收益；"连击按次数加乘方"（第 3 次同音 = 0.2²）→ 相邻 7.5%→5.0%、最长连击 2.2→1.8，但强拍和弦音 94.3%→89.1%，收益只落在少见的连击 3 下，**已回退**。
- **★ 探针口径**：页面把种子字符串哈希成数字（`hashSeed(text)`，djb2），所以"输入框里填 2024"与"直接给 `collapseLine` 传 2024"是两首不同的曲子。⚠️ **但这里原来的证据是错的**（第十一轮纠正）：当时说"实测前 12 个音完全不同"，真正的原因是探针**根本没把种子设上** —— `exercise-controls.seedValue` **只有 getter**（`s.seedValue = '7'` 是空操作），于是每次运行都是随机种子。要设种子必须写 shadow root 里的 `input` 再派发 `exercise-seed-apply`；而且 **`exercise-seed-apply` 自己就会开始播放**，再补发 `exercise-play` 会让两条坍缩链短暂并存（音符数随机变化、步时刻错位）。
- 改音乐权重必然换掉整首曲子（随机序列相同、判决不同）：所以"改前 95% / 改后 86%"这种跨版本比较是错的，**必须同一份源码只替换那一个常量做 A/B**（本轮 `关` 复现出 27.6% 才确认 A/B 干净）。

### 04 第十一轮：留白不该用"掐掉还在响的音"来实现（2026-09-20）

用户报「如果下一个是空拍，前一个音会被突然截断」。**用调用栈而不是猜测定位**：给 `Tone.Sampler.prototype.triggerRelease` 打桩、抓到每个音的 `triggerAttackRelease` 与每次**外部**释放 + `new Error().stack`，再用状态栏标出每一步的类型 —— 只有"句尾留白"那一步会主动放掉还在响的音（`plan.phraseRest && plan.ringing.length → voice.releaseNotes`）。读**实际加载的** 14.7.58 源码确认那一下有多硬：`triggerAttack` 里 `new ToneBufferSource({ …, fadeOut: this.release })`（=1.5s），`triggerRelease` 是 `sources.forEach(s => s.stop(t))`，`_stopGain` 是 `linearRampTo(0, _fadeOut)` —— 于是**从满音量开始的 1.5s 线性淡出**，而那个音本来还要再响最多 2 拍。实测每个留白窗口 1–4 个音被提前放掉（最多提前 2 拍）。

- **★★ "让留白听得见"和"不要掐断音"是直接冲突的，不要用音频操作去实现音乐决定。** 第二轮当时的理由是"不放掉，长音尾巴会盖过休止，留白听不见"；但钢琴 release 就是 1.5s（3 拍），2 拍留白**必然**被尾巴覆盖 —— 想同时要"真静音"和"不掐音"，只能砍音或者加长留白。正确的取舍是：**留白 = 这两拍不再有新起音**，正在响的音按自己的时值走完、用**自己**的 release 自然衰减进去。第十一轮就是这么改的（顺带删掉只服务于此的 `plan.ringing` 字段）。改完实测：留白步上被放掉的音 **3 → 0**，外部释放只剩同音退场的 2 次且都精确落在音的起音上，**模型逐位没变**（同一颗种子音符、时值、顺序完全相同）—— 所以这是一次纯听感修复。

**这一轮探针踩的三个坑（都很容易再犯）**：

- **★★ 本地页面探针必须带 cache-buster**：`python -m http.server` 只给 `Last-Modified`，Chrome 会用**启发式缓存**（无 `Cache-Control` 时按年龄的 10% 当新鲜期）→ `Page.navigate` 到同一个 URL 可能**根本没重新加载**，我前几次一直在测**改之前**的页面。症状很有迷惑性：改动"没生效"，而且那些释放点在时间上找不到对应的起音（因为它们属于旧代码的留白释放）。发现方式：**在页面里 `fetch(location.href)` 拿源码检查标记字符串**，并给 URL 加 `?cb=Date.now()`。
- **`exercise-controls.seedValue` 只有 getter**（`shared/exercise-controls.js` 里只有 `get seedValue()`）：`s.seedValue = '7'` 是**空操作**，于是每次运行都是随机种子（音符数一直在 42–52 之间跳，我还一度把它解释成"种子哈希"）。要设种子必须写 shadow root 里的 `input` 再派发 `exercise-seed-apply`。★ 这条同时**推翻了第十轮那条结论的证据**（见下）。
- **`exercise-seed-apply` 自己就会开始播放**：再补发一次 `exercise-play` 会让两条坍缩链短暂并存（第一条在被 `schedule()` 清掉前还会跑几拍），表现为步时刻错位、音符数随机。
- 另记一条**没跑通的路**：想在输出链路末端挂只读 analyser 量 RMS —— **悬空分支读到的恒为 0**（分析器必须串在链路里才被浏览器处理），而这次在页面里做的串联对照实验报了 Tone 内部错（`A value with the given key could not be found`），最后改用**源码 + 调用栈**定位。要量包络就得先把抽头跑通，别在半通的抽头上做判断。

### 04 第十二轮：听觉上的间隔 ≠ 步长 —— 拍内延迟把整拍网格压成了十六分（2026-09-20）

用户说「问题不是等 2–3 拍，那种也是正常的，现在是听感上**很多音根本不在拍子上**」。**前几轮量错了量**：坍缩步长早已全是整拍（第九轮修好并复验过），但耳朵听的是**音头**。补量两个量之后一目了然（16 种子 / 757 音）：音头有 **24% 落在十六分位**（+0.25 / +0.75 拍），**实际起音间隔只有 38% 是整拍**（其余是 1.25 / 1.5 / 1.75 / 2.5 拍这类半拍错位），最小间隔 **0.25 拍**。

- **★★ 公式要写全：听觉间隔 = 等待拍数 + (下一格的延迟 − 这一格的延迟)。** 步进是从**拍**推进的（`stepBeat += waitBeats`），音头再加这一格自带的拍内延迟 —— 于是延迟差 −0.5 拍能把"等 1 拍"压成"半拍"，甚至 0.25 拍。**"步长是整拍"完全不能推出"听起来在拍上"**；量化节奏类改动时，指标必须落在**实际起音时刻/间隔**上，而不是调度用的步长（这与第三轮"公式类规则要逐项核对"、第九轮"要量累积漂移"是同一条原则的第三次加码）。
- **★ 这是"拿空间坐标当音乐时间用"的第四例**：拍内延迟由 `(row*2 + col*3) % 4` 派生（0 / 0.125 / 0.25 / 0.375s），而坍缩顺序是熵顺序 → 延迟落在随机时刻。前三例是重音不能来自 `col`、和声不挂 `row/col`、同音降权不能只看左邻格。**凡是要进耳朵的时间量，都得过一遍"它是不是从 row/col 来的"**。
- **修法（用户选 B）**：拍内延迟只留 **0 与 0.5 拍**两档（型名也从描述"拍内第几个位置"的 `1/8 / 1/4 / 3/8` 改成如实描述）。实测：音头 **57%→87%** 在正拍点、**24%→0%** 在十六分位、整拍间隔 **38%→75%**、最小间隔 0.25→0.5 拍；步长仍只有 {1,2,3} 拍、最大离拍 0.000000、留白拍上 0 音、调外音 0 全都没动。★ 顺带确认：`waitBeats = ceil((延迟 + 时值) × 0.6)` 在四档与新两档下结果一致（短音保底 1 拍、2.4 拍都给 2、4 拍都给 3），所以改的**只是音头落点**，不是步法。
- **三个候选方案都实测过，留档**：A 延迟全 0（音头 100% 在拍点、间隔 100% 整拍，但机械）；B 只到八分（采用，87% / 保留八分切分）；C 延迟交给时钟（0/0.5，0.5 只在弱拍 —— 能给"空间坐标当时间用"一个正面替代，但要新增一条按拍位的规则）。**给用户做这类取舍时要带数字**（"87% vs 100% 在拍点"比"要不要保留切分"好判断得多）。
- **★★ 改"拍点"必须连效果链一起检查**：用户随后问「是不是加了音频效果器，怎么感觉有回响」—— 查 git 发现混响 + **半拍 FeedbackDelay**（`wet 0.1 / feedback 0.12`）是 0.2 **首次提交**就有的（不在我的改动里），但它**给每个音在正拍之间加一份副本**，音头对齐之后就成了拍间唯一的能量，于是"回响"才变得明显。已删除该延迟（混响保留）。两条通用教训：① **一个延迟就能把刚对齐的网格重新弄脏** —— 做时间/网格类改动时要把效果链当作"另一条时间轴"来审；② **效果参数如果按"建引擎时的 BPM"算死，就等于把它钉在错误的拍位上**（原 `delayTime:'8n'` 走 Tone 的 `Transport.bpm`、改成 `(60/bpm)/2` 又只在建引擎时求值，播放中改 BPM 会漂成一整拍 / 八分之一拍）。★ 也记一条用户偏好：**没人要求的效果器不要加**，加了要说清动机与参数（本次用户就是先追问"你出于什么考虑加的"）。
- **★ Tone 命名空间的属性是 getter，探针里给它赋值会静默失败**：我两次想用 `Tone.FeedbackDelay = class extends …` / `Tone.Reverb = function …` 统计实例数，结果计数恒为 0 —— 非严格模式下对 getter-only 属性赋值不报错也不生效（`class extends Tone.Limiter` 那次能成，是因为我改的是行为不是替换命名空间？总之**别用"替换 Tone.X"的方式打桩**）。可靠的替代：**静态清点 `new Tone.X` 的出现次数** + 播放中数 `triggerAttackRelease` + 检查控制台。

## 已知的重要实现经验

- Tone.Oscillator、Tone.Noise 等一次性声源 stop 后不要复用；停止后应销毁引擎，下次播放重建。
- 最长和弦为 16 秒，看门狗阈值必须明显大于它；当前为 25 秒。
- 对共享 duck gain 安排 Kick automation 时，Kick 必须按时间升序调度。
- `Tone.getContext()._ticker` 是 Tone.js 私有实现。当前代码为时钟恢复使用它；升级 Tone.js 时优先重新评估这一部分。
- Stop/Regenerate 必须等淡出完成再 dispose，避免突然切断或旧定时任务停止新引擎。
- 低频问题首先检查 Pad、Drone、Bass、Kick sub 的叠加，不要只靠 Limiter 或整体降音量解决。
- 03 Phase Loops 的圆环动画必须与音频触发共享同一套时间状态。Tone.Transport 回调会受 lookAhead 影响提前执行，不能在 Transport 回调里直接推进视觉状态，否则会出现播放头和音符触发对不上的问题。做法：音频预排使用 `scheduledFireAt`；视觉显示使用 `visibleFireAt`；只有在 `Tone.Draw.schedule(..., audioTime)` 对应的实际发声时刻才推进 `visibleFireAt` 和触发视觉高亮。
- 03 的同心圆视觉语义：右侧固定播放头不动，彩色音段顺时针转动；当音段前端到达播放头时，该音触发。不要再加入独立的“当前相位圆点”或“初始相位小刻度”，这些标记容易让音画关系变得含混。
- 03 0.2 的 SVG 绘制层级为：灰色轨道 → 固定播放头 → 彩色音符与白色音名 → 触发轮廓。播放头后的扇形/梯形感应区域已确认无语义并删除，不要恢复。
- 03 0.2 的音符触发轮廓必须与音符 `duration` 同寿命：从音段头部向尾部裁切，透明度和线宽按包络下降，实际绘制一帧透明度 0 后再删除。扩散距离随音长由约一到三个环距变化，向中心时必须在圆心前停止。
- 03 0.2 的 Moodist Texture 目前只保留背景音频和概率调度，不提供测试按钮或对应视觉。淡入淡出统一由下游 Gain 管理，Tone.Player 不再叠加素材级长淡入。

- **收起必须是“滑到宿主背后被挡住”，不能原地淡出**（02 用户第九轮报的 bug：下一次音符变少时有点“突然消失”）：收起也走一次飞行（`mode: 'retreat'`），位移用 `easeOutCubic`、不透明度用 `1 − easeInCubic(t)` —— 前段几乎全亮（看得出在移动），末段迅速淡掉，而末段正好是钻进宿主背后的时刻。★ 两个踩过的细节：动效**不要用 `easeInOutCubic`**（前段太慢，实测换句后 0.15 秒只走了 0.4px，观感像“愣在原地”，改用 `easeOutCubic` 后同样时间走 24px）；在此之前曾按用户要求做过“原地快速淡出 + 不可见后瞬移”，现已被这条新要求取代 —— 需求变过，以最新为准，但两版的原因都留在这里免得来回摇摆。
- **“弹一下”要的是“短促 + 单次小过冲”，而且要和音乐同刻**：02 0.3 上先后被否掉两个极端 —— 欠阻尼弹簧（k=0.012 / 阻尼 0.94）过冲 39% 并在到位后来回弹几下；改成完全单调的 `easeOutQuart` 后，用户反馈“几乎是平移过去”。最终用 `easeOutBack`（`WAKE_BACK = 2.0`，单次过冲约 13%、起步速度约为平均的 5.7 倍、收回后不再有来回），用户参考的手感是 **0.2 那种短促的弹**。时长后来改为跟着音符间隔走（见“弹出/收起要给每个点不同的速度”那条），不再有固定的 `WAKE_FLIGHT_S`。**时机同样重要**：0.2 的弹踩在乐句重拍上，0.3 一开始把重组提前 1.2 秒就开始，感觉对不上；此后试过“占满上一个音到首音的空白”，又因为那段没有新音而显得干（见“结构变化的时长基准”那条），最终定成**与首音同刻开始**。判断曲线是否可用时，除了峰值还要数“峰值后的回升次数”，它必须为 0。
- **连线的“生长”只由“有新点冒出来”触发**（02 用户明确的规则）：一端刚变成乐句点的转移要**朝那个新点**长过去 —— 新点在起点端就从终点端反向长过来（`stroke-dashoffset` 取负值）、在终点端就从起点端长出去（正值）；**两端本来就是乐句点的连线不做生长动画**（直接画满，只是跟着点移动），两段都有的连线完全不动（`setEdgePresence` 必须对目标状态幂等）。**收回必须是“反向生长”，不能是消失或透明度递减**（02 用户第二轮明确要求）：起点端收起就朝终点端退、终点端收起就朝起点端退，**收回全程保持满透明度**，只有几何在缩。
- **结构变化的时长基准要跟"本句内部"的音程走，而且变换必须与首音同刻开始**（02 用户第三轮 + 第十轮反馈）：一开始用固定时长（0.7 秒）→ 用户指出"一条还没长完，另一条已经开始了"；改成"上一个乐句最后音 → 本句首音"的空白当窗口、在首音收尾 → 用户又指出**那段区间按定义没有任何新音，变换跑在空白里、观感很干**（实测 2.2 秒的变换里约 73% 无新音）。最终方案：重组从**首音前 `MORPH_LEAD_S = 0.05` 秒**开始，时长基准取**本句内部第一个音程**（首音 → 第二个音，`clamp(M, MORPH_MIN_S = 0.32, MORPH_MAX_S = 1.6)`），于是密句约 0.6–0.8 秒、常见间隔 1.0–1.5 秒，全程有音乐。附带好处：不再需要跨乐句保存"上一句最后一个音的时刻"这种状态（早期版本必须按**调度时刻**计算它，因为视觉回调可能还没跑到）。⚠️ 教训：当"时长跟音乐关联"实现成"占用上一个空隙"时，很容易把动画放进没有声音的区间 —— 关联的对象应该是**正在发生的音乐**，不是它之前的静默。
- **弹出/收起要给每个点不同的速度，并让连线跟着自己的点走**（02 用户第六轮反馈：“每个点的速度不要完全一样，现在整体都太快了”，以及“点已经到目的地了，但线还没长完”）：飞行时长 = `音符间隔 × WAKE_FLIGHT_SCALE × 该音高自己的倍率`（SCALE 现为 2.0，见下一条），倍率按**黄金比小数**打散在 `0.8~1.25`（`noteToMidi(note) * 0.618… % 1`）；连线的生长/反向生长直接用**它自己那个点**的时长（两端都是新点时取平均），于是“线长满”与“点到位”落在同一帧。★ 打散倍率时**不要用哈希低位**（`hashSeed(note) % 1000`）：音名相近时低位会撞在一起，14 个音高只出 9 个不同倍率、速度差被压扁到 0.75~0.81，等于没打散。
- **连线的明度要直接编码马尔可夫转移概率**（02 用户提出）：`walkNote` 是从当前音的后继数组里等概率挑后继（重复项即权重），所以概率 = 该转移出现次数 ÷ 该起点音的后继总数；明度线性映射 —— 现值为 `EDGE_OPACITY_MIN/MAX = 0.16/0.72`（**元素 `opacity`**）。★ 这两个值是把旧版写在 CSS 里的 `stroke-opacity: .8` 折算进来的结果（0.2×0.8 / 0.9×0.8），屏幕上线的明度一点没变，但箭头现在能跟着线走（原因见下面“箭头的明度”那条）；不要再把明度拆成两处相乘。★ 先试过开方映射，实测效果更差：本素材里既有大量 `p=1` 的确定转移、也有 `p≈0.07` 的偶然转移，开方反而把低概率抬到 0.39、压缩了对比（线性映射下 A 段 0.272–0.72、C 段 0.20–0.72）。验证时要独立重算一遍概率（从 `NOTE_CHAINS` 数出现次数）再和渲染出来的明度比对，并读 `getComputedStyle` 确认真的变了而不是只写了内部字段。
- **让整张图随视口等比缩放，而不是逐个常量乘系数**（02 用户 2026-09：“窄屏下很好，宽屏下四周的空白太大了”）：症状来自半径上的**绝对上限**（`min(380, W*0.36)` / `min(330, H*0.32)`）—— 窗口超过约 1055×1031 后环就不再长大，2560×1440 里只剩 760×660 一圈（横向 30%、纵向 46%）。修法是把内部坐标定义成**设计单位**：`viewBox` 写“设计尺寸 = 窗口尺寸 ÷ scale”，让浏览器把整张 SVG 等比放大，`scale = clamp(sqrt(窗口面积 ÷ 参考面积), 1, 上限)`（02 参考 1100×700、上限 2.5）。**好处**：环、节点、音名字号、描边宽度、箭头（`markerUnits="strokeWidth"` 会自动跟随）、物理冲量全都按同一比例，不可能漏；而**逐个常量乘系数**必然漏掉某个量（节点半径、隐藏半径、宿主偏移、字号、箭头长度、冲量……），一漏就出现“环变大了、点还是 17px”的割裂。★ **下限 1 是关键**：参考尺寸以内的窗口 scale = 1、渲染结果与改造前逐像素一致，用户已经认可的窄屏观感一点没变。半径只按比例算（02：横向 72%、纵向 64%），不要再给它设绝对上限。换视口时先按设计尺寸的变化等比挪点、再 `layoutGraph()` 重算环位，视觉才是连续的（从窗口切到全屏是“整张图放大并重新站位”，不是硬切）。验收要**同时**量两件事：**填充比例**（环的屏幕跨度 ÷ 视口，02 实测恒为 0.68 / 0.63）与**细节比例**（相邻点间距 ÷ 节点半径，02 实测 10–15）—— 只量一处尺寸会漏掉一半问题；而且量屏幕尺寸必须经 `getScreenCTM()` 换算（设计单位 ≠ CSS 像素）。
- **全屏用键盘事件就够**（浏览器只要求“由用户手势触发”，键盘事件算手势）：`f` 键调 `requestFullscreen()` / 已全屏时调 `exitFullscreen()`，并在 `fullscreenchange` 里重算视口（进/出全屏**不一定**派发 `resize`）；焦点在输入框（`INPUT`/`TEXTAREA`/`contenteditable`）里要跳过，否则种子输入框里打不出 f；★★ 但**这个判断必须用 `event.composedPath()`，不能只看 `event.target`** —— 种子输入框在 `exercise-controls` 这个 Web Component 的 **shadow root** 里，而 window 上的监听拿到的是被**重定向**过的 target（`<exercise-controls>` 宿主，tagName 根本不是 INPUT），于是"跳过输入框"形同虚设：02 的 `f` 键就一直有这个 bug（在种子框里打 f 会切全屏），后来加 `s` 键调试时才用探针发现并一起修掉（判据：`composedPath().some(node => node.tagName === 'INPUT' || …)`）。`requestFullscreen()` 的 Promise 要 `catch`，否则被拒绝时控制台留未捕获错误。全屏与“点击画面隐藏 HUD”是两件事，不要合并。
- **箭头要跟着"正在移动的头部"走，方向取该点切线**（02 用户 2026-09："生长/反生长时箭头能否跟随曲线的头部，而不是箭头一直在目的地等着曲线过来；指向要根据曲线计算，一定不能固定或固定成结尾的朝向"）。技术要点：SVG 的 `marker` 只能落在**路径端点**上，所以要让箭头跟着头部，就得为每条边再加一条"承载路径"（02 叫 `.chain-head`）：每帧把它的 `d` 重算成"头部前一小段曲线"（02 取 `HEAD_ARROW_BACK = 12` 用户单位），末端放在头部上、`orient="auto"` 就自动给出**该点的切线** ✔。四个细节：**①折线末端就取在头部那一点**（"箭头底边压在线的端点上"）——**不是把尖端放在头部上**：参考点是底边中点，把尖端对齐头部会让线头从箭头旁边露出来、并在"骑行箭头 → 停在终点的那支"交接时整整跳出一个箭头长度（02 用户报的"线的端点会超出箭头"+"箭头突然往前弹一下"都出自这里）；**②取样点的顺序必须"从后往前排到头部"** —— marker 的朝向取自末端那一小段，写反会正好掉头 180°（02 实测点积 `dotWithTangent = −1`，改回 +1）；**③承载路径的描边要不可见但颜色要对**：用 `stroke-opacity: 0`（marker 的 fill 是 `context-stroke`，实测**不受** `stroke-opacity` 影响，所以描边不显示、箭头照常显示），而 `stroke-width` 必须和线一致（1.1），否则 `markerUnits="strokeWidth"` 会让箭头尺寸对不上；**④一条边同时只显示一支箭头**：颜色还在走时终点那支先不挂（否则就是"在目的地等着"），到位后骑行箭头收起、交给停在终点的那支。方向：行进时沿曲线正向（θ=0），**反向生长时掉头指回起点端（θ=π）** —— 用户肯定过这个转向，但要的是"**慢慢转过去，不要一瞬间转回去**"（02 曾每帧直接取正/反向 = 瞬间 180°，被否；我第二轮又整个删掉转向，也被否）。做法：方向**显式算出** `u = 切线·cosθ + 法线·sinθ`（切线/法线取头部局部值），θ 逐帧爬到 π，转向时长 = 高亮时长 × 0.6（钳制 0.22–0.5 秒），实测 8ms 一帧 `4 → … → 180`、0.36 秒转完。★ 转向是"绕头部"的（底边中点钉在头部），所以整个过程线的端点都在箭头身体里。另外彩色层要用**平头描边**（`stroke-linecap: butt`）：圆头比算出来的端点再多伸 1.2，反向生长时那截会露出来。验证办法：逐帧读承载路径的 `d`，**独立算一遍曲线在该点的切线**再与箭头方向求点积（应恒为 ±1，≈0 就说明算错了），并用**4ms 细步**记录"箭头底边到静止位置的距离"确认交接**线性单调减到 0**（落差一致才算没有弹跳）。
- **连线的出现/消失一律走几何：生长 / 反向生长；透明度只用来表达"明度"这类静态量**（02 用户 2026-09 把这条明确成了规则："所有连接线的出现/消失都要生长/反生长的动态，而不是透明度控制"）。踩过的三处：①`applyPhraseVisual` 对"不再属于本段落"的连线顺手写了 `edge.opacity = 0`，而每帧的 `updateEdgePresence` 又把明度写进 `opacity` → **反向生长那一整段是看不见的**（实测收回途中 presence 0.653、alpha 已经是 0）；②彩色高亮层不管被叠加层的几何，保持满长、最后靠 1.2 秒退色收场 → 画面上是"停在原处慢慢变淡"而不是"退回去"；③高亮**被下一条转移取代**时也用了 `opacity` 退色。规矩：**①退场的元素先按原样把几何收完，alpha 留到"收完那一帧"再归零**（明度只在"它属于当前状态"时更新，退场期间保留上一次的值）；**②叠加层（彩色/高亮/轮廓）的可见区间必须裁到被叠加层的可见区间之内** —— 02 每帧算 `[扫过区间] ∩ [灰线可见区间]` 并用 dash 表示（起点为 0 时沿用旧的 `"L L"` + 正 offset，**与旧实现逐像素等价**；起点 > 0、即灰线从终点端长出来时，用 `"段长 L"` + 负 offset 表示中间一段）；**③"高亮退场"也要反向生长**：揭示区间从全长缩回 0（终点端先退、起点端最后退），时长就取它走过来时的那个时长（不用另外发明一个"退色时长"）。★ 两个坑：dash 区间要按**两套 offset 约定**分别解码（02 的探针一开始只按一种解码，把另一种读成了 `[0,0]`，差点误判）；判定"退场"要看 `presenceTarget`，不能只看 `presence < 1`（生长时也 < 1，那时应当裁区间、而不是当收回）。
  （仍然允许用 `opacity` 的地方：①表达概率明度这种静态量；②节点"滑到宿主背后"时的收尾淡出（用户明确要求"被挡住"的观感）；③停止播放这类全局状态切换。判据是：**这个 alpha 变化是不是在表达"某个东西出现/消失了"** —— 是，就必须换成几何。）
- **换句时每个点都要动，而且"每句不一样"必须有音乐依据、不能用随机数凑**（02 用户第八轮要求"整体位置都有一定的跨度"；2026-09 又进一步要求"不想让每一句的分布完全固定，每次要不一样，但整体逻辑还是要有的 —— 不要随机，完全的随机毫无意义"）。旧做法是每次换句取一个 ±0.1 弧度 / 0.95–1.05 倍的**随机**微扰：可复现，但没有依据，幅度又小到每句几乎一样 —— 已被否掉，`visualRng` 一并删除。现在的两条规则都只用**这一句的音乐**：**A 朝向 = 把本句首音的槽位转到正上方**；**B 半径 = 该音在本句的发声次数**（弹得越多越靠内，本段落在场但本句没用上的留在最外圈）。★ 三条教训：**①A 必须限速**（每句最多转半个槽位）：本素材的乐句首音只有 C3/C4/C5/E4（槽位 1/5/7/11），C4↔C5 差 6 个槽位，一次摆到正上方会让环单帧目标就是 154°、最远那颗点要跑 **720px**（对比原来的 19–39px），限速后每句 ≤ **90.8px**（实测 87.1–90.8、平均 67px）—— 和"箭头掉头要慢慢转"是同一条原则：**转向要有过程**；**②同一段音乐必须画出同一张图**（实测同一形状重算两次偏差 0.000px），所以视觉侧可以完全不用随机流 —— 若将来又要加随机，仍须从种子派生独立流、绝不能动钢琴的 rng；**③半径上的"信息"要被看见**：环位原来带 ±12% 的按 index 抖动，会把"活跃度"这个真信号淹掉，现在只留 ±4%。另外 `layoutGraph()` 仍必须重算**连线弹簧的静止长度**（不重算的话边弹簧会把位移拉回去，实测只剩 16% 偏移）。刚变成乐句点的点用 `easeOutBack`（弹），保持不变的用 `easeInOutCubic`（平滑滑位、不过冲）。★ **这条"不要随机"只约束状态图，不是全局禁随机**：用户 2026-09 后来说得很清楚 —— "**不要随机的原则保留，允许在明确需要使用随机的时候使用**"。判据：这个量**本来就该各不相同**吗？状态图上的位置/半径/时长都该由音乐算出来（用随机就是偷懒），而**环境层回声**（02 的涟漪）要对应的是鸟叫那种忽大忽小忽快忽慢的质感，用确定性的几何反而是错的。三个前提：① 有一个**非随机的外框**（范围由 `targetGain`/`fade`/`pan` 定，随机只在范围里分配）；② 随机流必须**种子派生、可复现**；③ 不能用随机替代"本该跟音乐挂钩"的量。这一条完整写在 [`exercises/02-aisatsana-markov/视觉规则.md`](exercises/02-aisatsana-markov/视觉规则.md) **§15**（含**允许的三个条件**：① 有非随机的外框 —— 范围由声音给、随机只在框内分派；② 种子派生的独立流、结果可复现；③ 这个量"本来就该各不相同"）。
- **不要再加“点必须在首音之前到位”这类约束**（02 用户第七轮明确否掉）：那会把速度逼快（“不然这个限制会导致快”）。飞行时长现在是 间隔 × `WAKE_FLIGHT_SCALE(2.0)` × 该音高倍率，钳制 0.6~2.2 秒、允许延伸到首音之后；实测最密的乐句 600–798ms。若将来又觉得“点和线在发声之后还在动”不协调，应该调 `WAKE_FLIGHT_SCALE` 而不是重新引入硬上限。
- **一个音程要复用给所有与节奏相关的视觉时长**（02 用户第四轮反馈：“音符点亮到暗的间隔也要和乐句间隔关联，而不是每一个音符点都一样”）：`clamp(上一个音到这个音的实际间隔, EDGE_SWEEP_MIN_S = 0.16, EDGE_SWEEP_MAX_S = 1.5)` 同时驱动 ① 彩色行进时长、② 音点从亮到暗的时长（`node.flashDuration`，线性回落到常态色）、③ 箭头亮起的时刻。三者用同一个值，所以天生同步；音密处一闪即暗、留白处余韵长。第一个音没有参照，用 `FIRST_NOTE_INTERVAL_S = 0.5` 兜底（行进与点亮都用它，免得开场第一个音闪成 0.16 秒）。旧实现是每帧固定减 0.012（人人都约 1.4 秒），用户明确指出“不要每个音都一样”。
- 节点位置用弹簧-阻尼求解时，转移边**不能带“绝对理想长度”**：02 0.3 早期版本让边把两端拉到 170–280px，而环间距只有约 130px，结果边把环整个撑开、弹簧平衡点偏移 30px 以上，节点弹出后在 72%~117% 之间来回摆且停不下来。但边**可以**当“铰链”参与动力学 —— 只要把静止长度取成**环上的原始距离**，环就仍是弹簧网的平衡位置，边只负责把运动传给邻居。
- **换句的“弹”必须沿连线传开，而不是整体外扩**（02 用户的原话：看起来像整体向外扩，而不是通过铰链连接那种很有活力的弹）：不要用“整环缩放”做弹力，改成给在场节点一次**切向**冲量（方向按索引交替），位移由连线弹簧（`EDGE_COUPLING`）传给邻居；阻尼要够轻，否则扰动会被立刻吃掉（0.80 太快吃掉、0.92 可用），但再放松就会变成乱抖。验证要量三件事：单点切向位移、邻居位移（证明传导）、以及**全环平均半径的变化**（证明不是外扩）。
- **“振幅不够”时不要只想着加冲量**：02 用户的原话是“速度够、范围不够，像是很短的弹簧，把弹簧放长一点”。离散模拟的结论（阻尼 0.92/帧）：单把弹簧变软 k 减半只值 1.25× 行程；放松阻尼能加行程但方向反转从 3 次涨到 9 次；加冲量则是线性的。最终用“软一档 + 适度加冲量”：`NODE_HOME_SPRING` 0.012→0.009、`EDGE_COUPLING` 0.016→0.012，并把推挤/漂移按同比例降到 900 / 0.038（**静态偏移 = 力 ÷ 弹簧，弹簧变软时这两项必须一起调，否则平衡点远离环位、整张图看起来变松**），冲量 6→8.5，行程 17.2→27.3px，起步速度只涨约 40%。改完要复测“静止时节点离环位”确认没变松（实测 0.4–3.3px）。
- **弹的力度要分成可分辨的两级**（02 用户反馈“应该有两种，现在只有一种”）：换句/段落切换一级（`PHRASE_KICK = 8.5` / `SECTION_KICK = 12.5`，实测峰值 27.3 / 40.1px），单个音符发声一级、要明显更轻（`NOTE_KICK = 1.7`，实测 5.9px）。两级数值太接近时听感上就只有一种弹，换句的重音也就丢了；两级比例定在约 5:1。
- 弹簧的静止长度这类派生量要在**创建时**就初始化：02 0.3 把 `edge.rest` 放在 `layoutGraph()` 里算，而 `layoutGraph()` 在边创建之前就被调用了，于是 `distance - undefined` = NaN，整张图瞬间全部变 NaN（探针里表现为所有位移都是 NaN）。派生量要么在创建处赋值，要么在计算处显式兜底。
- 弹簧常数不要凭感觉定，先用几十行离散模拟（`x'' = -k x - c x'` + 速度阻尼 `v = (v + f) * d`）算一遍峰值与稳定时间，再写进代码并在注释里留下“k / 阻尼 → 过冲比例 / 稳定时间”。02 0.3 的常数就是这样定的。
- 转移边“激活”不要整条瞬间变色（02 用户明确不喜欢），要做成沿曲线行进：同一条曲线加一层彩色覆盖路径，`stroke-dasharray` 设成“全长 全长”、`stroke-dashoffset` 由全长降到 0，颜色就从起点长到终点；灰底边本身不变色。行进时长按**实际音程**算（上一个音到这一个音隔了几秒就走几秒，两头钳制），并由 JS 逐帧写 dashoffset（用 CSS transition 会在中途改 dasharray/几何时被重置）。
- **箭头（marker）的明度只跟元素的 `opacity` 走，跟 `stroke-opacity` 无关**（02 用户 2026-09 报“线都长完了，箭头的三角还有点透明，明明是一条完整的连接”）：标定实测（同一页 5 条路径）`stroke-opacity=.8` + 元素 `opacity=1` → 线 **0.800**、箭头 **1.000**；元素 `opacity=.9` → 线 **0.719**、箭头 **0.900**。而线常常是**两层元素**叠出来的（底边 + 行进层），箭头却只挂在底边上，于是颜色到位后线已经饱和、箭头还停在概率明度上（最暗的那条：线 `(139,92,246)`、箭头 `(40,40,44)`）。两条规矩：**①连线明度只能有一个来源（元素 `opacity`），不要写进 `stroke-opacity`**（02 已把旧的 `.8` 折算进 `EDGE_OPACITY_MIN/MAX`，屏幕上线的明度不变）；**②凡是“叠加出来的线”，箭头必须同样叠两层** —— 给行进层挂一支几何完全相同的箭头。行进层描边更粗，所以那支箭头要用 `markerUnits="userSpaceOnUse"` + 绝对值长度（`markerWidth` = 原宽度 × 描边宽度），否则 `strokeWidth` 单位会把箭头放大（02 实测 2.18 倍）；并且**只在颜色到达终点时才挂上**（marker 永远画在路径末端，dash 揭示不会挪动它）。改后实测：灰态 线 `(39,39,42)` vs 箭头 `(40,40,44)`；最暗转移走彩色时 线 = 箭头 = `(139,92,246)`（差 0）；退色一半时差 0.013。
- **箭头挂法的唯一规则：参考点（`refX`）放在箭头底边的中点**（`refX = 0`，`refY` = 箭头中线）。`refX/refY` 就是“路径末端落在箭头坐标系里的哪个位置”，放在底边中点之后，线尾正好停在箭头**最宽**的那条底边上：既不可能从收窄的锥面里露出来（02 用户第一轮报的“连接线超出了箭头”，那时 `refX = 7`，实测线尾处箭头宽度只有 **1.10**，恰等于线宽 1.1），也不必再靠“把线尾藏进箭头身体里”那种补偿链（02 曾同时改路径末端 `ARROW_TAIL_INSET` 与 `refX` 让两者相抵，已删除 —— 能不用补偿就不用）。箭头位置改用“离目标节点边缘的距离”表达：`ARROW_TIP_GAP = 2.9`、路径末端 = `R + ARROW_TIP_GAP + ARROW_LENGTH`（02 实测底边 28.7px、尖端约 20px，与旧版一致）。另注意：**元素 `opacity` 会把描边与 marker 合成一个透明组**，组内重叠（线尾压在箭头上）不会叠乘变实，所以“箭头比线更实”在同一个 path 内不成立；会叠乘的是**别的元素**。
- **用像素验证“两条元素明度一致”之前，先查采样点旁边有没有别的元素**：02 的 48 条边都汇到少数几个节点，实测另一条连线 `C4|G3`（明度也是 0.72）从采样点旁 **2.9px** 穿过，像素被叠乘成 `1−(1−0.72)² = 0.92` 而不是 0.72，差点被误判成“箭头比线更实”。做法：让探针对每条在场连线采样上百个点，把到采样点的最小距离一起打出来，再下结论。
- 量 SVG 图形尺寸时不要指望栅格化：把 SVG 当 `<img>`（data URL）画进 canvas 时 **marker 不会渲染**（实测只剩连线像素），所以箭头尺寸没法用像素统计验证；可行办法是验证"结构等价"——同一个 path、同一个 marker、同一 `stroke-width`，并断言 `getComputedStyle(path).strokeWidth` 在状态切换前后不变；涉及"路径末端 vs 箭头"这种相对关系时，按 `refX` + 描边宽度把两种浏览器实现（marker 内容按描边缩放 / 不缩放）都算一遍，两种都成立才算修好。另注意无头环境里 CSS 过渡的动画时钟几乎不前进，要读目标值得先临时把 `style.transition` 置为 `none`。
- **SVG 呈现属性会被 CSS 规则覆盖**：JS 用 `setAttribute('opacity', 1)` 点亮的元素，只要样式表里有 `.some-class { opacity: 0 }` 就依然完全不可见。02 0.3 的行进层就这样“属性写着 1、画面全程不显示”，用户直接反馈“彻底没有彩色连线”。规律：凡是被 JS 逐帧驱动的透明度，都写**内联样式**（`el.style.opacity`），并且**不要在 CSS 里声明同名属性**；同理，视觉验证不能只读 `getAttribute`，必须读 `getComputedStyle`，否则会误判为通过。
- **加“深色 / 浅色”主题时：颜色只存一份，而且浅色不是把色阶对调**（02 0.3，2026-09 用户：“准备调整配色，先在 HUD 里加 light/dark 按钮，用当前 icon 库的 icon”）。三条经验：**①单一来源** —— 一个量只能有一处定义。02 后来的做法是**画面颜色集中在 JS 的一个 `PALETTE` 块**里（用户要求“把非激活点 / 音符字 / 连线 / 背景色这些变量和段落色写到一块，我边看边调”）、由 `applyTheme()` 推成 `<html>` 的内联 CSS 变量供 CSS 规则 `var()` 取用，节点颜色因为要逐帧 RGB 插值而直接吃同一份值；页面 chrome 仍在 CSS 变量里。★ 由此得出的硬规矩：**既然值是从 JS 推到内联样式上的，CSS 里就不要再声明同名变量** —— 内联优先级更高，写在 CSS `localStorage` 会抛错），让 `color-scheme` 跟着主题走；默认主题不跟随系统 `prefers-color-scheme`，除非用户要求。**③浅色 ≠ 色阶镜像** —— 第一版按 zinc 色阶深浅对调（500→400、600→300），实测**节点几乎融进底色**（1.34:1，深色是 2.51:1）、连线墨色从 4.02:1 掉到 2.33:1，整张图发虚：反差来自纸与墨的明度差，把墨一起调浅等于两边都丢了。正确做法是**对齐对比度**：墨色（连线与节点描边）两套主题共用同一个灰、由纸提供反差，节点灰度按目标对比度反解（02 浅色 `#b3b3b8` / `#9a9a9e` → 实测 1.90:1 / 2.55:1，对齐深色的 1.86 / 2.51），文字颜色再跟着节点明暗决定（深色白字、浅色 `#18181b`）。验收要**同时量两套主题**的这几组 WCAG 比值 —— 只确认“切过去了”会漏掉“切过去之后糊了没有”。★ 附带发现：某个颜色既当“发光”又当“墨”用时（02 的日志正文直接用段落色），深色下 8.97:1 的颜色到浅色只剩 1.97:1 —— 换底色之前先把所有“带颜色的文字”找出来验一遍。**④分主题的颜色要给“当前值”留迁移路径**：02 换一组色时**按色相最近一一对应**，不要凭感觉指派（02 用户的原话：“当前如果有蓝色，就用这组色值中的蓝色，其它也是一个意思”）：实测原紫/绿/橙/粉到新色的色相距离是 29°/23°/3°/9°，而各自的“次近候选”都远得多（35°/58°/32°/22°），对应关系因此没有歧义；给不出对应物的颜色（02 `nodeIdle`（收起点）与 `nodePresent`（在场点）两个键，用户一眼看出问题 —— “两边 nodeIdle 都没有作用”（收起的点透明度是 0、靠宿主遮住，那个颜色只在过渡途中一闪而过）—— 所以**删掉它**，别留“改了没反应”的键。但紧接着我把用户另一句话（“在激活的点应该是当前乐句颜色啊，为什么也有单独的配色”）读成了“平时也该带一点段落色”，加了 `nodeTint` 去混合，结果**整圈点都变成段落色**，用户直接指出“你搞错了，前面的结果是视觉上是对的，问题是代码没跟上……现在全部都成乐句颜色了”。★ 教训：用户说“X 应该是 Y”时，先分清他是在说**渲染结果不对**还是在说**代码结构没表达出这个关系** —— 这里他要的是后者：`nodePresent` 那个键让“被激活时的颜色”看起来是另配的，而它本该**由段落色算出来**。正确的模型是两个状态两种来源：平时 = `nodeBase`（点**本来的颜色**，不随段落变），刚发声 = `mix(nodeBase, 段落色, flash)`（**跟随乐句颜色**，flash=1 就是纯段落色）。**不要再把“平时的颜色”往段落色上染**；改动渲染结果之前先问清楚，或者先只动结构、把观感留原样。
连带的两个结论仍然成立：**描边不要就不要留变量**（用户“音符点不要描边”，于是 `--graph-node-stroke` 与图例上的描边一起删掉）；**压在彩色上的文字颜色应该算出来而不是配出来** —— 但“算出来”不等于“不给调”，用户随后要求“音符点的字色也要在这里”，最终的形态是**一个明确的 `labelInk`**（见下面那条：两个候选的写法已经被证伪）。**⑦声明顺序**：把一个“调用点很早的函数”接到新依赖上之前，先确认那个依赖声明得够早 —— 02 这轮就是把音名墨色接进 `applyTheme()`（它在脚本中段就被调用一次）而 `mixRgb` 声明在后面，直接 `Cannot access 'mixRgb' before initialization`，整页视觉全不建起来（探针里表现为 `ensurePhraseGraph is not defined`，因为脚本中断后所有 `const` 都没执行）。
- **方向信息不要靠“给每条边一个箭头”来堆**（02 0.3，2026-09 用户：“去掉常规连线的箭头，显得很乱，能否用渐灰度代替箭头的方向。激活线的箭头还保持啊”）。几十条边各带一个三角时，画面上全是噪声；但**箭头本身是好的**——它是“这条线正在被走到”的强调，所以正确的切分是：**常规连线不挂箭头，方向由沿线灰度渐变表达；箭头只留给激活的连线**（骑行箭头 + 停在终点的那支）。三条经验：**①SVG 的 `linearGradient` 只能沿直线插值**，所以“沿曲线渐变”只能拿**弦**当轴（起点端 → 终点端），两端用 `stop-opacity` 拉出浓度差；线是弯的也不影响读方向。这样“方向”和“概率明度”正好是两个独立通道（`stop-opacity` vs 元素 `opacity`），互不干扰。**②渐变必须与路径共用同一份几何**（02 把它收进 `edgeGeometry()`，同时返回 `d` 与轴，每帧一起更新）—— 分开算就会错开。**③自环会让渐变整条不渲染**：起终点重合时 `x1,y1 == x2,y2`，按规范该元素**不被绘制**，于是那条线直接消失（02 的 48 条边里正好有 1 条 `C3|C3`，是对着数据查出来的，不是猜的）。另外 `stop-color` **不能**写 `currentColor` / `context-stroke`（那只在 marker 里有效），所以墨色得由 JS 从调色板写进 stop。★ 顺带一条**删代码的判据**：底边一旦没有箭头，“画满后给底边换色”（`.active`）就失去了唯一可见效果 —— 因为底边永远被更宽的彩色层完整盖住；这种“只剩内部状态、画面上无差别”的机制要跟着一起删，否则下一个人会以为它在起作用。

`options.onStart(texture, time)`，不参与任何增益/调度计算 → 传不传都不影响声音），**"只有 birds 才画"这条判断留在视觉侧**；通知必须走 `Tone.Draw.schedule(..., time)`（预排回调受 lookAhead 影响会提前跑，只有 Draw 到达那一刻才是听到声音的时刻）。**③"大小跟声音关联"要有依据**：02 用该层的 教训：**由音乐参数直接算出的"位置"很容易把画面锁死在一个区域**，而"偏置/倾向"既保住了那条关系、又让画面用得上整块画布），并且把这些依据写进注释；若要做**逐时刻真实响度**，得给音频链加一个 AnalyserNode 分接 —— 那属于"碰音频"，要先问用户。**④第一版的"触发"和"配色"几乎一定会被追改**：用户看完第一版后追加了两条 —— "不要只在开始的时候，在 birds 发声的过程时不时出现"、"要配色，不要单色"。所以：**触发要覆盖整段发声窗口**（02 的做法：开场立刻一发，之后每隔 `fade × 0.9`（钳 3–6 秒、叠 ±22% 种子抖动）续排一发，排到 `duration + fade` 这个"还听得到"的窗里为止，并保证每发至少一半扩张落在窗内；实测 12s 的鸟叫 4 发、25s 的 7 发），后续几发同样用 `Tone.Draw.schedule(…, time + offset)` 排**在音频时刻上**（停止时 `Tone.Draw.cancel(0)` 一起取消）—— 通知回调因此要把**这一响的实际时长**也带上（`onStart(texture, time, duration)`）。**"配色"要从基准色算出来**，不是换成"另一组固定色"：02 用 `shiftHue()`（RGB→HSL→转色相→RGB）把本段落色**给每个元素各取一份**色相（`hueBase ± 42°`），每发再整体偏 ±18°，于是一发里每根线的颜色都不一样，而且**换段/换主题时整组跟着走**（固定色值一换主题就和画面脱节）。**⑤"砍元素数量"是最容易砍错的一刀：要按"哪个动作制造了那个观感"来留，不能按数量多少来砍**（同一件事的第三轮）。02 第一版把参考砍到 9 个元素并沾沾自喜，用户看完直接说 **"太大了，形态也不好，完全没抓住参考中好的地方，需要那种旋转游走的线，现在的特别呆，每一个都一摸一样"** —— 复盘参考的 82 个对象才看清比例：**20 个"公转中游走"的拖尾线（Orb）是主体**、50 颗星点次之、**涟漪圈只有 2 个（它只是锚）**，而第一版恰好留了锚、把主角当噪声删了，还自己发明了 6 根 60° 等分的放射线（参考里根本没有）→ 同心圆不旋转不游走 = "呆"，几何完全对称 + 逐元素同参 = "一摸一样"。★ 所以读参考源码时要连**每个类的 `move()`** 一起读：那个 sketch 的全部秘密就是 `Orb` 的三行 —— `ang += angStep`（**自转**）、`x += xStep; y += yStep`（**中心游走**）、`pos.push(…); if (len > 10) splice(0,1)`（**只留最近 10 个采样点画成折线**，所以画出的是"一小段扫过的弧"而**不是圆**）。★★ 顺带一个好用的技巧：**逐帧累加式（frame-based integration）的运动，只要那几项都是线性的，就等价于解析式** —— `pos(τ) = 起点 + 速度·τ + R·min(1, τ/T)·(cos, sin)(ang₀ + ω·τ)`。写成解析式有两个好处：① **与帧率无关**（原版按帧累加，120Hz 屏上同一条拖尾只有一半长）；② 不用保存逐帧状态，仍从 `startedAt` 一次算出来，保住"同一个输入必然同一帧画面"。验收方式是**独立重算一遍这个解析式**再和 DOM 上的点比（02 实测差 0.040px），再用"1 大步 vs 30 小步"比对 `points` 是否逐位相同。**⑥"形态的丰富度"本身可能就是被调的对象**：用户说"每一个都一摸一样"时，不要用"固定下来才方便对比"来反驳自己 —— 02 的调试入口第一版就是那么做的（把调试发做成完全确定），结果正好撞在用户的抱怨上。正确做法是**两者兼顾**：每次触发换一条新流（这样每下都不同），而那条流由**触发序号**派生（这样"第 N 下"仍可复现、仍可与改动前后对比，而且不消耗演出那条流）。**⑦"每个元素各取参数"并不等于"每发都不一样" —— 结构性的量也必须各抽**（第四轮）：用户下一句反馈是 **"好了非常多，但是中间两个固定的同心圆还是很呆，不一定永远有……还是太大了，包括生命值也一摸一样，这个就是想从观感上和鸟叫适配，有大有小，有快有慢"**。逐项对上：**"固定的同心圆"** = 两圈的**半径比写死**（1 : 0.62）、**圆心都是爆点**、扩张**共用同一个 `grow`** —— 参数是随机了，**结构没随机**，所以每一发看上去仍是同一发；现在改成 **0/1/2 圈按权重抽**（"不一定永远有"）+ 每圈自己的圆心偏移、半径、起始时刻、寿命（实测同一发里两圈半径比在 0.72/0.99/1.00/1.24 之间，旧版恒 1.62）。**"生命值也一摸一样"** = 所有元素的寿命都以同一个 `grow` 为中心、只在 ±15%~±30% 内浮动；现在各自从宽区间抽（线 0.35–1.8×、圈 0.45–1.7×、痕 0.3–1.6×，实测线寿命 0.88–4.29 秒）。**"还是太大了"** 则只是把**基准尺度**再降一档（每轮只动这一个基准，其余全是它的倍数，所以游走的手感比例不变；验收量"整发墨迹的峰值"：43/58/78px = 视口高的 6.1%/8.3%/11.1%，上一版恒定 85px = 12%）。★ 另外两条实现经验：**①要"有大有小"光有随机不够，还得看分布形状** —— `rng()` 是均匀的，看上去仍"每个都差不多"；`rng() × rng()`（均值约 0.25）把小端拉长，才有"小的多、偶尔一声大"的层次。**②"有快有慢"不要另给一个"速度上限"，要用"一生走多远 ÷ 寿命"** —— 前者的长寿命 × 高速度会让一根线跑到 400px 以外（整发失控地大），后者天然给总伸展设了上限，而且"同样远的行程、寿命短的就走得快"正好就是"有快有慢"。**⑧"贴近真实声音的随机感"往往要动的是**时间结构**，不只是形状**（第五轮）：用户接着要求 **"每一发的线条数量也要不一样。允许同时发射几个，而不是明显一个接一个的出现，这也是为了贴近鸟鸣的随机感"**。两处对应：**① 一发内部别"一个个冒出来"** —— 参考是 `addObjs()` **一次性创建全部对象**（20+50+2+10 同一帧出生，个体差异全来自各自的随机寿命），所以把各元素起始时刻的抖动从 0.5–0.8 秒收到 0.12–0.25 秒（实测一发里最后一个元素最晚 0.244s 启动）；**② 击发要能成簇** —— 排一串"等距单发"永远是队列感，改成"一次击发有 55% 概率是 2–4 发"（成员在 1.1 秒内散开、位置各不相同、寿命 1–4 秒所以必然同时可见；实测 12 段鸟叫的"同时在场"峰值几乎都是 **4 发**，相邻间隔 0.04–4.64 秒，而旧版是 4.5 秒等距）。★ 两个配套细节，缺一个就白做：**簇的成员位置必须各不相同**（`pan` 只当锚点 + 横向抖动 `BURST_X_JITTER`，否则几发叠在一个点上，看着仍是"一发"而不是"几发"）；**整段的击发时刻要先算完再排**（用一个 `offsets` 数组，否则排到一半被条件打断、簇会残缺）。
- **调试入口要与被调试对象"同参"，而且用户输入不能消耗种子流**（02 0.4，2026-09 用户："增加一个调试，鼠标点击的时候就在点击来一发，不然还得专门等着"）。**触发类视觉调起来要干等**（02 的涟漪只跟 birds 走，而 birds 每 55–115 秒才出现一次），所以一个手动注入口是必要的。三条规矩：**①同参** —— 调试起爆取的就是真鸟那一份配置（`MOODIST_TEXTURES.find(t => t.name === 'birds')`），**不是另写一组"调试用的数"**：一旦有两套参数，你在调试入口上调好的东西就不是真鸟叫看到的那一发，这个入口反而有害。**②落点别自己发明一套** —— 用户后来把触发从"鼠标点击"改成了 **`s` 键**（原话："测试发射保留吧，但不是鼠标点击，改成 s 键，**位置按照已有的算法计算**"），于是调试发与真鸟叫走**同一个** `spawnBurst(texture, rng)`、落点用同一套安全区算法 —— 调试看到的就是真鸟叫会看到的那一发（`at` 参数与那套鼠标坐标换算随之删掉，不留没人用的分支）。★ 顺带一条仍然有效的通用经验：**只要真的要用鼠标坐标，就必须过 `getScreenCTM()` 的逆变换** —— `clientX/clientY` 是 CSS 像素，而本项目的 viewBox 是"窗口尺寸 ÷ scale"，`scale > 1` 时两者不相等（02 实测 1400×900 → `scale 1.2792`，忘了过 CTM 时 `fx` 会算成 0.639 而不是 0.75），验证时要**故意挑一个 scale > 1 的视口**，1:1 的视口里这个 bug 是隐形的。**③触发不消耗演出那条流，但自身要有变化** —— 每按一下就把序号 +1，用 `makeRng(f(序号))` 派生一条**独立**流传进 `spawnBurst(texture, rng)`：于是①每下形态都不同（用户后来正是抱怨"每一个都一摸一样"）；②"第 N 下"仍可复现（要对比改动就按同样几下、看第同样的那一下）；③演出那条 `burstRng` 一点没动，所以"按与不按，后面真鸟叫那几发逐位相同"（实测同一颗种子下 `A1===C1`、`A2===C2` 全 true）。★ 教训：我第一版把调试发做成**完全固定**并写了理由"方便改一个常量再点一下做对比"，结果正好撞在用户的抱怨上 —— **丰富度本身可能就是被调的对象**，把它固定下来等于把要调的东西拿掉了；"可对比"和"有变化"可以同时满足（按序号派生流），不要二选一。这与"视觉侧不消耗 `textureRng`"是同一条原则的另一面：**调试行为不该改变被调试对象**。★ 两条工程细节：**①触发方式要让开已经被占用的交互** —— 原来是鼠标点击，可点击早被"隐藏 / 显示 HUD"占了（点一下既切界面又炸一发，容易误触），改用 `s` 键后与 `f` 全屏共用一套键盘约定（带修饰键放过、输入框里跳过、`preventDefault`），验收要专门测"在种子框里打这个字母还能不能打出来"；**②调试监听要与被调试功能解耦** —— 别把它并进现有的 click / keydown handler，各自独立才能单独删掉（删调试入口时不会连带删掉界面显隐）。
- **"新加的东西没有副作用"要用两次独立运行对照来证明，不能只测一次**（02 0.4 的涟漪）：涟漪不参与节点/连线力学，但如果只在前跑一遍、后跑一遍去比"节点坐标 hash"，图自己本来就在呼吸漂移，hash 一定会变 —— 于是你会误判成"有副作用"。正确做法：**同一确定性序列跑两次独立加载**（同样的假时钟步长、同样在某一帧起爆），一次带新功能一次不带，两次的 hash 必须**逐位相同**；顺带还能证明**确定性**（两次带功能的运行，随机量完全一致）。★ 另一个坑：无头 Chrome 加 `--virtual-time-budget` 时**`performance.now` 与 `Date.now` 都被虚拟时钟接管**，"毫秒级帧耗时"根本量不出来（会得到 0ms 或假值）；要量开销就改量**确定性的客观量**，比如用 MutationObserver 数"每帧 DOM 改动条数"（02 实测：涟漪层 **37.0–61.6 条/帧**，按一发 12–32 个元素而定，整张图稳态 378–380 条/帧 → **单发时** +10%~16%；成簇时 4 发同时在场 → 约 4 倍，这是上限、只在鸟叫的簇里短暂出现）。★ 但**必须用 `mo.takeRecords()` 取值**：MutationObserver 的回调是微任务，在被测的同步循环里根本不会被派发，直接读计数会得到 **0** —— 这一轮就踩了，第一版读数 0.0 差点被当成"零开销"报出去。
- **“派生自主题色的历史记录”必须能重着色**（02 0.3，2026-09 用户："打印的乐句颜色没跟上吧"）：日志每行按它所属段落的颜色着色，而段落色是分主题的 —— 旧实现把**那一刻算出的颜色字符串**存进数组（`log(msg, sectionColors()[section])`），于是切主题后老行永远留在旧主题的配色里；这类“把颜色烤进 DOM/数组”的写法在主题系统里都是定时炸弹。修法：存**语义**（段落号）而不是结果（颜色），并提供一个 `repaintLog()` 在切主题时重新着色；逐行插值（每行有自己的段落），不能复用“只插当前段落色”的那个 tween。规律：**凡是历史记录 / 缓存下来的视觉量，都要问一句“主题换了它跟不跟”** —— 点、连线、图例、日志这四处都要各查一遍，漏一个就是“只有背景变”的半个 bug。
- **“整组状态切换”的最后一句不能裸奔：引用了不存在的顶层变量 → 静默半切换**（02 0.3，2026-09 用户报“切换 light/dark 只有背景变，其它颜色没有跟着变化”）。根因：主题按钮的 handler 最后一句是 `tweenSectionColor(sectionColors()[currentSection])`，而 **`currentSection` 在顶层根本不存在** —— 那两处 `let currentSection` 分别在段落链工厂与 `activateEngine` 内部（我读代码时以为它是顶层状态，探针里又一直直接调 `applyPhraseVisual`、从没走过按钮那条路，所以两个方向都没发现）。于是点击时抛 `ReferenceError`：`applyTheme()` 已经跑完（背景、面板、点、连线全换了），只剩**最后一步**没做 —— 段落色停在旧主题上，而它管着刚发声的点、彩色连线、图例彩点与日志文字。三条教训：**①** 一个函数里“改一组状态”的语句是**同生共死**的，最后一句失败 = 半切换；要么包 `try` + 明确报警，要么先算好再改。**②** 用 `let` 声明的“当前状态”很容易踩这个坑（同名变量在不同函数作用域里各自存在，顶层那个可能压根没有）—— 引用前先 grep 一眼它的声明位置与缩进，**不要凭印象**。**③验收要专门盯“最不显眼的那类颜色”**：段落色只在换段或发声时才明显，我之前的主题验证全是直接调视觉函数、绕过了按钮，于是“切换路径”本身没测过；现在补了按钮路径的探针（点一下 → 读背景/面板/点/音名/段落色/图例/渐变），这才是用户真正走的那条路。
- **调色板的键名必须说清“它是什么”**（同一个 bug 报告里的第二件事）：02 的音名字色我先做成 `labelInkLight` / `labelInkDark` 两个候选 + 自动挑对比度高的那个，本意是“浅色墨 / 深色墨”，用户却读成“浅色主题的字色 / 深色主题的字色”，于是两边各填一组同明度的值 —— 两套主题里音名都糊在点上（实测深色 `#18181b` 压 `#414149` = 1.8:1、浅色 `#ffffff` 压 `#C2C2C2` = 1.6:1）。改成**一个明确的 `labelInk`**：对比度低于 3:1 时退回白/深墨并**在控制台点名**（既不会糊，也不静默替用户决定）。规律：给用户手调的键，宁可少而直白；需要“自动选择”时，把两个候选的**用途**写进名字或注释里，否则用户会按自己的理解填错。

- **"总音量"要真的存在：增益与限幅必须在同一条母带链上，而且限幅是最后一级**（02 0.4，2026-09 用户："总音量有什么控制吗，怎么感觉音量还是偏小"）。当时的情况很典型：钢琴自己带一个 `Limiter(-1)` 再直连 `Tone.Destination`，环境层连限幅都没有 —— 于是"整体调响"没有旋钮可拧，只能分别去改钢琴 `volume` 和各层 `targetGain`，而且一旦推过 −1 dB 就**削顶**（DAC 硬切）。修法：把两路都汇到 `钢琴 + 环境层 → masterGain → Limiter(-1) → Destination`，总音量只剩一个常量（dB）。三条经验：**①限幅只能有"一个天花板"，而且必须在链末** —— 把限幅放在某一路自己的链上（原来的钢琴），另一路就完全没有保护，而且后面的总增益可以在限幅之后再把信号推过头；**②挪走限幅时别忘了 dispose 列表**（原来 `limiter` 挂在钢琴的 `fxNodes` 里，现在归母带节点，两处都要改，否则要么重复 dispose、要么泄漏）；**③"某一部分更响" ≠ "整体更响"** —— 前者改该路自己的增益（钢琴 `volume` dB、环境层 `targetGain` 线性 0–1，`0.1` 就是 −20 dB，所以环境层天生很轻），后者才用母带那个常量；往上推超过约 +12 dB 得到的多半是压缩而不是更响，那时该回头调各路的相对平衡。★ 附带一条无头验证的边界：**音频链在无头环境里跑不完**（`activateEngine` 会卡在 `Tone.start()` / `Reverb.generate()` 这类依赖真实 AudioContext/OfflineAudioContext 的 await 上，即使把采样与音效都换成假对象也一样），所以"接线对不对"只能靠**静态核对**（数一数 `new Tone.Limiter` 有几处、谁 `.connect(Tone.Destination)`、两路各接到哪），响度只能靠耳朵 —— 别为了"验一下"去写跑不通的探针。 ★★ 2026-09 更正：上面这条已经不成立 —— 加 `--autoplay-policy=no-user-gesture-required` 后，无头 Chrome 里的 `activateEngine` 只需 **4.3 秒** 就能跑完（见下面那条）；卡住的根因是没有用户手势时 AudioContext 保持 suspended。
- **"跟声音关联"要量对时间尺度，而且要选"离线包络 + 预排"而不是实时读响度**（ 02 0.4，2026-09 用户："能否让发射和 birds 音量关联，音量大的时候相对多，小的时候相对少"，紧接着又说 **"判断音量不是判断某一刻，而是一段，不要某一刻音量大就突然发好多"**）。做法与四条约束：**① 量一段**（素材能量先做 2.5 秒滑动平均；0.1 秒一格只是**测量分辨率**不是驱动窗）；**② 映射有界**（密度 0.5–2 倍，且以该层自己的**中位数**为参照，所以是"比平时响"而不是绝对音量）；**③ 间隔有硬下限**（2.2 秒，这样"绝不会突然炸一片"可以被**机器证否**：200 段模拟、违例 0）；**④ 同时性只由既有的"簇"负责**（响度只调节奏，绝不碰簇的概率与成员数 —— 否则"响一下炸一片"立刻回来）。为什么用**离线包络**：① 实时读响度（AnalyserNode）会把"同一颗种子 → 同一场演出"破掉（每帧读数取决于 rAF 节奏），而且**每一次都会把瞬时峰值变成一簇发射**；② 包络离线算一次很便宜（实测 115 秒素材、0.1 秒一格共 1151 格只要 **6.2ms**）；③ 全部击发时刻仍然用 `Tone.Draw.schedule(…, time + at)` **预排在音频时刻上**，视觉与声音仍然同源。★ **把规则提成纯函数**（`planBurstOffsets(texture, duration, startOffset, rng) → { firings, offsets }`）是关键：入口只剩"排到音频时刻上"一件事，而验收可以**不开浏览器**就量"最小间隔 / 每段发数 / 最坏并发"（`firings` 与 `offsets` 分开返回，是为了能区分"击发"与"簇成员"—— 不分开的话旧的"相邻两发 0.04 秒"会和新的"击发之间 ≥ 2.2 秒"看起来矛盾）。
- **素材的"播放起点"是一个容易被忽略的隐藏常量**（同上）：`Tone.Player.start(time)` 不给 `offset` 时，**loop 模式下取 `loopStart`（默认 0）** —— 于是 115 秒的素材、窗口只有 17–30 秒时，**每一次听到的都是素材开头那一截**，响度曲线逐次相同（可视化量若跟素材内容挂钩，就会变成"每一次都一模一样"）。★ 验证方法很快：在页面里 `Tone.Player.prototype._start.toString()` 直接读**真正在跑的那份代码**（比翻文档/源码快，也不会认错版本）：里面就是 `e = this._loop ? defaultArg(e, this._loopStart) : defaultArg(e, 0)`。★ 改起点时：起点上限取 `素材时长 − 这一段的窗口`（**永不环绕**，否则查包络会在环绕处跳一下）；并且用**又一条独立流**（`startRng`）而不是原来那条 `textureRng` —— 这样"哪一层什么时候出现、出现多久"的既有序列**逐位不变**，改动面被限制在"从素材哪里开始"这一处。
- **性能要量"边际成本曲线"，不是只量一个总数**（同上）：同时在场 0/1/2/4/8/12 发时，DOM 改动 **0 / 67.0 / 144.8 / 274.9 / 536.9 / 804.2 条/帧**、主线程 **0 / 0.113 / 0.180 / 0.303 / 0.662 / 1.132 ms/帧**（每帧强制 style+layout：0.005/0.070/0.130/0.255/0.413/0.607 ms）→ 这类"逐帧改 SVG 属性"的成本近似**线性**（约 **0.06–0.09 ms/帧/发**），12 发也只占约 6% 帧预算 —— 所以"能不能加"的答案是能，但**要给上限**。★ 安全阀的取值要**大于实测最坏值**（实测最坏并发 9 → 上限定 10）：这样它**平时不生效**（不会偷偷吞掉你期望的那一发），只在异常时兜底；而且超限时要**让调试入口说明原因**（`spawnBurst` 返回 false → 控制台打"已达并发上限"），否则"按了没反应"看起来像 bug。
- **新增的数值包装层要有"缺数据兜底"，而且最好用现成的调试入口顺便验一下**（同上）：密度计算依赖 `texture.energy`，而调试按键取的是 `MOODIST_TEXTURES` 里的**原始配置**（没有 `energy`）—— 于是那条路径自然成了"缺数据"的反例：实测 `burstDensityAt` 恒返回 1、`normalise` 恒为 1，**节奏退回改动前的固定值**（不崩不乱）。规律：凡是"从外部拿一份数据才能算"的新功能，都要有一条**退化到旧行为**的路。
- **"绝不会突然 X"这类要求要变成可测的不变量**（同上）：用户要的不是"我保证"，而是"这件事不成立"。把它写成数量关系（击发间隔 ≥ 2.2 秒）并在 200 段模拟里统计**违例数 = 0**，比任何描述都硬。★ 同时要**把"例外的那个量"单独命名**（这里是"簇内成员间隔 ≤ 1.1 秒"），否则新旧两组数字会看起来互相矛盾（"0.04 秒"与"≥ 2.2 秒"）。
- **"某个功能好像没做"要先查"静默失败"，别先怀疑调度**（02 0.4，2026-09 用户："听了好久都没有鸟叫，也没有相应的触发了"）。三步把范围压死，**三步都不需要听**：① **把调度逻辑复刻成离散事件模拟**（环境层的门是纯时间逻辑，与音频无关）—— 实测 birds 首次出现中位 **1.6 分钟**、之后约 **3 分钟一次**、30 分钟中位 **7 次**、"前 10 分钟没出现"只占 **4.4%** → **排程不可能解释"好久都没有"**；② 探针直接调 `createMoodistTextures` 看素材能否加载（实测 6/6、2.5 秒）；③ **端到端跑用户那条真实路径**。结论：链路是通的，真正的毛病是**两个静默**：**(a) 某一层素材加载失败/超时（12 秒、不重试）只往控制台打一行 warning，那一层就整场缺席**，画面上看不出来；**(b) 环境层有没有开始发声，画面上同样没有任何痕迹** —— 而"没加载上"和"加载上了但被钢琴盖住"在画面上长得一模一样。修法：超时放宽 + **自动重试（3 次尝试、退避、每次换全新节点）** + 通过 `options.onNotice` / `onStart` 把"就绪 / 最终失败 / 每次真的开始发声"写进 **HUD 里的一行状态**。 ★★ **但不要写进画面上的文本**（初版我把它写进了画面上的日志，用户看到后要求："环境层的信息不要出现在页面的文本中，可以放在 hud 中"）。判据：**画面上的文本只放作品内容**（这里是马尔可夫链的行走），而加载结果 / 运行状态 / 调试信息这类**系统状态**属于 HUD（且跟 HUD 一起隐藏）。同样的道理也适用于页面正文里的教学说明：设备/网络层面的排障信息不要堆在作品说明里，详细理由写在规范与 README。★ 顺带一条：**"新包装层"必须包 `try`** —— 在 `onload` 里抛出去会让 `loaded.push` 不执行，那一层永远不出声（"静默丢层"最难查）。
- **调试入口要覆盖"音频侧"，而且要让两条路径共用同一个实现**（同上）：`s` 键（`spawnBurst`）只验视觉，"能不能听到"它验不了；所以加 `b` 键 → `playNow('birds', rng)`。★ 关键工程手法：把"让某一层真的开始发声"抽成**唯一一个函数**（`startTextureEvent(texture, time, duration, startOffset)`，参数里**不含随机、不含门禁**），排程器通过门禁后调它、调试入口也调它 —— 于是两边天然同参（增益包络、`start(time, offset)`、`onStart` 通知、素材起点规则全一致），而且改一处不会漏掉另一处。参数里不放随机还有第二个好处：**排程器那条随机流的消耗顺序不会因为这次重构而改变**（改了顺序 = 偷偷改变整场演出）。调试入口照常设 `activeUntil`（门禁状态与真实播放一致），并用**按按键序号派生**的独立流抽参数（按与不按，之后真鸟叫的序列逐位相同）。
- **无头环境里音频链是能跑完的 —— 前提是给 Chrome 加 `--autoplay-policy=no-user-gesture-required`**（2026-09 更正下面那条"音频链在无头环境里跑不完"的旧结论）。以前 `activateEngine` 会卡住，根因是**没有用户手势时 AudioContext 停在 suspended**，`Tone.start()` / 依赖上下文的 await 永远不 resolve —— 不是无头环境本身的限制。加上这个开关后实测：`window.exercise.activate(seed)` **4.3 秒**跑完（含 50MB 钢琴采样 + 6 层环境音），`Tone.Transport` 正常推进、`Tone.Draw` 正常回调、`player.start()` 正常、涟漪正常出现。★ 于是"音频 + 视觉"的**整条链路**都可以在无头环境里端到端验收（不必再靠静态核对），但**响度依然只能靠耳朵** —— 无头能证明"播了"，证明不了"听得到"。
- **让"文本/列表"承载时间信息时，时间要取事件自己的时间轴，不要取"它什么时候被画出来"**（02 0.4，2026-09 用户："页面中的乐句文本，文本间的间隔就是演奏的间隔，而不是现在这样完全均匀的"）。画面那片日志一句一行、每行固定占一个行高，于是**不管两句之间隔了多久都看着等距**；而每句真正开始发声的时刻本来就是动的（句内第一个音落在第几步、以及演奏版本的 `late` 偏移都会变）。改法：把相邻两行的垂直间距做成 **∝ 两次演奏的真实时间差**，时间取该句首音的**音频时刻**（`Tone.Draw` 的**帧到达**时刻会被帧率与后台节流影响 —— 用它量出来的间隔是噪声，不是信号）。★ 三条实现细节：**① 比例映射要先把"名义间隔"对齐到原来的尺寸**（这里名义间隔 = 一句 9.6 秒 ≙ 1.5 个行高），再夹在 `[原尺寸, 3×原尺寸]` —— 下限保证文字不重叠、上限避免一次长静默吃掉整屏；**② 间距写成 `padding-top` 而不是 `margin-top`**：推动容器那一步用的是 `getBoundingClientRect().height`，它**含 padding 不含 margin**，用 margin 会少推一点、整片错位；**③ 验收要量"排序一致性"**（间隔最大的那行是否真的间距最大），只量"间距有变化"会被夹取/取整骗过去。实测（静音探针、真实时钟、60 秒 7 行）：行盒 **34.6 / 36.9 / 32.4 / 34.7 / 43.2 / 26.1 / 34.6** px vs 间隔 **10.21 / 9.00 / 9.62 / 11.95 / 7.23 / 9.60** 秒，排序一致；区间内未触发夹取 → 纯比例：`高度 ≈ 间隔 × 3.6px`。
- **把"时间"编进等宽文本时：用空格数，不要用绝对定位；尺度先对齐原来的密度**（02 0.4，2026-09）。用户要"音符间的距离 = 时间差"（"真正的需求指的是音符间的距离，而不是乐句的行距"）。做法：日志行内相邻音名的**字距 ∝ 两个音的音频时刻之差**（时间差 0 的同拍和弦至少留 1 个空格，否则糊成一团）。★ 三个决定：**① 用空格而不是 `<span>` 绝对定位** —— 那片日志本来就是一整片等宽纯文本（`pre-wrap`、可选中），绝对定位会把这个性质拆掉；代价是分辨率只有一个字符宽（13px Consolas 实测 **7.147px**，视口 1200px 时可用 **151 字符**）。**② 尺度先取"基本步长 = 1 个空格"**（原本 `LOG_NOTE_CHARS_PER_SECOND = 10`：0.3 秒 = 3 字符 = 音名 2 字符 + 1 空格 → **默认密度与改动前逐字符一致**；用户后来手调到 **4**，整行明显变紧）—— ★ 但**这个值有下限**：音名每推进一个占 3 字符，`每秒字符数 × 步长 < 3` 时字符推进会追过时间轴、间距全落最小值（实测 4 → 0.3/0.6 秒都看不出差别，6 才分得出 0.6 秒，10 = 原始密度）；**手调这类"每秒比例"时要顺手量一遍"哪些间隔还分得出来"**；调"时间→像素"的比例时，先把**名义/基本单位**对齐旧观感，再谈放大。**③ 超宽要整体压缩**（按可用字符数等比缩 `charsPerSecond`）：窄屏不换行，而且**相对疏密保持不变**。★ 验收要量**倍数关系**而不是"看起来有变化"：真实运行末行音名起始位置 `[7,22,31,43,49,70,79,91,97]`、相邻间距 `[15,9,12,6,21,9,12,6]` —— **全是 3 的倍数**，正落在 0.3 秒步长网格上（`间距 = 3 × 步数`）；取整与压缩都能让"有变化"成立，只有网格倍数能证明它真在跟时间走。★ 这条与我先前误做的"日志**行距** = 演奏间隔"是两件事（行距管行与行、本条管一行之内）：用户说行距那版"不是需求、先留着" —— **保留但别当成需求**，这类"先留着"的实现要在文档里标清楚它为什么在那儿。
- **"间隔/距离"要先问清是"行与行"还是"一行之内"，而且编码出来的间距必须有上下限、并在最窄视口上验证不换行**（02 0.4，2026-09）。这一轮先做错了粒度：用户说"页面中的乐句文本，文本间的间隔就是演奏的间隔"，我做成**行距** ∝ 两次演奏的时间差（实现本身没问题、实测排序一致性也对）；用户随后澄清 **"这并不是需求，真正的需求指的是音符间的距离，而不是乐句的行距"**，并要求 **"去掉乐句间不同的行距，恢复到之前"**。★ 教训一：**"间隔"是歧义词**（行距 / 字距 / 音距都叫间隔），动手前用一句确认代价极低，做错一版要返工两处（代码 + 文档）。★ 教训二：**把间距做成编码时一定要给上下限** —— 第一版只有"比例 + 下限"，最长的一次留白换成 **19 个空格（≈136px）**，用户立刻反馈 **"音符间的间隔要限制一下间隔的范围，现在有点太多了，移动端甚至出现了一行乐句断行"**；加上限（`LOG_NOTE_MAX_GAP = 5`）后音名间距夹在 **[3,7] 字符**，一行宽度因此有确定上限（桌面最坏 19 个音 92 字符 / 可用 151）。★ 教训三：**"放得下"要算准，不能估** —— 原先按 `跨度×每秒字符 + 音名字符` 估算再整体缩放，忽略了取整与最小间隔的地板，移动端实际仍会溢出几个字符而断行；改成**先排一遍、若超出就二分找刚好放得下的尺度**（下界 = 全部取最小间隔）才真正不断行。★ 教训四：**字宽/字距这类缓存要连着字号记** —— 移动端断点会把日志字号从 13px 降到 10px，只缓存宽度会让换断点后仍按旧值算可用字符数、于是又断行。★ 验收要在**真实最窄视口**上量"行盒高度是否等于单行高度"（390px 实测 `17.8/17.8/17.8`、溢出 `[0,0,0]`），并记下**理论最短**（19 音 = `19×2 + 18×1 = 56` 字符）：低于它的屏幕宽度无解，属已知边界而不是 bug。

- **03 0.3 的 3D 旋转必须读取实际音频时钟**：Tone.js 14.7.58 的 `Tone.Transport.seconds` 使用含 lookAhead 的时钟，实测比 `Tone.Transport.getSecondsAtTime(Tone.immediate())` 提前 0.100 秒。连续视觉用后者；实际击发仍由 `Tone.Draw` 报告，记录事件自己的 `fireAt`，不要用帧到达时间。圆柱带面的前端为 theta=0（+Z 播放头），带面从 `−duration/period×2π` 到 0，旋转直接由时间求值。灰轨道只画音段之外的互补弧并同步旋转，避免同半径完整轨道与带面共面产生深度冲突。

## 修改与验证要求

- 修改音乐逻辑时，同时检查注释和页面上的教学说明是否仍然准确。
- 修改 JavaScript 后至少执行一次语法检查。
- 涉及播放、停止、换一版或长时间调度时，应在浏览器实际验证控制台和生命周期。纯视觉改动可以绕开音频做无头验证：在仓库根目录起静态服务器（`python -m http.server 8765`），写一个临时探针页用同源 iframe 打开练习页，用 `iframe.contentWindow.eval()` 直接调用页面里的视觉函数并读取 DOM、属性与内部状态，Chrome 用 `--headless=new --user-data-dir=<临时目录> --virtual-time-budget=<ms> --screenshot=<png>`（沙箱会拦截 Chrome 的 IPC 命名管道，需要 danger-full-access；探针页与截图用完即删，不要提交）。注意无头环境里 rAF 会被节流到约 1 tick/500ms，动画循环等于不跑：先 `requestAnimationFrame = () => 0` 把调度停掉，再手动循环调用 `animateGraph()` 逐帧推进，物理与形态才可复现地验证（同时注意 `performance.now()` 几乎不前进，漂移项会退化成常量偏移）。★ 三个踩过的坑：**①页面内部的常量都是顶层 `const`，不是 window 属性** —— 探针里写 `w.graphMotion` 只会拿到 `undefined`，必须把驱动代码整段 `eval` 进 iframe 自己的全局作用域；**②无头 Chrome 的 stdout 常常拿不到**（`--dump-dom` 可能一个字都收不到），让探针页把结果 `fetch('/__report?line=…')` 发给本地静态服务器、再去读服务器日志才稳；**③量像素前先排除旁边的其他元素**（见“用像素验证……先查采样点旁边有没有别的元素”那条）。**④探针的传参单位要和页面内部一致** —— 02 0.4 的收尾冒烟里，我给 `onTextureStart(texture, time, duration)` 传了 `25000`（毫秒），可它内部按**秒**用（`duration` 来自 `texture.durationRange = [12, 25]`），于是"时间窗"变成 25005 秒、排程一次排出 **11736 发**，差点被当成调度 bug 去查代码；改成 `25` 后立刻是预期的 17 发。规律：**在看到离谱的数字时，先核对探针传参的单位**，再去怀疑被测代码。 **⑤ 要在探针里拉远程素材，就不能用 `--virtual-time-budget`** —— 虚拟时钟不等网络：预算（哪怕 60 秒）会在 2MB 的 mp3 回来之前就耗尽，页面在 `await fetch` 上死掉、一行报告都传不出去（现象是"探针只打了 boot 就没了"）。改用**真实时钟 + `--remote-debugging-port=<端口>` 保活**（不给 `--screenshot` 也不给虚拟时间），让页面自己把结果 `fetch` 到静态服务器日志即可（顺便还能在真实时钟下量真实耗时）。 **⑥ 跨 realm 的 Tone 选项对象不被认作 options** —— 在父页面里 `new (子页面的 Tone.Filter)({ type: 'lowpass', … })` 会报 `Invalid argument(s) to setValueAtTime: {…options…}, 0`（选项对象被当成了第一个位置参数）。探针要么在**页面自己的作用域里** `eval` 出来调，要么只调品牌方法、不自己构造带选项对象的节点。
- **无头探针会"真的出声"，而且 PowerShell 不会替你收尾**（02 0.4，2026-09 真把用户吵到了："你是在哪启动页面吗，我能听到，但是找不到窗口"）。两条都必须做：**① 加 `--mute-audio`** —— 为了让 AudioContext 真的 running（见上面那条"无头能跑完音频链"），必须加 `--autoplay-policy=no-user-gesture-required`，而它会让音频**真的送到系统输出设备**；`--mute-audio` 只静音输出、不影响上下文推进与调度，所以"验链路"和"不吵人"可以同时成立（无头没有窗口，用户听得见却找不到来源，体验非常糟）。**② 启动时拿 PID、结束时明确 kill** —— `& chrome.exe …` 在 PowerShell 里**不等 GUI 程序**（它只等控制台程序），于是后台任务显示"完成"时 Chrome 其实还在跑：这一轮我留下 **6 个**无头实例、**63 个**进程在放音乐，直到用户来问才发现。做法：`Start-Process -PassThru` 拿 `$p.Id`，或在收尾时按命令行过滤（`Get-CimInstance Win32_Process -Filter "Name = 'chrome.exe'"` 再匹配自己的 `--user-data-dir` 前缀）后 `Stop-Process -Force`，并**确认"剩余 0 个"**才算完事；临时 `--user-data-dir` 也要一起删掉。★ 顺带：沙箱下 `Get-CimInstance Win32_Process` 会被拒（"拒绝访问"），按命令行识别进程需要更宽权限；**识别不出来时绝不要用"杀掉所有 chrome.exe"这种粗暴办法** —— 那会把用户自己的浏览器一起关掉。
- **每个状态都要单独跑一次**：探针页的状态由 URL 参数决定，一次 Chrome 进程只截一张图；而且同一台机器上连续起多个 Chrome 实例容易互相干扰（同一个 `--user-data-dir` 会复用已有实例、页面根本不加载）—— 每次用独立的临时 `--user-data-dir`，并在两次之间留一点间隔。

- 保留用户已有实验和笔记，不要为了重构删除尚未确认无用的内容。
